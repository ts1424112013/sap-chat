## 一、项目背景速览（30秒校准）

- **项目**：SAP AI Chat（SAP Compass）——UI5 前端 + ABAP 后端（OData），内置 LLM Agent，支持库存工具与动态 SQL 业务分析
- **环境（2026-10-05 用户确认，取代此前的"760"记载）**：SAP S/4HANA **2020 SP03**（ABAP Platform 2020 = SAP_BASIS **755** SP0003，SAP_GWFND 755 SP3，SAP_UI 755 SP5，HANA 2.0 SPS05，系统 A4D/实例00/客户端470，Unicode，嵌入式 FES）。ABAP 代码按 **7.50 语法**编写——7.55 内核是 7.50 的严格超集，**已验证无需任何改动**；GENERATE SUBROUTINE POOL 已获公司允许
- **模型**：内网私有化 LLM（可接收所有业务数据）+ DeepSeek（仅本地测试用）
- **范围约束**：第一阶段仅 IT 账号；只读 SELECT；写操作明确不做
- **关键参数（已定，勿随意改）**：单 SQL 5000 行（硬上限 50000）、回填模型 200 行、单请求 5 次 run_sql（上限10）、Agent 10 轮 / 180 秒
- **项目不是 git 仓库**；ABAP 无法本地编译，验证靠人工核查；JS 靠 `node --check`
- **改动前备份**：`_backup_20261004/` 保存了改动前的后端与前端完整副本

### 3.2 可接受的设计差异（勿"修正"）

- **FROM 子查询**：计划书原定 7.50 不支持、直接拒绝；Codex 实现为放行（子查询内表仍逐表校验权限，编译不过时报错回模型）。核查结论：安全性不受影响，符合 P0 验收项"子查询可执行"。

### 3.3 本次会话（测试评估）发现的 5 个测试风险点（未修，仅记录）

test-server 的 5 个用例预计一次通过 3-5 个，以下风险属**断言/环境设计问题而非功能缺陷**：

1. **用例4 可能"假失败"**：断言要求 run_sql 必须出现 REJECTED 记录；但若模型不调工具直接口头拒绝（行为正确），断言反而失败。
2. **最终答案 ≤60 字符**：agent-loop 协议 final 答案写在 summary（≤60字符），5 个用例关键词都塞得进但很紧；需与真实 ABAP 端协议核对是否同样限制。
3. **本地通过 ≠ 安全通过（最重要）**：Mock 的 run_sql 校验仅 2 行（SELECT 开头 + 4 个写关键字），远弱于真实 ZCL_AI_SQL_GUARD（23 关键字整词匹配 + 敏感表黑名单 + VIEW_AUTHORITY_CHECK）。本地只验证 Agent 工作流，安全保证只能靠 SAP 端 7 个验收用例。
4. **用例2 可能跳过 describe_table**：领域卡已列出 VBAK 等表名，模型可能直接猜字段写 SQL。
5. **小问题**：temperature 0.7 对严格 JSON 协议偏高；JSON 解析正则贪婪匹配，多段大括号时解析失败会静默变 TIMEOUT；GENERAL 域传空 `tools:[]` 给 DeepSeek 未实测兼容性；Mock 中 EKPO 无字段定义（describe 返回 NOT_FOUND）；**Mock 无自建表（Z表）**。
