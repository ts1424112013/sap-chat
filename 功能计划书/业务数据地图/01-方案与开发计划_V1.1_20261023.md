## 0. 一页看懂

- **要解决的问题**：用户说一个业务（“看看 ABZ1 还有多少采购没到货”），模型应该知道**先用哪个数据源**（公司已有报表还是查表）、**查哪几张表、怎么关联**、**口径是什么**（哪些行要排除、单位怎么处理）。现在这些全靠模型按关键词搜表、凭通用 SAP 常识去猜。
- **做法**：建一张「业务数据地图」——按业务主题维护：典型问题、先问清楚的口径、数据源优先级、核心表与关键字段、表之间怎么关联、口径与坑、已验证的示例查询、核对方法。
- **怎么用上**：
  1. 用户提问时按关键词匹配主题，把最相关的 1–2 个主题**摘要直接注入**提示词（不多花一轮模型调用）。
  2. **结构化追问**：主题里定义了“先问清楚”的口径；问题有歧义、本任务也没确认过时，后端直接出选择卡（不调模型）；问题里已经说清楚的，自动按用户的说法定口径。
  3. **知识资源目录**：一对通用工具——`list_resources` 按关键词找资源，`read_resource` 按地址读取（如 `map:MM_PO_OPEN`、`table:EKET`、`join:EKPO,EKET`、`report:…`、`fiori:SHIPMENT`）。
  4. 之后仍走现有的 `describe_table` → `run_sql`，安全检查和权限校验不变。
- **维护**：一期每个主题一个 JSON 文件，放仓库里做版本管理，用 SE38 程序导入（与 Fiori 报表登记同一套做法）；二期在设置页维护，并加「口径正确」按钮沉淀已验证查询。
- **不做**：不接 MCP 协议（只借鉴思路，§1.3 / §1.4）；不新增任何数据权限，地图只是指引，取数仍按当前用户的权限。
- **样板**：出货、采购未清、库存三个主题（§5），配 18 道测评题（§6），用测评结果对比开 / 关地图的效果。
- **分期**：D0 样板核对 → D1 机制 + 三个样板上线 → D2 测评调优 → D3（二期）设置页维护、结构化追问卡、已验证查询沉淀、与技能入口合并 → D4 工具自动登记（§10）。

## 1. 要解决的问题

### 1.1 一个例子

用户在「数据分析」场景问：“ABZ1 工厂现在还有多少采购没到货，按供应商列一下”。

| | 现在 | 有了数据地图 |
|---|---|---|
| 第 1 步 | `search_tables("采购")`，返回几十张带“采购”字样的表 | 命中主题「采购未清」，摘要已在提示词里；“没到货”命中选项「未收货」，口径自动确定，不用追问 |
| 选表 | 模型凭常识选 EKPO，常漏掉 EKET（交货计划） | 地图写明 EKKO + EKPO + EKET，关联字段给出 |
| 口径 | “未到货”常被算成 `EKPO-MENGE` 全量，不排除删除行、交货已完成行 | 地图写明：未清 = 计划数量 − 已收货数量；排除删除 / 锁定、交货已完成、退货行 |
| 轮数 | 搜表 → 看字段 ×2 → 写 SQL → 报错重写，常用满 5 次 `run_sql` 额度 | 看字段 ×1（可省）→ 写 SQL，一般 2–3 轮 |
| 结果 | 数字偏大且说不清口径 | 数字可核对（ME2N 选择参数 WE101），回答里说明口径 |

如果用户只说“采购未清”，没说是没到货还是没开票：后端直接回一张选择卡（「未收货」/「已收货未开票」），用户点一下再查，不浪费一轮模型调用，也不会按错的口径算。

### 1.2 现状的短板

`ZCL_AI_DOMAIN_CARDS` 的「数据分析领域卡」里有一段写死的「常用业务表地图」，只有标准表名（如“MM 采购：EKKO / EKPO / EBAN”）。缺的是：

1. **关联路径**：表之间用哪些字段连、是 1:N 还是 N:1。
2. **公司自己的东西**：已登记的 TCode 报表、Fiori 报表（这才是公司口径），以及公司 Z 表。
3. **口径与坑**：删除标记、完成标记、单位 / 币种、S/4 里已经变成兼容视图的表（`VBUK`、`MSEG`、`KONV`）。
4. **歧义时怎么问**：现在靠模型自己决定要不要问、怎么问，问法每次不一样，前端也不一定能识别成选择卡。
5. **能改**：现在要改一个字都得重贴 ABAP 类。

### 1.3 为什么不接 MCP 协议

MCP 是一种把工具接进 AI 客户端的标准接口，它解决的是“工具怎么接”，不提供“业务数据在哪、怎么连”的知识。对照外部项目 `romankorim/sap-mcp-server`：它提供的读表、看字段、调只读 BAPI、查 OData，我们在 SAP 内部都已具备，而且按当前用户校验权限；接上它模型照样要靠猜。另外我们的 Agent 在 ABAP 里运行、调用公司内部模型，ABAP 侧没有 MCP 客户端；那个项目还用一个公共技术账号读数据，与我们“助手里看到的不能比 Fiori / SAP 里多”的规则冲突。

### 1.4 借鉴了 MCP 的哪些思路（V1.1）

不接协议，但 MCP 的几个设计思路正好对得上我们的问题：

| MCP 的思路 | 意思 | 本方案怎么用 |
|---|---|---|
| Resources（资源） | 只读知识用统一地址列出和读取 | **知识资源目录**（§4.4）：主题、表、关联、报表、Fiori、已验证查询都是“资源”，一对工具读全部 |
| Elicitation（追问） | 工具执行中向用户要结构化输入 | **结构化追问**（§4.5）：地图里定义问题和选项，后端出选择卡 |
| Tools 发现 | 客户端运行时问“有哪些工具”，新工具自动接入 | **工具自动登记**（§10），列为后续改造项 |
| Prompts（提示模板） | 服务端提供固定做法，用户用“/”选 | 就是「技能入口」的设计（输入“/”选技能），方向一致 |

| 现有能力 | 位置 | 本方案怎么用 |

| Agent 协议 | 模型每轮只回两种 JSON：`{"action":"tool",…}` 或 `{"action":"final","answer":…}` | 不改协议；追问用工具 `ask_clarify` 表达 |
| 业务卡片注入 | 组装消息时，按场景取 `get_card( domain )` 作为一条系统消息 | 地图摘要作为紧随其后的一条系统消息注入 |

| 前端参数卡 | 后端返回 `pendingParamsJson`：`kind = FIORI` 出 Fiori 参数卡，**其他一律当 TCode 报表参数卡（提交即执行报表）** | 一期**不能**用它出追问卡；二期给前端加 `kind = CLARIFY` 分支（§4.5.6） |
| 动态 SQL 安全检查 | `ZCL_AI_SQL_GUARD`：只许单条 SELECT；拦 `INTO` / `WITH` / `CLIENT` 等关键字和 `.` `;` `"` 等字符；表存在性 + 敏感表黑名单 + 表权限 | 样板 SQL 按这些规则写；导入时用它校验 |
| 表搜索与字段 | `ZCL_AI_DDIC_TOOLS`：`search_tables`（DD02T 描述 + 表名模糊）、`describe_table` | `list_resources` 的表搜索复用 `search_tables`；`read_resource(table:…)` 复用 `describe_table` 的读取与权限检查 |
| 报表登记 | `ZAI_RPT_DEF`（TCode 报表，键 `REPORT_ID`，另有 `TCODE` / `PROGNAME` / `REPORT_NAME` / `DESCRIPTION`）、`ZAI_FRPT_DEF`（Fiori 报表，键 `REPORT_ID`，另有 `KEYWORDS` / `DESCRIPTION`） | 作为 `report:` / `fiori:` 资源，实时判断是否已登记、已启用 |
| 库存专用工具 | `ZCL_AI_INVENTORY_TOOLS`：`resolve_material` / `get_stock_snapshot`（MARD）/ `get_daily_movement`（MSEG）/ `get_batch_stock`（MCHB） | 库存样板里作为“单料号查询”的首选数据源 |
| 预算 | 每次提问最多 10 轮、180 秒；`run_sql` 最多 5 次（`SQL_MAX_EXEC`） | 注入摘要、追问前置都省轮数；摘要限长 |
| 测评 | 前端测评窗口 + `webapp/model/evalCases.json`（`expect.tools` / `toolsAny` / `answerAny` / `answerRegex` / `maxRounds` / `maxSeconds`） | 每个样板 5 题 + 追问 3 题，开 / 关地图对比 |

## 3. 总体方案

### 3.1 流程

```text
用户提问（数据分析 / 自动场景）
  │
  ├─ ① 匹配主题：关键词 / 同义词（简繁英）+ 问题里点名的表名 → 得分最高的 ≤ 2 个主题
  │
  ├─ ② 判断口径（§4.5，后端完成，不调模型）：
  │     本任务已确认过 → 用已确认的
  │     问题里有选项识别词（“没到货”→ 未收货）→ 按它定
  │     标为「必须先问」且仍不清楚 → 直接回选择卡，本轮结束（0 轮模型调用）
  │     其余 → 用默认口径，回答里说明
  │
  ├─ ③ 注入摘要（系统消息，≤ 1200 字 / 主题）：已定的口径、数据源优先级（含本场景能不能用）、
  │     核心表与关联、关键规则、资源地址
  │
  ├─ ④ 模型按需调用：
  │     read_resource   —— 读完整主题卡、表结构 + 已知关联、两表关联路径、报表说明、示例查询
  │     list_resources  —— 摘要里没有时，按关键词找资源（含表搜索）
  │     ask_clarify     —— 取数中途发现地图里定义的歧义，由后端出选择卡
  │     describe_table / run_sql —— 现有，安全检查与权限不变
  │
  ├─ ⑤ 回答：数字可溯源，写明口径；首选数据源在别的场景时，提示用户去那个场景（不越权调用）
  │
  └─ ⑥（二期）用户点「口径正确」→ 这次的 SQL 进入待审核 → 管理员通过后成为该主题的已验证查询
```

### 3.2 一个主题里放什么

| 部分 | 内容 | 例（采购未清） |
|---|---|---|
| 基本信息 | 编号、名称、模块、关键词 / 同义词 | `MM_PO_OPEN`、采购未清、MM、“采购未清, 未到货, 未交货, open PO, 採購未清…” |
| 典型问题 | 3–5 个例子，用于匹配和测评 | “某供应商还有多少没交货”“逾期未交的采购单” |
| 先问清楚（结构化） | 每条：编号、问题、2–6 个选项（标签、说明、识别词）、默认选项、问不问 | `OPEN_KIND`：「未清」指哪一种？未收货（默认）/ 已收货未开票；问题里只有“未清”时先问 |
| 数据源优先级 | 依次：已登记报表 / Fiori（公司口径）→ 专用工具 → 表；每个写用途与所在场景 | 暂无登记报表 → 表 EKKO / EKPO / EKET |
| 核心表 | 表、角色（头 / 行 / 主数据 / 文本）、关键字段 | EKET：`EINDT` 交期、`MENGE` 计划数量、`WEMNG` 已收货 |
| 关联 | 两表之间的 ON 条件和基数 | `EKPO~EBELN = EKET~EBELN AND EKPO~EBELP = EKET~EBELP`（1:N） |
| 口径与坑 | 排除条件、单位 / 币种、S/4 差异、大表必带条件；可按选项分别写 | 排除 `LOEKZ` 非空、`ELIKZ = 'X'`、`RETPO = 'X'` |
| 示例查询 | 已在 SAP 上跑通的 SQL + 对应问题（可标注适用的选项） | “按供应商统计未清”（§5.2） |
| 核对方法 | 用哪个标准 / 公司 TCode 对数 | ME2N 选择参数 `WE101` |

### 3.3 数据源优先级与场景

1. **公司已有报表优先**：已登记的 TCode 报表（报表执行场景）或 Fiori 报表（Fiori 报表场景）承载的是公司口径，能用就用。
2. **专用工具其次**：如库存的料号级工具（精确、带校验）。
3. **最后才是查表**：标准表 / Z 表 + `run_sql`。

场景限制不放宽：数据分析场景里不能调报表或 Fiori 工具。首选数据源在别的场景时，摘要里会写明（例：“更准的来源：『Fiori 报表』场景的 shipment 報表”），模型照常用表回答，但必须告诉用户口径可能不同、建议去哪个场景查。是否在自动场景里据此直接切换，放到二期（§7 D3）。

### 3.4 与现有几样东西的关系

| | 管什么 | 在哪 | 谁维护 |
|---|---|---|---|
| 场景 | 能用哪些工具（白名单） | `ZCL_AI_TOOL_REGISTRY` | 开发 |
| 业务卡片（领域卡） | 场景通用规则：SQL 写法、报告格式、自查清单 | `ZCL_AI_DOMAIN_CARDS` | 开发 |
| **数据地图（本方案）** | **某个业务的数据在哪、怎么连、口径是什么、歧义时问什么** | **4 张表 + JSON** | **管理员 / 业务骨干** |
| 技能（设计中） | 某类任务怎么做：步骤、自查、输出格式 | 计划中的 `ZAI_AGENT_SKILL` | 管理员 |

技能可以引用主题（如技能「采购未清分析」引用 `map:MM_PO_OPEN`），二期在设置页里共用一个维护框架。地图上线后，领域卡里写死的「常用业务表地图」一段可以删掉，改由地图提供（待确认，§9）。

### 3.5 越用越准

数字对不对，最终靠“跑通过、对过数”的查询来保证。每个主题保存若干条**已验证查询**（问题 + SQL + 最近一次试跑时间 + 适用的口径选项）：

- 一期：随 JSON 维护，导入时经安全检查，并可选试跑一次。
- 二期：回答下方加「口径正确」按钮，把这次运行里的 SQL（来自运行记录）存为草稿，管理员审核通过后入库。

读主题卡时只返回与当前口径相符的、最多 2 条已验证查询，作为模型写 SQL 的范例；它们仍然只经 `run_sql` 执行，照常过安全检查和权限校验。

### 4.3 匹配与注入

- **计分**：关键词命中按词长加权（“采购未清”比“采购”权重高）；问题里出现某主题核心表名（如 `EKET`）直接加分；选项识别词也计入（“没开票”也能命中采购未清）；同时命中多个主题时取前 2 个。
- **阈值**：低于阈值不注入，模型照旧找资源（现有行为不变）。
- **长度**：每个主题摘要 ≤ 1200 字，合计 ≤ 2400 字；注入文本开头写明“以下是业务数据地图的参考，若与用户问题无关请忽略”，降低误命中的影响。
- **记录**：命中了哪些主题、得分、口径怎么定的（已确认 / 识别词 / 默认 / 追问），写进 Agent 运行步骤，测评时能看到。

注入摘要示例（采购未清，问题是“ABZ1 还有多少采购没到货”）：

```text
【业务数据地图 · 采购未清】(参考信息; 与问题无关请忽略)
口径(已定): 未清 = 未收货 —— 问题里说了"没到货"。回答开头写明这个口径。
数据源: 暂无登记报表 → 查表(本场景可用)。
核心表: EKKO 采购订单头(LIFNR 供应商, BSTYP, LOEKZ) / EKPO 行(WERKS, MATNR,
  MENGE, MEINS, NETPR, PEINH, LOEKZ, ELIKZ, RETPO) / EKET 交货计划(EINDT 交期,
  MENGE 计划数量, WEMNG 已收货) / LFA1 供应商名称(NAME1)
关联: EKKO~EBELN = EKPO~EBELN (1:N); EKPO~EBELN = EKET~EBELN AND EKPO~EBELP =
  EKET~EBELP (1:N); EKKO~LIFNR = LFA1~LIFNR (N:1)
规则: 未清数量 = EKET-MENGE - EKET-WEMNG, 只计 > 0 的计划行; 只看 EKKO-BSTYP = 'F';
  排除 EKKO/EKPO-LOEKZ 非空、EKPO-ELIKZ = 'X'、EKPO-RETPO = 'X'; 按 EKPO-MEINS
  分组, 禁止跨单位加总; 逾期 = EINDT < 今天。
核对: ME2N 选择参数 WE101。
资源: map:MM_PO_OPEN(完整卡与示例查询) / table:EKET / join:EKKO,EKPO,EKET
```

### 4.4 知识资源目录（V1.1，借鉴 MCP 的 Resources）

#### 4.4.1 地址

所有知识都是“资源”，地址写作 `<类别>:<编号>`（类别小写，编号大写）：

| 地址 | 内容 | 来源 | 权限 |
|---|---|---|---|
| `map:<TOPIC_ID>` | 完整主题卡：口径（含已定值）、数据源（含本场景可用性）、关联、规则、≤ 2 条相符的已验证查询、核对方法 | `ZAI_DMAP_*` | 只返回启用的主题 |

### 4.5 结构化追问（V1.1，借鉴 MCP 的 Elicitation）

#### 4.5.1 定义（存在 `CLARIFY_JSON`）

```json
[{
  "id": "OPEN_KIND",
  "question": "采购「未清」指哪一种？",
  "mode": "ASK",
  "trigger": "未清",
  "default": "GR",
  "options": [
    {"key": "GR", "label": "未收货", "desc": "已下单、仓库还没收到的部分（默认）",
     "match": "到货,收货,交货,交期,没来,未到,逾期,在途"},
    {"key": "IR", "label": "已收货未开票", "desc": "仓库已收、发票还没到的部分",
     "match": "发票,开票,对账,付款"}
  ]
}]
```

| 字段 | 说明 |
|---|---|
| `id` | 追问编号，主题内唯一 |
| `question` | 问句，必须以“？”结尾（前端选择卡靠它识别） |
| `mode` | `ASK` = 不清楚时先问再查；`DEFAULT` = 不问，按默认口径查并在回答里说明 |
| `trigger` | 可选。只有问题里出现这些词时才考虑追问（逗号分隔）；空 = 命中主题就考虑 |
| `default` | 默认选项的 `key` |
| `options` | 2–6 个选项；`label` ≤ 12 字，`label` + `desc` ≤ 50 字；`match` 是识别词，问题里出现即视为选了这一项 |

导入时校验：选项数、长度、问号、默认值存在、各选项识别词不重叠。

#### 4.5.2 口径怎么定（每条追问，按顺序）

| 顺序 | 条件 | 结果 | 记录为 |
|---:|---|---|---|
| 1 | 本任务最近几轮的用户消息里出现过某选项的 `label`（用户点过选择卡）或识别词 | 用该选项 | 已确认 |
| 2 | 本次问题里出现某选项的 `label` 或识别词 | 用该选项 | 识别词 |
| 3 | `mode = ASK`、`trigger` 命中（或为空）、`DMAP_ASK_FIRST = 'X'`，且本任务**没有**问过这一条 | **直接追问**：回选择卡，本轮结束，不调模型 | 追问 |
| 4 | 其他（含已经问过一次、用户没选就继续说别的） | 用 `default` | 默认 |

同一任务同一条追问最多问一次；第二次直接按默认口径回答并说明，避免反复追问。

#### 4.5.3 模型中途发起：工具 `ask_clarify`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `uri` | text | 是 | 主题地址，如 `map:MM_PO_OPEN` |
| `clarify_id` | text | 是 | 地图里定义的追问编号 |
| `lead` | text | 否 | 一句话引子（≤ 60 字），如“要统计 ABZ1 的采购未清，先确认一个口径：” |

只能问地图里定义好的追问，问句和选项由后端按定义生成，模型不能自己编选项；编号不存在时返回错误、本轮继续。调用成功后本轮结束，回答 = 引子 + 选择卡文本。

#### 4.5.4 一期的输出格式（前端零改动）

按 `AskCard.detectChoices` 能识别的格式输出：回答末尾一行问句（含“？”），紧跟 2–6 行编号选项，选项写成“标签：说明”：

```text
要统计 ABZ1 的采购未清，先确认一个口径：

采购「未清」指哪一种？
1. 未收货：已下单、仓库还没收到的部分（默认）
2. 已收货未开票：仓库已收、发票还没到的部分
```

前端显示为选择卡；用户点「未收货」后，选项原文作为下一条消息发出，后端在 §4.5.2 第 1 步识别为“已确认”，结合任务上下文里的原问题继续取数。

#### 4.5.5 为什么一期不用待填参数卡

前端现在只要收到非 Fiori 的 `pendingParamsJson`，就当作 TCode 报表参数卡，点提交会去执行报表（`StartReportRun`）。一期如果把追问放进 `pendingParamsJson`，会被误当成报表参数。所以一期只用文字选择卡，**不设置待填参数、不置 `needsInput`**。

#### 4.5.6 二期：结构化追问卡

- 后端同时返回 `pendingParamsJson = {"kind":"CLARIFY","topic":"MM_PO_OPEN","params":[{"param_id":"OPEN_KIND","data_type":"ENUM",…}]}`，复用参数卡的下拉 / 单选渲染（ENUM 已支持）。
- 前端 `_updateTaskState` 加 `kind = CLARIFY` 分支：提交时发一条规范消息（如“【口径】未清=未收货”）并带上原问题重发，不调报表接口。
- 好处：可以一次确认多条口径、带默认值预选、选择结果规范，后端识别更稳。

### 4.6 场景接入

开关打开时：

| 场景 | 口径判断 + 注入摘要 | 工具 | 说明 |
|---|---|---|---|

### 4.7 维护（一期）：JSON 导入导出

- 每个主题一个文件：`backend-abap/data-map/<TOPIC_ID>.json`，放仓库里，改动走提交记录，便于审阅。

  - 表存在（`DD02L`）、关键字段与 ON 条件里的字段存在（`DD03L`）；

  - `SUMMARY` 不超长；关键词不为空。
- 导入一个主题 = 整份替换该主题的数据源、关联和示例查询（`VERSION` + 1）。

### 5.1 出货（`SD_SHIPMENT`）

**范围**：已发货（交货单已过账发货）的数量，按日期、工厂、客户、物料等维度；以及未发货的交货单。

**关键词**：出货, 出貨, 发货, 發貨, 交货单, 交貨單, DN, 已发货, 未发货, shipment, ship mode, 出货量

**先问清楚（结构化）**

| 编号 | 问句 | 选项（识别词） | 默认 | 问不问 |
|---|---|---|---|---|
| `SHIP_BASIS` | 「出货」按哪种口径算？ | `PGI` 已过账发货：按实际发货日期（发货, 发出, 出库, 过账, 已出）<br>`DN` 交货单已创建：含还没发货的交货单（开单, 建单, 交货单创建）<br>`BILL` 已开票：按开票日期（开票, 发票, 出账） | `PGI` | `DEFAULT` |
| `RETURNS` | 退货要不要算进来？ | `EXCL` 不算：退货单独列出（默认）（不含退货）<br>`INCL` 算进来：按净额扣减退货（含退货, 扣退货, 净出货） | `EXCL` | `DEFAULT` |

| `VBFA` | 凭证流 | `VBELV` / `POSNV` 前序 → `VBELN` / `POSNN` 后续、`VBTYP_N` 后续类型（J 交货 / M 发票 / R 货物移动） |
| `KNA1` | 客户 | `KUNNR`、`NAME1` |

**关联**

| 左 | 右 | ON | 基数 |
|---|---|---|---|
| LIKP | LIPS | `LIKP~VBELN = LIPS~VBELN` | 1:N |
| LIPS | VBAP | `LIPS~VGBEL = VBAP~VBELN AND LIPS~VGPOS = VBAP~POSNR` | N:1 |

**口径与坑**

1. `[SHIP_BASIS=PGI]` 已发货 = `LIKP-WADAT_IST` 有值（或 `WBSTK = 'C'`），按 `WADAT_IST` 取日期范围。
2. `[SHIP_BASIS=DN]` 按交货单创建日期 `LIKP-ERDAT`；未发货交货单 = `WBSTK` 为 `A` / `B`。
3. `[SHIP_BASIS=BILL]` 按发票（`VBRK` / `VBRP`，经 `VBFA` 关联），一期不出样板 SQL。
4. S/4 里 `VBUK` / `VBUP` 已不再维护（只剩兼容视图），状态直接读 `LIKP` / `LIPS` 上的字段。
5. `LFIMG` 是销售单位数量，汇总必须按 `VRKME` 分组；跨物料汇总改用 `LGMNG` + `MEINS`，仍按单位分组。
6. 交货单上没有价格；要金额需从销售订单行或发票取。`KONV` 在 S/4 不能直接读（公司报表用 `V_KONV_CDS`）。一期样板不算金额。
7. `[RETURNS=EXCL]` 退货交货（交货类型待确认）单列，不与正常出货相加。
8. `LIPS` 是大表：先用 `LIKP` 的日期范围或工厂过滤。
9. `MAKT` 的语言：简体中文内部码 `'1'`、繁体 `'M'`，以系统实际维护为准（待确认）。

**示例查询（草稿）**

① 某月各工厂已发货数量（`SHIP_BASIS=PGI`）：

```sql
SELECT P~WERKS AS PLANT, P~VRKME AS UNIT,
       COUNT( DISTINCT L~VBELN ) AS DN_CNT,
       SUM( P~LFIMG ) AS SHIP_QTY
  FROM LIKP AS L
  INNER JOIN LIPS AS P ON L~VBELN = P~VBELN
  WHERE L~WADAT_IST BETWEEN '20260901' AND '20260930'
  GROUP BY P~WERKS, P~VRKME
  ORDER BY SHIP_QTY DESCENDING
```

② 某工厂到期未发货的交货单：

```sql
SELECT L~VBELN AS DN, L~WADAT AS PLAN_GI_DATE, L~KUNNR AS SHIP_TO, C~NAME1 AS SHIP_TO_NAME,
       P~MATNR AS MATERIAL, P~LFIMG AS QTY, P~VRKME AS UNIT
  FROM LIKP AS L
  INNER JOIN LIPS AS P ON L~VBELN = P~VBELN
  LEFT OUTER JOIN KNA1 AS C ON L~KUNNR = C~KUNNR
  WHERE L~WBSTK IN ( 'A', 'B' ) AND L~WADAT <= '20261022' AND P~WERKS = 'ABZ1'
  ORDER BY PLAN_GI_DATE
```

**核对**：Fiori shipment 页面（同条件）；`VL06G`（发货过账的出库交货）；`ZDPSD012`。

**待确认**：公司“出货”口径（过账发货 / 开票），两条追问该不该改成 `ASK`；ship mode 对应的字段（可能是 `LIKP-VSBED` 装运条件，也可能是 Z 字段）；退货交货类型、公司间交货是否计入；`ZRSD_IDP_0033` 的 TCode；两个报表是否登记。

### 5.2 采购未清（`MM_PO_OPEN`）

**范围**：已下单、未收货的采购订单（数量，可选金额），按供应商、工厂、物料、交期 / 逾期；另一种口径：已收货未开票。

**关键词**：采购未清, 未清, 未到货, 没到货, 未交货, 未收货, 在途采购, 逾期未交, open PO, 採購未清, 未交貨

**先问清楚（结构化）**

| 编号 | 问句 | 选项（识别词） | 默认 | 问不问 |
|---|---|---|---|---|
| `OPEN_KIND` | 采购「未清」指哪一种？ | `GR` 未收货：已下单、仓库还没收到的部分（到货, 收货, 交货, 交期, 没来, 未到, 逾期, 在途）<br>`IR` 已收货未开票：仓库已收、发票还没到的部分（发票, 开票, 对账, 付款） | `GR` | `ASK`，`trigger = 未清` |
| `AMOUNT` | 要不要算金额？ | `QTY` 只看数量：不算金额（默认）（数量, 多少件, 多少个）<br>`AMT` 加上金额：按订单价格近似计算（金额, 多少钱, 价值, 价钱） | `QTY` | `DEFAULT` |

`OPEN_KIND` 的效果：问题只说“采购未清”时先问；说了“没到货 / 逾期”就直接按未收货查；说了“没开票”就按发票口径。

**数据源优先级**

| 优先 | 类型 | 引用 | 场景 | 用途 / 说明 | 状态 |
|---:|---|---|---|---|---|
| 10 | 报表 | 候选：标准 `ME2N`（程序 `RM06EN00`，选择参数 `WE101`） | 报表执行 | 标准口径的未清清单（`OPEN_KIND=GR`） | 候选：需先验证 ALV 采集能否取到，再登记 |
| 20 | 表 | EKKO / EKPO / EKET（+ LFA1 / MAKT / EKBE） | 数据分析 | 按任意维度统计、逾期分析 | 可用 |

**核心表与关键字段**

| 表 | 角色 | 关键字段 |
|---|---|---|
| `EKKO` | 采购订单头 | `EBELN`、`BSTYP`（F 订单 / K 合同 / L 计划协议）、`BSART` 订单类型、`LIFNR` 供应商、`EKORG`、`EKGRP`、`BEDAT` 订单日期、`WAERS` 币种、`LOEKZ` |
| `EKPO` | 行项目 | `EBELN`、`EBELP`、`MATNR`、`TXZ01` 短文本、`WERKS`、`LGORT`、`MENGE`、`MEINS` 订单单位、`NETPR`、`PEINH` 价格单位、`LOEKZ`（L 删除 / S 锁定）、`ELIKZ` 交货已完成、`RETPO` 退货行、`PSTYP` 项目类别 |
| `EKET` | 交货计划 | `EBELN`、`EBELP`、`ETENR`、`EINDT` 交期、`MENGE` 计划数量、`WEMNG` 已收货数量（均为订单单位） |
| `EKBE` | 订单历史 | `EBELN`、`EBELP`、`VGABE`（1 收货 / 2 发票）、`SHKZG`（S / H）、`MENGE`、`BUDAT` |
| `LFA1` | 供应商 | `LIFNR`、`NAME1` |

**关联**

| 左 | 右 | ON | 基数 |
|---|---|---|---|
| EKKO | EKPO | `EKKO~EBELN = EKPO~EBELN` | 1:N |
| EKPO | EKET | `EKPO~EBELN = EKET~EBELN AND EKPO~EBELP = EKET~EBELP` | 1:N |
| EKPO | EKBE | `EKPO~EBELN = EKBE~EBELN AND EKPO~EBELP = EKBE~EBELP` | 1:N |
| EKKO | LFA1 | `EKKO~LIFNR = LFA1~LIFNR` | N:1 |
| EKPO | MAKT | `EKPO~MATNR = MAKT~MATNR AND MAKT~SPRAS = '1'` | N:1 |

**口径与坑**

1. `[OPEN_KIND=GR]` 未清数量按**计划行**算：`EKET-MENGE − EKET-WEMNG`，只计大于 0 的行；不要用 `EKPO-MENGE` 直接当未清。
2. 排除：`EKKO-LOEKZ` / `EKPO-LOEKZ` 非空、`EKPO-ELIKZ = 'X'`（交货已完成，剩余量不再交）、`EKPO-RETPO = 'X'`（退货行）；只看 `EKKO-BSTYP = 'F'`。
3. 数量是订单单位 `EKPO-MEINS`，按单位分组，禁止跨单位加总。
4. `[AMOUNT=AMT]` 金额只能近似：未清数量 × `NETPR` ÷ `PEINH`；价格单位与订单单位不同（`BPRME`）时不准，回答必须注明；币种 `EKKO-WAERS`，按币种分组。
5. EKPO 一行有多条 EKET 时，按行汇总前不要把 EKPO 的数量字段一起 SUM（会重复计数）。
6. `[OPEN_KIND=IR]` 已收货未开票 = 收货净量 − 发票净量：用 `EKBE`，`VGABE = '1'` 为收货、`'2'` 为发票，按 `SHKZG` 区分正负（冲销为 H）；一期不出样板 SQL，先在 D0 确认口径。
7. 逾期：`EKET-EINDT < 当天` 且仍未清。

**示例查询（草稿）**

① 某工厂按供应商统计未清（`OPEN_KIND=GR`，数量按单位分组）：

```sql
SELECT K~LIFNR AS VENDOR, V~NAME1 AS VENDOR_NAME, P~MEINS AS UNIT,
       COUNT( DISTINCT P~EBELN ) AS PO_CNT,
       SUM( E~MENGE ) AS SCHED_QTY,
       SUM( E~WEMNG ) AS GR_QTY
  FROM EKKO AS K
  INNER JOIN EKPO AS P ON K~EBELN = P~EBELN
  INNER JOIN EKET AS E ON P~EBELN = E~EBELN AND P~EBELP = E~EBELP
  LEFT OUTER JOIN LFA1 AS V ON K~LIFNR = V~LIFNR
  WHERE K~BSTYP = 'F' AND K~LOEKZ = ' ' AND P~LOEKZ = ' '
    AND P~ELIKZ = ' ' AND P~RETPO = ' '
    AND E~MENGE > E~WEMNG AND P~WERKS = 'ABZ1'
  GROUP BY K~LIFNR, V~NAME1, P~MEINS
  ORDER BY SCHED_QTY DESCENDING
```

未清数量 = `SCHED_QTY − GR_QTY`（只统计了未清的计划行，所以差值就是未清量）。若试跑确认 7.50 支持 `SUM( E~MENGE - E~WEMNG )`，改成直接输出 `OPEN_QTY`。

② 逾期未交的计划行明细（`OPEN_KIND=GR`）：

```sql
SELECT K~EBELN AS PO, P~EBELP AS ITEM, K~LIFNR AS VENDOR, P~MATNR AS MATERIAL,
       E~EINDT AS DUE_DATE, E~MENGE AS SCHED_QTY, E~WEMNG AS GR_QTY, P~MEINS AS UNIT
  FROM EKKO AS K
  INNER JOIN EKPO AS P ON K~EBELN = P~EBELN
  INNER JOIN EKET AS E ON P~EBELN = E~EBELN AND P~EBELP = E~EBELP
  WHERE K~BSTYP = 'F' AND K~LOEKZ = ' ' AND P~LOEKZ = ' '
    AND P~ELIKZ = ' ' AND P~RETPO = ' '
    AND E~MENGE > E~WEMNG AND E~EINDT < '20261022' AND P~WERKS = 'ABZ1'
  ORDER BY DUE_DATE
```

**核对**：`ME2N` / `ME2L`（按供应商）选择参数 `WE101`；单张订单用 `ME23N`。

**待确认**：公司间调拨（`BSART = 'UB'`）、外协（`PSTYP = '3'`）、服务行是否计入；是否需要金额；“已收货未开票”的公司口径；`ME2N` 能否经 ALV 采集取数并登记。

**关联**

| 左 | 右 | ON | 基数 |
|---|---|---|---|
| MARD | MARA | `MARD~MATNR = MARA~MATNR` | N:1 |
| MARD | MAKT | `MARD~MATNR = MAKT~MATNR AND MAKT~SPRAS = '1'` | N:1 |
| MARD | MARC | `MARD~MATNR = MARC~MATNR AND MARD~WERKS = MARC~WERKS` | N:1 |
| MCHB | MARD | `MCHB~MATNR = MARD~MATNR AND MCHB~WERKS = MARD~WERKS AND MCHB~LGORT = MARD~LGORT` | N:1 |
| MARD | MBEW | `MARD~MATNR = MBEW~MATNR AND MARD~WERKS = MBEW~BWKEY AND MBEW~BWTAR = ' '` | N:1（估价范围 = 工厂、非分割估价时） |
| MSEG | MARA | `MSEG~MATNR = MARA~MATNR` | N:1 |

**口径与坑**

1. 库存按类型分开列（非限制 / 质检 / 冻结 / 退货 / 在途），不要只报 `LABST` 就叫“库存”。
2. `[STOCK_SCOPE=SLOC]` 项目库存（`MSPR`）、寄售（`MKOL`）、销售订单库存（`MSKA`）不在 `MARD` 里，回答里注明“不含项目库存与寄售”；`[STOCK_SCOPE=ALL]` 用 `ZRMM_IDP_0003C`。
3. `MARD` 只有当前值；某个历史日期的库存要用报表 `0003C`（或 `MB5B`），不要自己倒推。
4. `[VALUE_BASIS=MBEW]` `MBEW` 是工厂级总值，不是库位级；库位金额只能用数量 × 单价近似；`[VALUE_BASIS=COMPANY]` 用 `0003C`（含“非成本数据用移动平均价”等公司口径）。
5. 基本单位 `MARA-MEINS`，不同单位的物料不能加总。
6. 收发净额按 `SHKZG` 区分方向；冲销是成对的移动类型（101 / 102、261 / 262、601 / 602……），统计时不要只看收货类型。
7. `MSEG`、`MARD` 在 S/4 是兼容视图，`MSEG` 取数必须带过账日期范围和工厂。
8. 0 行是有效结论（该范围内没有库存记录），不是失败。

**示例查询（草稿）**

① 某工厂库存最多的物料（含质检、冻结；`STOCK_SCOPE=SLOC`）：

```sql
SELECT D~MATNR AS MATERIAL, T~MAKTX AS DESCR, A~MEINS AS UNIT,
       SUM( D~LABST ) AS UNRESTRICTED, SUM( D~INSME ) AS QUALITY, SUM( D~SPEME ) AS BLOCKED
  FROM MARD AS D
  INNER JOIN MARA AS A ON D~MATNR = A~MATNR
  LEFT OUTER JOIN MAKT AS T ON D~MATNR = T~MATNR AND T~SPRAS = '1'
  WHERE D~WERKS = 'ABZ1'
  GROUP BY D~MATNR, T~MAKTX, A~MEINS
  ORDER BY UNRESTRICTED DESCENDING
```

② 某段时间按移动类型统计收发：

```sql
SELECT M~BWART AS MVT_TYPE, M~SHKZG AS DEBIT_CREDIT, M~MEINS AS UNIT,
       COUNT( * ) AS LINE_CNT, SUM( M~MENGE ) AS QTY
  FROM MSEG AS M
  WHERE M~WERKS = 'ABZ1' AND M~BUDAT_MKPF BETWEEN '20261001' AND '20261022'
  GROUP BY M~BWART, M~SHKZG, M~MEINS
  ORDER BY QTY DESCENDING
```

**核对**：`MMBE`（单料号）、`MB52`（仓库库存）、`MB51`（物料凭证清单）、`MB5B`（按日期库存）、`ZRMM_IDP_0003C`。

**待确认**：公司“库存”是否含项目库存 / 寄售 / 在途（决定 `STOCK_SCOPE` 默认值）；库龄与金额是否一律以 `0003C` 为准；`0003C` / `0018` / `0021` 的 TCode 与是否登记；公司 Z 表（如 `ZIDPMM016` / `ZIDPMM017` 库位附加信息、`ZIDPMMWHCD` 仓码对应账册、`ZIDPMMAGING` 库龄）的用途，决定要不要写进地图。

## 10. 后续改造项：工具自动登记（借鉴 MCP 的 Tools 发现）

### 10.1 现在的问题

新增一个 Agent 工具要改三处：`ZCL_AI_TOOL_REGISTRY=>get_tools`（工具定义）、`get_tools_for_module`（场景白名单）、`ZCL_AI_AGENT_SERVICE` 主循环里的 `IF` 分支（执行与结果处理）。`AGENT_SERVICE` 是全系统最大、最核心的类，每加一个工具就要整类重贴一次，部署风险高；场景白名单也写死在代码里，调整就要改代码。

### 10.2 做法

照 MCP 的“工具清单 + 工具调用”约定，在 ABAP 里定义一个能力提供者接口，每个能力模块自己报工具、自己执行，Agent 只负责分发：

```text
接口 ZIF_AI_CAP_PROVIDER
  get_tools( iv_scene )                      → 本模块在该场景提供的工具定义（名称、说明、参数、只读与否）
  call_tool( iv_tool, iv_args_json, is_ctx ) → 结果 JSON + 控制标记（结束本轮 / 需要用户输入 / 待填参数 / 计入 SQL 次数 / 数据集）
  （可选）list_resources / read_resource     → 资源类提供者（如数据地图）

登记表 ZAI_CAP_PROVIDER
  PROVIDER_ID / CLASS_NAME / SCENES / ACTIVE / SORT_NO

AGENT_SERVICE
  组装工具清单 = 各启用提供者的 get_tools( 当前场景 )
  分发        = 工具名 → 提供者 → CREATE OBJECT (CLASS_NAME) → call_tool
  特殊处理    = 只看 call_tool 返回的控制标记，不再按工具名写分支
```

### 10.3 迁移步骤

1. 定义接口与登记表，`AGENT_SERVICE` 改为按提供者分发，但现有工具先用一个“兼容提供者”包住，行为不变。
2. 逐个拆出提供者：库存（4 个工具）、动态 SQL（`search_tables` / `describe_table` / `run_sql`，带 SQL 次数与数据集标记）、报表只读、代码分析、数据地图（`ZCL_AI_DATA_MAP` 已按这个形状写，加上 `INTERFACES` 即可）。
3. 场景白名单从代码移到登记表的 `SCENES`。
4. 每一步前后都跑原有 29 道测评题 + 本方案 18 道，结果不变才进下一步。

### 10.4 收益与风险

| | 说明 |
|---|---|
| 收益 | 新增能力 = 新建一个类 + 登记表加一行，不再重贴 `AGENT_SERVICE`；场景白名单可配置；每个提供者可以单独测试 |
| 风险 | 改的是 Agent 主循环；`run_sql` 的次数限制、数据集收集（图表引用）、追问结束本轮等特殊逻辑必须通过控制标记完整保留；动态 `CREATE OBJECT` 的错误在运行时才暴露 |
| 对策 | 兼容提供者先行、逐个迁移、每步跑测评；部署自检程序（已提为单独任务）检查登记表里的类都存在且实现了接口 |
| 时机 | 待定（§9 Q11）。建议在数据地图 D2 之后单独做：那时数据地图本身已按接口形状写好，可以作为第一个迁移的提供者 |
