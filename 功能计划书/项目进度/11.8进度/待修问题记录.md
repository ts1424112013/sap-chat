# 11.8 待修问题记录

## #01 新引擎写文件不限文件类型（待修）

**发现**：2026-11-08，问「写入文件时可以创建和写哪些文件」时对照引擎代码发现。

**现状**：新引擎在用户选的文件夹里能新建 / 覆盖 / 修改文本文件，每次写前确认、改前备份到 `.lingxi/备份/`；不能删文件、不能执行命令；`.lingxi/` 对模型只读。但写入时**不检查扩展名**（`agent-bundle/src/folder-backend.js` 的 `_guardWrite` 只拦路径和 `.lingxi/`）。

**问题**
1. 模型能写出 `.bat` / `.cmd` / `.ps1` / `.vbs` / `.sh` 等脚本文件。引擎自己不会运行，但用户没细看就双击会在电脑上执行。
2. 模型只能写文本，写进或覆盖 `.xlsx` / `.docx` / `.pdf` / 图片会变成打不开的文件（有备份能恢复，但用户会困惑）。

**修法**
- `_guardWrite`（写、改）只允许常见文本类型（txt / md / csv / tsv / json / xml / yaml / sql / abap / html / log 等，和读文件的文本类型对齐）；
- 脚本类、Office、PDF、图片一律拒绝，错误提示让模型改存成 CSV 或 Markdown（要 Excel 用 `save_result_to_folder` 存 CSV）；
- 系统说明（FOLDER_PROMPT）补一句能写哪些类型；引擎自测加用例；只改前端（引擎包），SAP 不用改。

## #02 新引擎不能删除文件（待做，和 #01 一起改）

**发现**：2026-11-08，用户问「某个文件不想要了，可以删除吗」。

**现状**：模型没有删除工具（Deep Agents 给的文件工具只有 ls / read_file / write_file / edit_file / glob / grep），文件不想要只能用户自己去文件夹里删；删除整个文件夹的代码也完全没有。`folder-backend.js` 里已有 `delete()`：删前确认、备份到 `.lingxi/备份/`、记修改记录、撤回能恢复；时间线确认卡也已有「删除」样式。只差包成工具交给模型。

**做法**
- 新工具 `delete_file`（只删单个文件，调 `FolderBackend.delete`）；文件夹、`.lingxi/`、`灵犀记忆.md` 不能删；
- 每次都确认，「本次运行都不再询问」对删除不生效（`allowAllWrites` 跳过删除）；
- 系统说明：只在用户明确说要删时才删，不为「整理」自己删；
- 引擎自测加用例（删除需确认、拒绝不删、本次都允许不覆盖删除、撤回能恢复）；只改前端（引擎包），SAP 不用改。

## #03 新引擎问代码时丢了「代码分析规则」（待修，和 #01 / #02 一起改）

**发现**：2026-11-08，评估「IT 用 Agent 写 / 改代码」时对照 `browser_start` 发现。

**现状**：V15.23 起新引擎永远是「自动」，系统说明里的领域卡由 `zcl_ai_domain_cards=>match_domain( 问题 )` 选；`match_domain` 从不返回代码域（代码域原本「仅场景显式选择」）。结果：有代码分析权限时 `read_program_source` / `describe_table` 工具照样给了，但代码分析领域卡没进系统说明，丢了这几条规则：按 keyword 定位不要从头通读大程序、结论引用行号、只陈述源码里看得到的、source_hidden / 非自开发对象如实说、不凭记忆补全代码。问代码时更容易编造。

**修法**（SAP，`ZCL_AI_AGENT_SERVICE`）
- 有代码分析权限时，新引擎系统说明里总带上代码规则（或问题像代码问题时带上）；
- 去掉旧卡里只为原引擎 JSON 协议写的限制（「回答 1500 字以内、每段代码不超过 15 行」），新引擎不需要；
- 静态检查加用例。

## 改进项：需求文档写程序（方案待写）

**背景**：2026-11-08 用户问「我们一般有需求文档，用需求文档让模型去写如何」。

**现在能做**：需求另存为 .md / .txt 放进文件夹 → Agent 读需求 + `describe_table` / `read_program_source` 核对 → 写「设计.md」让 IT 确认（口径不清弹问题卡）→ 分段写 .abap 文件 → IT 贴进 SE38 激活、报错贴回再改。

**短板**：新引擎读不了 .docx / .pdf（当二进制）；没有语法检查，改错循环靠人；长程序前后不一致、输出慢（约 37 token/秒）；不知道公司规范；受 #03 影响。也没有写代码的测试题（现有 CODE 题 5 道全是解读 / 审查 / 表结构 / 边界）。

**补充（2026-11-08）：需求文档多数是 Excel → 读 Excel 优先于读 Word**
- 现状：新引擎读不了 .xlsx（当二进制），附件按钮只收文本；项目里没有 Excel 库。临时办法另存 CSV：一次只存当前页、合并单元格只剩左上角、截图 / 颜色标记 / 批注全丢。
- 做法（只改前端，不加库）：.xlsx 是压缩包里的 XML，用浏览器自带解压（DecompressionStream）在 `folder-backend` 读文件时转成文字——全部工作表带表名、每行带单元格位置（如 B5）、合并单元格范围、批注；底色 / 删除线先简单标注（可第二步做）；图片提示「此页有 N 张图片未读取」；.xls（2003 及以前）提示先另存 .xlsx（用户确认需求文档都是 .xlsx，不引入 SheetJS；若以后要支持 .xls，用 SheetJS 官网 0.20 以上版本，npm 上 0.18.5 有已公开漏洞）。
- 大文件按工作表分开、每页限大小，模型要哪页读哪页。
- 最好拿一份脱敏的真实需求 Excel 调提取效果。

**建议顺序**
0. 新引擎读 .xlsx（见上，优先）；
1. 「需求文档写程序」技能：读需求 → 查表核对 → 写设计让人确认 → 分段写代码 → 自查清单 + 公司 ABAP 规范（命名、程序头、AUTHORITY-CHECK、只用 7.55 语法）；只写内容不改代码；
2. 新引擎能读 Word：浏览器里解压 .docx 取文字（只改前端）；PDF 先不做；
3. 语法检查工具：源码交给 SAP 做语法检查，返回报错和行号，不保存不激活（提升最大）；
4. 拿 2～3 份已完成的真实需求文档 + 最终代码做对照测试，再决定推广；另建 10～15 道写 / 改代码测试题。

## #04 已部署的灵犀写 SQL 成功率低（待取日志后修）

**发现**：2026-11-08 用户反馈：部署上去的灵犀，模型写 SQL 时经常编译失败或报其他错，成功率很低。

**链路**：模型写 SELECT → `ZCL_AI_SQL_GUARD` 校验 → `ZCL_AI_SQL_EXECUTOR` 自动拼 `INTO TABLE @DATA(...) UP TO n ROWS`，GENERATE SUBROUTINE POOL 编译执行（严格新式 Open SQL）。已拦住：点号别名、LIMIT/TOP、当前日期函数、DATEDIFF、双引号、中文别名、自写 INTO。

**怀疑原因（按可能性，待日志确认占比）**
1. `describe_table` 最多回 150 个字段，MARA / EKPO / VBAP / MSEG 等有 200~400 个，后面的字段模型看不到只能猜 → 「字段不存在」编译错。
2. 原引擎每轮一个工具、`describe_table` 一次一张表：3~4 张表的 JOIN 光准备就用掉 7~8 轮（上限 `AGENT_MAX_ROUNDS` 10、`AGENT_BUDGET_SEC` 180 秒），再错一两次就超限。
3. 严格 Open SQL 细节编译时才暴露：聚合 / 计算列没写 `AS 别名`；JOIN 同名字段没别名（重名）；函数括号内没空格；数量金额用 `/` 相除；GROUP BY 漏字段；CASE / COALESCE 类型不一致。每错一次耗一轮和一次执行（`SQL_MAX_EXEC` 默认 5）。
4. 数据分析领域卡（`ZCL_AI_DOMAIN_CARDS`）写着「当前系统 7.50」，据此禁 CTE（`WITH`）和窗口函数，实际是 7.55 都支持；还主动推荐 UNION ALL 合并多维度（各段类型 / 长度要求严，易错）。`ZCL_AI_SQL_GUARD` 关键字黑名单也拦了 `WITH`、`WINDOW`。另：run_sql 工具说明写「禁止子查询(FROM 后)」，与守卫注释不一致。
5. 前导零（ALPHA）：写 '131002' 而非 '000000131002' 不报错但查 0 行，用户也当失败。
6. 已修：SQL 超 200 字符编译失败（10.28 #02，`ZCL_AI_SQL_EXECUTOR` V1.3，应已在 11-07 部署）——SE24 确认有常量 `gc_seg_max = 180`。

**待用户提供**：SE16N 导出 `ZAI_SQL_LOG` 最近 1~2 周 Excel：CREATED_AT / USERNAME / SESSION_ID / STATUS（OK / ERROR / REJECTED）/ RESULT_ROWS / ERROR_MSG / SQL_TEXT。拿到后按原因分类、算成功率与占比，再定修复顺序。

**可能的修法（数据确认后再动）**
- `describe_table` 一次查多张表、可按关键字筛字段，或超 150 个字段时只列名称和类型；
- 守卫自动做机械修正（括号空格、聚合列别名等），不浪费一轮；
- 领域卡改成 7.55、放开 CTE、不再推荐 UNION ALL；
- 新引擎一轮可并行调多个工具，原因 2 大幅缓解——尽快在 SAP 部署新引擎本身就能提高成功率。

**2026-11-09 日志结论与处理**（日志：`唐思成/SQL成功率低/sql導出結果.xlsx`，10-12 ~ 11-05 共 159 条，成功 47%）：失败 84 条里，括号写法 50、超 200 字符 21（10-28 已修，现场确认 `gc_seg_max = 180`）、UNION 带 UP TO 6、`||` 拼接 2、补零过长 3、其他 2。上面怀疑的 1（字段看不全）、5（前导零查 0 行）在日志里看不出来（0 行结果记为 OK）。已改：守卫 V1.2.4 自动补括号空格、`||` 改 `&&`；执行器 V1.4 UNION 不拼 UP TO；域卡 V1.7 不再推荐 UNION ALL、写明补零长度。同时定了分流：普通用户业务问题先找报表（参数卡预填），IT 自由 SQL 经 ADT 执行。见《03》〇-AQ、`功能计划书/业务问答分流/01-方案与第一批_V1.0_20261109.md`。未在 SAP 激活。
