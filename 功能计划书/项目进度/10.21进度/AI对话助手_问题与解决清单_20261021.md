## 问题 1：REPORT_SERVICE 签名块激活风险 ✅

**现象**：源码包预检发现 REPORT_SERVICE V1.0.12 实现区方法之间有 19 个 `<SIGNATURE>` 签名注释块（119 行）。

**根因**：TA 从 SE24 源码视图拷出类源码继续编辑，把显示装饰一并带入了仓库文件。按 09-04 实证铁律，**实现区方法之间的注释不可存储**（报 unknown comments can't be stored）。

**解决**：交付去签名块版——删除全部 119 行装饰注释，1352 条逻辑行逐行比对一致（逻辑零改动），贴入激活通过。

**教训**：SE24 拷出的类源码会带签名块装饰，整类粘贴前先剥。

## 问题 2：4 张权限表缺 MANDT 首键 ✅

**现象**：激活 ZCL_AI_AUTH_SERVICE 报 4 处 `LS_SAVE/LS_TAB/LS_RULE/RS does not have a component called "MANDT"`（L754/771/835/1687）。

**根因**：ZAI_AUTH_TAB / ZAI_AUTH_FMAP / ZAI_AUTH_RULE / ZAI_AUTH_REQ 四张表建表时没有按文档附录要求补首键 MANDT（CLNT 3，主键）。代码里显式 `ls_xxx-mandt = sy-mandt`（踩坑档案 #8 的写法），表里没有该组件即编译失败。

**解决**：SE11 逐表在字段列表第一行插入 MANDT 并勾键字段，激活后类一次通过。

**附带提醒**：Fiori 4 张表 + ZAI_CHAT_TEXT 的代码不显式赋 mandt（走 ABAP SQL 隐式集团处理），缺了字段编译不报错——属静默风险，需一并核对全部 9 张表。

## 问题 3：AUTH_SERVICE 方法间注释不可存储 ✅

**现象**：激活报 `The class contains unknown comments which can't be stored`。

**根因**：19 处 `"==== 公开方法 ===="` 风格的横幅注释卡在实现区方法之间。当日早间的预检扫描器只查了 `*` 风格注释，`"` 风格是盲区。

**解决**：交付零注释版——注释头原样保留（含 ★ 核对标记），其余 59 行整行注释 + 14 处行尾注释剥除，14 个截断点逐点人工核验全部落在注释上，逻辑零改动。激活通过。

**教训**：方法间注释扫描必须双风格（`*` 与 `"`）；方法体内部注释系统可存，无需清除。

## 问题 4：AGENT_SERVICE 报 GC_SCENE_FIORI unknown ✅

**现象**：激活 ZCL_AI_AGENT_SERVICE V15.4 报 4 处 `The field "GC_SCENE_FIORI" is unknown`，系统提示相似字段 GC_SCENE_AUTO / GC_SCENE_CODE / GC_SCENE_INVENTORY。

**根因**：依赖顺序跳步。`gc_scene_fiori = 'FIORI'` 是 INTENT_ROUTER V1.0.6 新增常量，系统内还是 V1.0.5（旧常量集），而 AGENT V15.4 编译期就要看得见它。

**解决**：先贴并激活 INTENT_ROUTER V1.0.6，回 Agent Service 直接重新激活（源码已在），4 错全消。

**教训**：卡片上的部署顺序（ROUTER → CHAT → AGENT → DPC_EXT）就是编译期依赖链，跳步必炸。

## 问题 6：前端调用 FI 报 404 Invalid Function Import Parameter ✅（当日最大坑）

**现象**：部署完成后前端权限链全线 404，报错参数名漂移——AuthSubmit 报 'Tcode'，AuthList 有时报 'Skip' 有时报 'Tcode'；直接浏览器调用、经 dev-server 代理调用表现不一致。

**排查弯路**（记录避坑）：元数据逐项核对全对 → 网关双层缓存清理无效 → 重新 Generate Runtime + 激活 MPC 无效 → /IWFND/ERROR_LOG 显示异常在 IWCOR URI 解析层且报错名随调用方变化——一度误判为「缓存收敛」，绕行近 3 小时。

**实锤方法**：手动补全全部 5 个参数调用 `AuthList?Top='50'&Skip='0'&Status=''&User=''&Tcode=''` → 返回 `Success=X` + 空列表，根因坐实。

**根因**：该版本 SEGW 的 FI 参数网格**没有 Nullable 勾选列**，生成代码 `set_type_edm_string( )` 未置可空 → **12 个 FI 的全部参数默认必填**。前端 4 处调用省略了空参数（如 AuthList 只发 Top/Skip），网关在 URI 解析层直接拒绝。且 **$metadata 不序列化 FI 参数的必填性**——这就是「元数据看着全对、运行时却炸」的表象矛盾来源。

**解决**：前端 `webapp/service/ChatService.js` 的 `_authCall` 出口统一补全——12 个 FI 参数映射表（`mAuthParams`）恒定全参数发送，调用方未给的键补空串（后端 `list_requests` 空串语义 = 不过滤，已核源码确认），映射表之外的键一律丢弃（防拼错键名）。语法检查 + 5 组 URL 模拟全过。其余 8 个 FI 调用点全量审计确认均发全参数，不受影响。

**教训**：
1. `Invalid Function Import Parameter 'X'` 报的是**缺失的必填参数名**——先对 URL 看缺哪个再动手，别先怀疑缓存；
2. FI 参数的必填性不进 $metadata，「元数据全对」≠「运行时不挑刺」；
3. 报错参数名随调用方漂移 ≠ 缓存收敛，先分清请求来源。

## 问题 7：Fiori 报表登记导入报全空 ⏳（当日唯一未解决项）

**现象**：ZAI_FRPT_MAINT 以 P_IMP + P_TEST 导入登记 JSON（登记版与原版模板均试过），校验报 `reportId 必填` + 6 条 `参数 paramId 必填`——JSON 结构解析到了（6 个参数节点被数出），但所有叶子值读取为空。

**已排除**：
- 文件内容：交付版字节级自检（无 BOM、键名逐个正确、reportId=SHIPMENT）；原版模板同错 → 与具体文件无关
- 读取环节：gui_upload 带 `codepage='4110'`（UTF-8）且已剥离 BOM（ZAI_FRPT_MAINT L99-113）
- 静态分析：SHAPER 的 parse/child/text/cfg/root 逻辑自洽（sXML 真 JSON 解析，格式不敏感），未发现可产生该症状的缺陷

**头号嫌疑**：部署的 ZCL_AI_ODATA_SHAPER 与仓库版本不一致（该类当日首建，登记 JSON 的 DOM 路径 parse/child/text/cfg 从未被任何用例覆盖——G0 的 P_SELF 也不测这条路径）。

**下一步（已定性的定位路线）**：调试器断点 `ZCL_AI_FIORI_REPORT_SERVICE=>save_def_json`（parse 调用之后），运行导入，观察三层：
1. `lv_json` 前 200 字符——应以 `{"reportId"...` 开头；异常则问题在读取/选错文件；
2. `lo->MT_NODES` —— NAME='reportId' 的行 KIND 应为 'S'、VALUE 应为 'SHIPMENT'；
3. `lo->MT_KIDS` —— PARENT=1 中 NAME='reportId' 是否存在（NAME='params' 必在，对比二者差异即答案）。

若部署 SHAPER 与仓库不一致 → 重贴 `backend-abap\ZCL_AI_ODATA_SHAPER.abap` 后复测即收口。

**附带进展**（不受此阻塞）：G0 的 T1 已实锤——`DynamiFIELDSet('SHMODE')` + expand 正常返回（d:Name=SHMODE / d:Value=D/C）；SHIPMENT 登记版 JSON 已按真实抓包填好（维度→`Group`、日期→`BegDat`/`EndDat` 显式 `eq`，依据 build_filter 代码语义），四个可选参数（SITE/MODEL/REGION/BU）待 $metadata 属性名后补 v2。
