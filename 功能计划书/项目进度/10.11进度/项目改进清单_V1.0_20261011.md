### 2.1 P0 · 正确性与上线门槛

#### FE-01 · `_taskCall` 的 CSRF 重试把查询串拼两遍　〔P0 · S〕

- **位置**：`webapp/service/ChatService.js` `_taskCall`（拆分后约 L558）。`fnBuild` 内两处 `sUrl += "?" + …`；重试在 `fnTry`。
- **问题**：`sUrl` 是外层闭包变量，`fnBuild` 每调用一次就往上追加一遍查询串。令牌失效触发 403 重试时，第二次请求 URL 变成 `…/StartReportRun?A='x'&B='y'?A='x'&B='y'`。
- **为什么现在才暴露**：d40cfe6 修了 `_isCsrfFail`（L1523；旧写法严格比较，V15.0.1 起错误带响应体后永不命中），重试路径此前从未真正执行过——这是修复暴露出来的回归。
- **影响**：`StartReportRun` / `ReportRunStatus` / `ReportResult` / `TaskAction` / `Tasks` 在 CSRF 令牌过期后返回 400/404，而不是自动恢复。
- **依据**：【确认】
- **改法**：在 `fnBuild` 内用局部变量拼本次请求的 URL 并随 `oInit` 一起返回（或把查询串拼装移出 `fnBuild`，参数不随令牌变化）。保持 ES5。
- **验收**：① 浏览器控制台执行 `ChatService._sCsrfToken = "bad"` 后提交一次报表运行：Network 里第二次请求的 URL 只含一份参数且返回 200；② PROC-03 的 Node 测试：fake fetch 先 403 再 200，断言第二次 URL 中 `?` 只出现一次。
- **部署影响**：仅前端（`npm run build` → dist）。

#### FE-02 · `_v8Call` 把后端失败当成功　〔P0 · S〕

- **位置**：`ChatService.js` `_v8Call`（拆分后约 L1154），判断：`if (d.Success && d.Success !== "X")`。
- **问题**：V8 系列接口失败时后端返回 `Success=''` + `Message`；空串为假，条件不成立，函数把空的 `d.Json` 当成功返回，调用方 `.then()` 照常提示成功。
- **影响**：开通 SU01 中不存在的用户仍提示"已开通"（`onAddUser`，现在在 `controller/mixin/SettingsPanel.js`）；保存配置 / 角色 / 提示词 / 会话更新失败时界面无任何提示。**C 批的 BE-08 让后端会拒绝非法的角色 / 提示词清单，但这个拒绝要等本项修好后前端才看得到。**
- **依据**：【确认】前端逻辑；【推断】`Success` 序列化为空串（而非单个空格或缺失）——先做 §4 T-01。
- **改法**：响应里带 `Success` 字段且不等于 `"X"` 就抛 `Error(d.Message || "调用失败")`；字段缺失（旧后端）保持放行。`_taskCall` 已是严格判断（`d.Success === "X"`），可对照。
- **验收**：用不存在的用户 ID 点"开通" → 出现后端消息（"SU01 中不存在用户 …"），列表不新增；保存成功路径不受影响。
- **部署影响**：仅前端。

#### BE-01 · `parse_model_json` 丢代码围栏与缩进　〔P0 · S〕

- **位置**：`ZCL_AI_AGENT_GUARD.parse_model_json`（V1.1.3 中约 L137 起）：`REPLACE ALL OCCURRENCES OF REGEX` 删三反引号（约 L142）、`CONDENSE lv_raw`（约 L143）、`FIND FIRST OCCURRENCE OF REGEX '\{.*\}' … SUBMATCHES`。
- **问题**：① L127 在整串里删除**所有**三反引号（包括 `answer` 字符串内部的代码围栏）；② L128 `CONDENSE` 把连续空格压成一个，代码缩进丢失；③ L135 的正则没有捕获组，`SUBMATCHES` 取不到值，"截取 JSON 对象"实际不生效——模型在 JSON 前后带文字时只能走修复重试。

#### BE-03 · SQL 校验层专项加固 + 负面用例集　〔P0 · M–L · 暂缓〕

- **状态**：2026-10-11 决定暂缓（内网、仅 IT 账号）。**放开给业务用户之前必须做**——它同时也是"模型写出的危险 / 超重 SQL"的最后一道闸。
