## 0. 一页看懂

- **做什么**：让 Gale-SAP 能读取公司已有 Fiori 报表的数据，用户自己决定要不要交给模型分析。
- **怎么取数**：Fiori 页面在浏览器里怎么调用 OData，ABAP 就在服务器内部以**当前用户身份**原样调用一次。报表逻辑、口径、权限全部复用，不读底层表、不重写业务逻辑。
- **怎么通用**：所有 OData 服务对外都是"URL 进、JSON 出"。不同报表的差异放进登记配置：参数怎么拼成 `$filter`、返回结果是什么"形状"。**新增一张报表只加配置，不写代码。**
- **界面**：新增「Fiori 报表」场景，首页是按业务分类的报表目录；选报表 → 参数卡 → 取数 → 表格 / 图表 → 「交给模型分析」（不点就不发给模型）。
- **隔离**：与「报表执行（TCode）」完全分开，现有 TCode 报表链路（`ZCL_AI_REPORT_SERVICE` / `ZCL_AI_REPORT_EXEC_SAP` / `ZCL_AI_REPORT_MOCK` / `ZAI_RPT_*`）一行不改。
- **分期**：G0 验证 → G1 单张报表打通 → G2 模型分析 → G3 登记助手 + 多选合并 → G4 上线。

## 3. 总体方案

### 3.1 原理

```text
Fiori 页面：  浏览器 ──GET /sap/opu/odata/sap/ZSD_IDP_001_SRV/DynamiFIELDSet?...──▶ Gateway ▶ DPC_EXT（报表逻辑）▶ 数据库
                                                                              ▲
Gale-SAP：    前端 ▶ ZAI_CHAT 服务 ▶ ZCL_AI_FIORI_REPORT_SERVICE ──同一个 URL（服务器内部调用）──┘
```

为什么不用另外两种方式：

| 方式 | 不选的原因 |
|---|---|
| 读底层表（run_sql） | 口径在 DPC 代码里，自己重写容易和页面对不上；每张报表都要重写一遍 |
| 直接实例化 DPC_EXT 调方法 | 要构造 Gateway 内部的请求上下文对象，每个服务不一样，做不成通用的 |

### 3.2 场景调整与隔离边界

**场景按钮**（前端 `SceneModels.SCENES`）：

```text
改前：报表执行 · 数据分析 · 库存查询 · 代码分析 · 自动
改后：报表执行 · Fiori 报表 · 数据分析 · 代码分析 · 自动
```

- 新场景代号 `FIORI`，名称暂定「Fiori 报表」（改名只是改 i18n 文案）。
- **「库存查询」只隐藏前端按钮**：后端 `INVENTORY` 场景和库存工具保留，旧的库存会话照样能打开（前端按「自动」显示），「自动」场景里问库存照样能答。

**隔离边界**

| 类别 | 对象 |
|---|---|
| **不改** | `ZCL_AI_REPORT_SERVICE`、`ZCL_AI_REPORT_EXEC_SAP`、`ZCL_AI_REPORT_MOCK`、`ZAI_RPT_DEF / PARAM / RUN / RESULT / STEP`、现有报表 FI |
| **新建** | 表 `ZAI_FRPT_DEF / PARAM / RUN / DATA`；类 `ZCL_AI_ODATA_CLIENT`、`ZCL_AI_ODATA_SHAPER`、`ZCL_AI_FIORI_REPORT_SERVICE`；FI `FioriReportDefs`、`RunFioriReport`、`FioriReportResult` |
| **追加修改**（只加分支，不动已有逻辑） | `ZCL_AI_INTENT_ROUTER`（新场景）、`ZCL_AI_AGENT_SERVICE`（FIORI 分支、分析闸门、白名单键）、`ZCL_AI_TASK_SERVICE`（新增常量）、`ZCL_ZAI_CHAT_DPC_EXT`（3 个 WHEN 分支）、前端 `SceneModels` / `AskCard` / `ChatService` / `MockBackend` 等 |

### 3.3 用户流程

**入口一：从目录选**（主路径）

1. 进「Fiori 报表」空会话 → 首页显示报表目录：按业务分类页签（全部 / 销量分析 / 采购 / 生产…）、搜索框。G1 单选，G3 支持多选。
2. 点一张报表 → 前端发出消息「选择报表：shipment報表」（走 `AnalyzeTask`，会话、任务、侧栏标题都由现有机制生成）。
3. 后端按报表名**精确匹配**登记表（报表名唯一，见 §5.1），不经过模型，直接返回参数卡（待填参数 JSON，§4.5）。
4. 用户确认参数 → 前端调 `RunFioriReport`（同步）→ 后端拼 URL、内部调用、转换、落库、登记结果 → 返回表格数据。
5. 前端显示结果：表格 / 柱状 / 折线 / 饼图 / 导出 Excel；步骤条标明"模型只知道行数和列名，没看到数据"；下面是「交给模型分析」按钮（§3.4）。

**入口二：直接说**

- 用户输入"10 月 HHZZ 的出货" → 后端在登记表里按报表名、分类、关键词、说明做**确定性匹配**（G1 不用模型）：
  - 只命中 1 张 → 直接出参数卡；
  - 命中多张 → 选择卡（复用 `AskCard` 的 choice 形态）让用户挑；
  - 没命中 → 场景说明（列出分类和报表数），提示用目录选。
- 从这句话里自动预填参数（如"10 月""HHZZ"）放到后面（§12 F7）：一期参数卡用登记的默认值。

**追问**

- "按 region 再看一次" = 换参数再取数：后端识别为对当前报表的重跑，弹出预填好的参数卡。
- 针对数据的提问（"哪个最大"）受 §3.4 的分析闸门约束。

### 3.4 数据给模型的规则（分析闸门）

| 情况 | 模型能看到什么 |
|---|---|
| 选报表、匹配报表、出参数卡 | 只有登记信息（报表名、参数定义），没有业务数据 |
| 取数完成后 | 只有"取到 N 行、有哪些列"，**没有数据行** |
| 用户点「交给模型分析」，或明确说"分析一下 / 解读 / 总结这个结果" | 该结果的后端统计 + 最多 `FIORI_MODEL_ROWS` 行（默认 200）；该运行标记 `ANALYZED = 'X'`，之后同一结果的追问可以用数据 |
| 未同意前直接问数据问题 | **不发数据**，确定性回复："这份结果还没交给模型，点「交给模型分析」后再问" |
| 报表登记 `ANALYZE_ENABLED` 为空 | 不显示按钮；分析请求一律确定性拒绝 |

## 4. 后端设计

### 4.1 取数：`ZCL_AI_ODATA_CLIENT`

| 项 | 规则 |
|---|---|
| 调用方式 | `cl_http_client=>create_internal( )` 在本系统内部调用 ICF，不经过网络，不需要 SM59 |
| 方法 | 只允许 GET；不发 CSRF；不支持 `$batch` |
| URI | `SERVICE_PATH` + `/` + `ENTITY_SET` + `?` + `$filter` + 固定查询项 + `$format=json` + `sap-client=<sy-mandt>` + `sap-language=<sy-langu>`；不带主机名 |
| 路径校验 | `SERVICE_PATH` 必须以 `/sap/opu/odata/` 开头、只含 `[A-Za-z0-9_/]`；拼好的 URI 超过 `FIORI_MAX_URI`（默认 2000）字符则拒绝 |
| 超时 | `FIORI_TIMEOUT_SEC`（默认 60）；超时如实返回，不重试 |
| 响应大小 | 超过 `FIORI_MAX_BYTES`（默认 20 MB）拒绝并提示缩小查询范围 |
| 错误 | HTTP 非 200：取响应里 OData 错误的 `message` 原文返回；401 / 403 提示"没有这张报表的权限"（就是 Fiori 页面上的权限） |
| 分页 | 若响应带 `__next`，最多跟随到 `MAX_ROWS` 行为止，超出截断并标记 |

示意代码（形参、异常名以 SE24 / SE37 实际签名为准，踩坑清单 §2.1 第 9、11 条）：

```abap
cl_http_client=>create_internal( IMPORTING client = lo_http ).
cl_http_utility=>set_request_uri( request = lo_http->request uri = lv_uri ).
lo_http->request->set_method( 'GET' ).
lo_http->send( ).
lo_http->receive( ).
lo_http->response->get_status( IMPORTING code = lv_code ).
lv_json = lo_http->response->get_cdata( ).
lo_http->close( ).
```

**G0 前提验证（开工第一步）**

写一个 SE38 测试程序 `ZAI_TEST_ODATA_INTERNAL`（选择屏幕：URI，带默认值 = shipment 的请求行），验证四件事：

| # | 验证 | 通过标准 |
|---|---|---|
| T1 | 能否调通 | HTTP 200，拿到与 F12 一致的 JSON |
| T2 | 是否以当前用户身份运行 | 在 DPC 侧（或 `/IWFND/TRACES`）看到的用户 = 执行测试程序的用户；换一个**没有该 Fiori 角色**的账号运行，应被拒（401 / 403 或业务报错） |
| T3 | JSON 能否通用解析 | `/ui2/cl_json` 把响应解析成通用数据（`REF TO data`），能按路径取到 `d.results[*].DynamicDataSet.results[*].Value` |
| T4 | 耗时与大小 | 记录典型查询的耗时和响应字节数，用来定 `FIORI_TIMEOUT_SEC` / `FIORI_MAX_BYTES` 默认值 |

T2 不通过的退路：SM59 建一个指向本系统的 HTTP 目标（类型 H），用登录票据传当前用户，改用 `create_by_destination`；需要 Basis 配置本系统接受自己签发的票据。T1 / T3 不通过：重新评估方案，此前不写后续代码。

### 4.2 参数 → `$filter`

每个参数登记一条 `ZAI_FRPT_PARAM`（§5.2），后端按下表拼条件，多个参数之间用 `and` 连接：

| `FILTER_OP` | 用途 | 生成的条件 |
|---|---|---|
| `EQ` | 单值 | `Prop eq 'v'` |
| `IN` | 多值 | `(Prop eq 'a' or Prop eq 'b')` |
| `BT` | 范围，同一个属性 | `(Prop ge 'a' and Prop le 'b')` |
| `BT2` | 范围，起止是两个属性（如 `BegDat` / `EndDat`） | `PropFrom ge 'a' and PropTo le 'b'`（两端运算符可在 `SHAPE_CFG` 之外单独配，见 §5.2 `OP_FROM` / `OP_TO`） |
| `SUBSTR` | 模糊 | `substringof('v', Prop)` |

值格式（`VALUE_FMT`）：

| 格式 | 写法 | 校验 |
|---|---|---|
| `STRING` | `'v'`，单引号写成两个 | 长度 ≤ 登记长度，超长**拒绝不截断** |
| `DATETIME` | `datetime'2026-10-01T00:00:00'` | 必须是合法日期 `YYYYMMDD` |
| `INT` / `DECIMAL` | `123` / `12.5M` | 完整数值形态 `^-?\d+(\.\d+)?$`（踩坑清单 §2.7） |

拼好的 `$filter` 整体做 URL 编码。空值参数不出现在条件里；必填参数为空则拒绝。

### 4.3 结构转换：`ZCL_AI_ODATA_SHAPER`

把各种返回结构转成统一数据集：

```text
ty_dataset = { columns: [{ name, label, numeric }], rows: [ { name: value, ... } ], truncated, total }
```

| 形状（`SHAPE`） | 例子 | 处理 |
|---|---|---|
| `FLAT` | `d.results` 每条是一行 | 直接成行；去掉 `__metadata`；`SHAPE_CFG.columns` 为空时取全部属性，列名即标签 |
| `PIVOT` | shipment：`DynamiFIELD` 是列，`DynamicDataSet` 是列值 | 按 `Position` 排列，按下标把各列拼成行；`Description` 作列标签 |
| `EXPAND` | 抬头 + 行项目 | 抬头字段复制到每个行项目上，展平成明细行 |

`SHAPE_CFG`（JSON）示例：

```json
// PIVOT（shipment）
{ "colList": "d.results", "colName": "Name", "colLabel": "Description", "colOrder": "Position",
  "valueList": "DynamicDataSet.results", "valueField": "Value",
  "unpivot": { "enabled": true, "keyLabel": "月份", "valueLabel": "数量" } }

// FLAT
{ "rowList": "d.results", "columns": [ { "prop": "Werks", "label": "工厂" }, { "prop": "Menge", "label": "数量" } ] }

// EXPAND
{ "rowList": "d.results", "itemList": "ToItems.results", "headerCols": ["Vbeln"], "itemCols": ["Posnr", "Matnr", "Kwmeng"] }
```

统一清洗：

- 去掉前后空格（shipment 的 `"     139418"`）；去千分位；ABAP 尾负号 `100-` → `-100`；`/Date(1640995200000)/` → `2022-01-01`。
- 一列的值去空格后**全部**符合完整数值形态 → 标 `numeric = true`（不用 `parseFloat` 前缀判断，踩坑清单 §2.7）。
- **PIVOT 对齐检查**：各列值个数不一致时不硬拼，如实报"返回结构列长度不一致"（某格无值时后端是否补空值，要在 DPC 代码里确认，见 §12 F2）。
- 逆透视（可选，`unpivot.enabled`）：把"维度列 + 多个期间列"转成"维度 / 期间 / 数值"长表，**只用于统计和给模型**，前端默认仍显示透视表。

### 4.4 报表服务：`ZCL_AI_FIORI_REPORT_SERVICE`

| 方法 | 可见性 | 说明 |
|---|---|---|
| `enabled` | PUBLIC | 读 `FIORI_ENABLED` |
| `list_defs` | PUBLIC | 目录用：`ACTIVE='X'` 的报表 + 参数（参数按 `ty_param` 同名字段序列化，见 §5.2），按 `CATEGORY`、`SORT_NO` 排序 |
| `get_def` / `get_params` | PUBLIC | 单张报表定义 / 参数 |
| `find_by_name` | PUBLIC | 「选择报表：xxx」精确匹配（多个名字用顿号分隔，G3） |
| `find_candidates` | PUBLIC | 一句话找报表：报表名、关键词、分类、说明的包含匹配打分，取前 5 |
| `validate_params` | PUBLIC | 必填、类型、长度、多值 / 范围、枚举值；错误逐项返回（与 `AskCard` 回显口径一致） |
| `build_filter` | PRIVATE | §4.2 |
| `run` | PUBLIC | 幂等（`REQUEST_ID`）：校验 → 拼 URI → `ZCL_AI_ODATA_CLIENT` → `ZCL_AI_ODATA_SHAPER` → 写 `ZAI_FRPT_RUN` / `ZAI_FRPT_DATA` → `ZCL_AI_TASK_SERVICE=>register_artifact`（类型 `FIORI_RESULT`、来源 `SNAPSHOT`）→ 返回结果 |
| `get_result` | PUBLIC | 按结果编号读取（归属校验：`OWNER = sy-uname`）；返回结构与 `ZCL_AI_REPORT_SERVICE=>ty_result` **同名同字段**（`label`、`schema_json`、`rows_json`、`row_count`、`summary_json`…），前端和分析链路不用分两套 |
| `compute_stats` | PUBLIC（G2） | 每个数值列的合计、最大 / 最小；每个维度值的占比和排名（前 10）；PIVOT 的期间列算相邻期间变化率；输出 `summary_json` |
| `set_analyzed` / `is_analyzed` | PUBLIC（G2） | 分析闸门（§3.4） |

### 4.6 SEGW / DPC_EXT

三个 Function Import，返回类型都用现有 ComplexType `GenericResult`（`Success` / `Message` / `ResultJson`），DPC_EXT 加三个 WHEN 分支，输出前经 `to_generic_odata`（踩坑清单 §2.3）：

|---|---|---|---|

## 8. 安全与审计

1. **只调登记过的服务**：URI 由登记配置 + 校验过的参数拼成，模型不参与拼 URI；路径必须是 `/sap/opu/odata/...`；只发 GET。
2. **权限 = Fiori 页面的权限**：以当前用户身份调用（G0 验证），`S_SERVICE` 和 DPC 里的权限检查照常生效，用户在助手里看到的不会比在 Fiori 里多。
3. **参数值一律校验和转义**（§4.2），超长拒绝不截断。
4. **登记表只有 ADMIN 能改**：一期用 SM30 维护；G3 的登记助手页面只对 `ZAI_CHAT_USER.ROLE = ADMIN` 开放。
5. **模型只在用户同意后看到数据**（§3.4），且有行数上限。
6. **全量留痕**：每次取数一条 `ZAI_FRPT_RUN`（谁、何时、哪张报表、什么参数、实际 URI、HTTP 码、行数、耗时、是否交给模型）。

## 11. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 内部调用不是当前用户身份（G0 T2 失败） | 权限会越过 Fiori 页面 | 换 SM59 登录票据方式；不通过前不写后续代码 |
| 某些报表很慢或数据量大 | FI 超时（ICM 超时同样适用） | 默认 60 秒 + 大小上限；目录说明里写清建议的查询范围；必要时以后做异步（与改进清单 BE-10 一起考虑） |
| 自写 DPC 不支持 `$filter` 的某些运算 | 条件被忽略，取到全量 | 登记时用登记助手 / 测试程序先验证；`REQUEST_URI` 可复现 |
| PIVOT 某格无值时后端不补空 | 拼行错位 | 对齐检查（§4.3）；以 DPC 代码确认 |
| 报表口径随源系统改版变化 | 登记配置失效 | 运行失败如实报错；登记表可随时改，不用重新部署代码 |
