## 一、Kimi 文章横评的 10 款工具：借鉴结论

### 1.1 先说结论

**10 款里 0 款可以直接搬进我们的环境，但它们的机制设计全部可以吸收**——而且对照后发现：我们已定的方案没有走偏，主要机制人家都有对应物；真正值得**新增**吸收的是 3 个点（见 1.3）。

### 1.2 十款工具分类与可用性判断

| 分类 | 工具 | 形态 | 对我们可用？ |
|---|---|---|---|
| 无代码/低代码云平台 | Gumloop、Stack AI、Lindy、Relay.app、Voiceflow | 云端 SaaS，拖拽编排 | ❌ 数据不出内网的硬约束直接排除 |
| 企业级云平台 | Copilot Studio、Gemini Enterprise、OpenAI AgentKit | 云生态绑定 | ❌ 同上（且 Copilot Studio 需 M365 生态） |
| **开源自托管平台** | **n8n、Dify** | 可内网 Docker 部署 | ⚠️ 技术上可行，MVP 阶段不引入（见下） |

**n8n / Dify 为什么先不引入**：它们要求新部署一个编排服务器、SAP 接口桥、凭据管理与运维流程，会把 MVP 从"ABAP 内嵌 Agent"扩展为跨系统项目，收益不足以覆盖成本。首期在 ABAP 内完成受限循环即可；但不能把工作量乐观估为“约 600 行”——工具注册、参数校验、权限、审计、异常和测试加在一起，应按一个独立子模块规划。若后续出现多系统串联、复杂人工审批队列或长流程任务，再评估 n8n/Dify；届时复用稳定的 ABAP 工具 API，不推翻首期设计。

### 1.3 机制借鉴对照表（核心收获）

| 来源工具的机制 | 我们方案中的对应物 | 状态 |
|---|---|---|
| Gumloop：节点逐步传递上下文 | Agent 循环中将**已裁剪的工具结果**回填消息数组 | 首期实现 |
| Stack AI：记忆系统 | 当前会话消息为短期记忆；跨会话记忆不进入首期 | 已有基础 |
| n8n：**AI 决策与确定性逻辑分离**（条件/脚本节点） | ABAP guard、工具 Schema、权限与汇总规则；模型仅决定下一步 | **首期铁律** |
| Relay.app：**人工审批节点（human-in-the-loop）** | 工具注册表的 `needs_confirm` 字段 | 二期；首期只读，不注册写入工具 |
| Dify：**知识库挂载** | 领域知识卡，描述业务口径和可用工具，不直接暴露任意 SQL | 首期实现库存首卡 |
| Dify：模型可切换 | `ZAI_MODEL_CFG` 模型配置与现有 AUTO 路由 | ✅ 已有基础；候选 Flash 模型待 P0 验证 |
| Voiceflow：结构化对话路径 | 库存 MVP 采用固定流程；开放式自主循环留在框架能力中 | 首期实现 |
| OpenAI AgentKit：工具调用 | 工具注册表 + 严格 JSON 意图协议 + ABAP Schema 校验 | 首期实现 |
| Gemini：预构建组件库 | 工具库按领域沉淀复用 | 后续迭代 |

一句话：**首期用“工具注册表 + 受限循环 + 领域知识卡 + ABAP guard”实现内嵌 Agent**；模型永远不能直接执行 SQL、调用任意 OData 或决定权限。

## 二、业务场景走查："分析 0001 工厂当天 A 料号的库存数据"

### 2.1 用户原始 4 步流程的映射与修正

| 你的步骤 | 映射到方案 | 修正/补充 |
|---|---|---|
| 1. 意图分析：怎么分析、查哪些表 | Agent 第 1 轮抽取槽位（工厂、料号、日期、分析范围）并选择库存工具 | **不能让模型裸猜表或字段**；知识卡只提供业务口径及工具说明，表和 SQL 固化在工具实现中 |
| 2. 通过 OData 动态调用已配置接口 | 工具注册表 handler 直接调用 ABAP 服务类 | Agent 位于 ABAP 后端，不能再绕回自身 OData；首期**不提供**通用 `query_table_data` |
| 3. 结果给模型判断是否符合用户需求 | 循环的反思（reflect）环节 | **补充结构化反思清单**（§2.5），特别是"空结果 ≠ 查询失败"的语义区分 |
| 4. 符合后整理返回对话页 | final 环节 → 复用现有聊天消息流 | 文字报告可复用现有页面；“查看过程”需新增 Trace 返回字段和前端展示，不能宣称零改动 |

### 2.2 第 1 轮的关键难点："当天"是歧义词（必须处理）

这是本场景最有教学意义的一点：

- **MARD（库位库存）是实时余额快照**——没有时间维度，查出来就是"现在"的库存，天然满足"当天"的一半含义；
- **"当天"的另一半含义是"指定过账日期的收发变动"**——余额表里查不到，需要查物料凭证数据。首期拟以 MSEG 的 `BUDAT_MKPF`、`WERKS`、`MATNR` 汇总；但必须先在目标 S/4 系统以 SE11/ST05 验证 MSEG/MATDOC 的实际数据源、字段可用性和访问路径，不能仅依据通用资料假定性能。

**Agent 的正确行为**：在料号、工厂和日期已明确时，查询当前库存快照与指定过账日收发，并在一张报告中分别呈现。报告必须说明“库存为查询时点快照、收发按过账日期统计”，不可将二者直接表述为严格的期初/期末勾稽关系。

> 反例（要避免的）：模型只查了 MARD 就回答"库存 123 PC"——漏掉当天收发，用户觉得"这不是我要的"。

### 2.3 新增机制：领域知识卡（借鉴 Dify）

**问题**：让模型自由选表，它可能猜出不存在的表、或漏掉关键表（批次/销售订单库存）。
**方案**：按业务域预制“知识卡”，作为 system prompt 的受控片段。知识卡描述业务口径、可调用工具和何时调用；**不**授权模型生成任意表名、字段或 WHERE 条件。

库存域知识卡示例（存 Z 表或配置文本，按域关键词路由）：

```
[DOMAIN] 库存 INVENTORY
触发词: 库存/在库/料号余量/收发/盘点
可调用工具:
- resolve_material：按精确料号或受限前缀查找候选料号（最多 10 条）
- get_stock_snapshot：返回指定工厂、料号的库位库存和库存类型汇总
- get_daily_movement：返回指定过账日期的收发汇总（按移动类型、借贷标识、单位）
- get_batch_stock：仅在物料有批次管理或用户明确追问时调用
口径提示: LABST 仅为非限制库存，报告需按库存类型拆分；收发方向看 SHKZG(S借/H贷)
常见组合: 当前库存快照 + 指定过账日收发；批次明细按需补充。具体表、字段、静态 SQL/CDS 由 ABAP 工具实现维护。
```

**落地**：`ZCL_AI_DOMAIN_CARDS=>GET_CARD( domain )` 返回库存卡；Agent 在识别库存域后注入。卡由业务/ABAP 人员维护，模型只消费。后续工单、采购等领域均按“领域卡 + 专用工具”扩展，不以新增任意查表权限为代价。

### 2.4 端到端工具调用序列（预期走查）

```
用户: 分析一下 0001 工厂当天 A 料号的库存数据

轮1 意图+主档校验
  模型: {"action":"tool","tool":"resolve_material",
         "args":{"material_hint":"A","plant":"0001"}}
  guard: 仅允许精确料号或受限前缀检索，返回最多 10 个候选；候选不唯一时要求用户确认

轮2 当前库存
  模型: {"action":"tool","tool":"get_stock_snapshot",
         "args":{"plant":"0001","material":"A001"}}
  guard: 校验工厂访问范围、料号格式与工具级行数上限；返回库存类型汇总及有限库位明细

轮3 当天收发
  模型: {"action":"tool","tool":"get_daily_movement",
         "args":{"plant":"0001","material":"A001","posting_date":"20260921"}}
  guard: 日期由 ABAP 解析和格式化；查询在工具内部做静态汇总，返回有限的移动类型/方向/单位汇总

轮4 反思 → final
  模型自查清单（§2.5）通过 → 输出报告（§2.6）
```

**资源账（待实测）**：最多 4 次工具、最多 4 次 LLM 调用。首期设置总耗时预算 45–60 秒、最大轮数 4、单工具结果 200 行/16KB 以内、回填模型前再压缩为汇总。Flash 的具体延迟、上下文和 JSON 服从性须以企业网关的实测 P95 为准；不能仅据模型标称上下文判断同步请求“无压力”。

### 2.5 反思清单（第 3→4 步的结构化，防止"假成功"）

模型在 final 前必须逐项自答（写进 agent system prompt 的收尾规则）：

| 检查项 | 不通过时的行为 |
|---|---|
| 料号主档存在？ | 0 条 → final 反问，不带数字编答案 |
| MARD 查到行？ | 0 行且主档存在 → 试 MCHB（批次管理料号库存不在 MARD）；仍无 → 报告"该料号在 0001 无库存记录"（这是**有效结论**） |
| MSEG 当天 0 行？ | → 报告"当天无收发"，**不算失败**（空是业务事实，不是错误）——你的步骤 3 里"结果是否符合"最容易被这点坑 |
| 数量口径齐了吗？ | 只报了 LABST → 补齐质检/退货等库存类型再收口 |
| 单位一致？ | MEINS 多值 → 报告分单位呈现，禁止跨单位加总 |
| 数字可溯源？ | 报告里每个数字标注来自哪张表哪个条件 |

### 2.6 报告输出模板（final 环节）

```
【A001 在 0001 工厂的库存分析】(单位: PC)
◆ 当前库存合计 120（非限制 100 / 质检 20 / 退货 0）
  - 库位 1001: 80 ｜ 库位 1002: 40
◆ 当天收发（09-21）: 收 50（101 入库），发 30（261 生产领料），净增 20
◆ 提示: 该料号有批次管理（如需批次明细可继续深挖 MCHB）
[查看过程: 3 条查询 ▾]
```

## 三、模型接入影响评估：候选 Flash 模型 / 256K 上下文

| 影响面 | 之前假设 | 现在 | 结论 |
|---|---|---|---|
| 同步超时风险 | 单轮调用可达 300 秒 | 候选 Flash 模型预期更低延迟 | 只能通过网关实测 P50/P95 确认；首期保留总预算和轮次上限 |
| 上下文预算 | 当前无 Agent 上下文管理 | 候选模型宣称 256K | 保留结果裁剪纪律；工具结果先汇总，不能因窗口变大而传入明细垃圾 |
| JSON 协议服从性 | 当前客户端仅处理文本 content | 需验证候选模型及企业网关是否稳定支持 | P0 必做 20 条用例；非法 JSON 必须由 ABAP 拒绝或一次修复重试 |
| 多模型路由 | 现网已有模型配置和 AUTO 选择 | 可为 Agent 单列 `AGENT_FAST` 配置 | 首期优先同一模型完成循环和报告；两段模型路由放 P2，避免增加故障面 |

## 四、首期目标、范围与非目标

### 4.1 首期目标

在现有 UI5 → OData → ABAP → 企业模型网关链路内，为库存场景提供受控的多步分析能力。用户输入“分析 0001 工厂当天 A001 的库存”后，系统能识别必要槽位、调用受限工具、输出可追溯报告，并保留过程审计。

### 4.2 首期范围（P0/P1）

| 类别 | 纳入范围 |
|---|---|
| 业务域 | 库存：物料识别、当前库存快照、指定过账日收发、按需批次库存 |
| 操作类型 | 仅读；不创建、修改、过账、审批任何 SAP 业务数据 |
| Agent 能力 | 最大 4 轮的受限工具循环；严格 JSON 协议；最终结构化报告 |
| 模型 | 使用当前 OpenAI 兼容客户端；模型及网关能力通过 P0 实测后确定 |
| 前端 | 复用发送、会话和消息展示；P2 增加“查看分析过程”折叠区 |
| 数据留存 | 会话正文沿用现有表；新增 Agent 运行与步骤审计，保存参数摘要、结果摘要、耗时、状态和模型 ID |

### 4.3 明确不纳入首期

- 任意表、任意字段、任意 WHERE/GROUP BY 的通用查询工具；
- 写入、过账、删除、主数据维护类工具，以及相应的人工审批流程；
- 跨会话长期记忆、跨 SAP 系统编排、异步后台任务、Dify/n8n；
- 多模型分工（循环模型与报告模型分离）；
- 将原始大批量明细直接传递给模型。

## 五、目标架构与调用边界

```text
UI5 App.controller / ChatService
  → OData Function Import: AnalyzeAgent（或 AnalyzeCode 内部按意图路由）
  → ZCL_AI_AGENT_SERVICE
      ├─ ZCL_AI_DOMAIN_CARDS      领域卡和报告规则
      ├─ ZCL_AI_TOOL_REGISTRY     工具白名单、Schema、确认标志
      ├─ ZCL_AI_INVENTORY_TOOLS   固定库存查询与汇总
      ├─ ZCL_AI_AGENT_GUARD       参数、权限、限流、结果裁剪
      ├─ ZCL_AI_LLM_CLIENT        既有模型 HTTP 客户端
      └─ ZAI_AGENT_RUN / STEP     过程审计
```

模型的唯一输出协议如下；任何不符合 Schema 的文本均不得执行：

```json
{"action":"tool","tool":"get_stock_snapshot","args":{"plant":"0001","material":"A001"}}
```

或：

```json
{"action":"final","answer":"..."}
```

ABAP 负责解析 JSON、校验 action/tool/参数类型、确认用户与工厂权限、执行固定工具、裁剪结果并决定是否允许进入下一轮。模型不能自行拼接 SQL、URL、OData Action、表名或字段名。

## 六、数据权限、审计与安全前置条件

| 控制点 | 首期要求 |
|---|---|
| 工具白名单 | 仅注册本文定义的库存只读工具；工具 ID 不可由模型扩展 |
| 参数校验 | 工厂、料号、日期均采用强类型 Schema；日期由 ABAP 解析，候选料号最多 10 条 |
| 数据权限 | 工具内显式校验用户的库存/工厂访问范围，并且已有会话必须校验 `created_by = sy-uname`。现有 ADMIN/USER 只用于应用管理，不能替代业务数据授权 |
| 表访问 | ABAP 工具中加入明确 `AUTHORITY-CHECK` 或项目确认的业务授权机制；不得依赖 UI 隐藏或动态 SQL 的偶然失败 |
| 数据最小化 | 工具输出以汇总为主，明细有行数和字符上限；仅将回答所需数据发给模型网关 |
| Prompt 注入 | 工具结果以 `tool_result` 边界包装；结果中的文本不得改变系统规则或触发其他工具 |
| 审计 | 每次运行记录用户、会话、轮次、模型、工具、脱敏参数摘要、结果摘要、耗时、成功/拒绝/超时状态 |
| 超时与限流 | 最大 4 轮、总预算 45–60 秒、单模型/单工具超时和单用户并发限制；超时返回可解释结果 |

> 上线前必须与 Basis/安全及业务负责人确认：企业模型网关的数据驻留、日志、缓存和运维访问范围均符合库存数据的保密要求。

## 七、开发计划

### P0：技术验证与数据口径确认（预计 2–3 个工作日）

| 编号 | 工作项 | 交付物 | 完成标准 |
|---|---|---|---|
| P0-1 | 确认企业网关中的候选模型、实际上下文、限流和超时 | 模型连通与性能记录 | 20 条 JSON 用例可重复执行，记录合法率及 P50/P95 |
| P0-2 | 确认库存数据源 | SE11/ST05/SE16 核对记录 | 明确目标系统使用的数据源、字段、索引/访问路径；验证 MSEG/MATDOC 取数方式 |
| P0-3 | 与业务确认口径 | 库存报告口径清单 | 确认库存类型、单位、移动类型、当天定义、空结果语义与样例基准答案 |
| P0-4 | 安全方案评审 | 工具权限矩阵 | 明确工厂权限来源、`AUTHORITY-CHECK` 方案、审计保留期、网关数据边界 |

### P1：后端 Agent 最小闭环（预计 5–7 个工作日）

| 编号 | 工作项 | 主要改动 | 完成标准 |
|---|---|---|---|
| P1-1 | Agent 数据结构与 OData 契约 | 新增 `AnalyzeAgent`、`AgentResult`、Trace 字段；更新 DPC_EXT | 单次调用可返回最终回答、状态、模型和 Trace 摘要 |
| P1-2 | Agent 循环与 JSON guard | 新建 `ZCL_AI_AGENT_SERVICE`；最大轮数、格式修复一次、总超时 | 非法 JSON、未知工具、参数非法均被拒绝且不执行工具 |
| P1-3 | 工具注册与库存工具 | `ZCL_AI_TOOL_REGISTRY`、`ZCL_AI_INVENTORY_TOOLS` | 三个核心工具只接受强类型参数，并返回受限结构化结果 |
| P1-4 | 领域卡与报告模板 | `ZCL_AI_DOMAIN_CARDS`；库存卡、反思清单 | 覆盖当前库存、当日收发、空结果、单位不一致等规则 |
| P1-5 | 权限和审计 | 工具级授权、`ZAI_AGENT_RUN`/`ZAI_AGENT_STEP` | 可追查谁在何时调用了什么工具、是否被拒绝、使用了何模型 |
| P1-6 | 异常与降级 | 模型/工具超时、空数据、候选不唯一、网关异常 | 不产生编造数字；返回明确下一步或部分结论 |

### P2：前端过程可视化与回归（预计 2–3 个工作日）

| 编号 | 工作项 | 主要改动 | 完成标准 |
|---|---|---|---|
| P2-1 | Agent 入口与状态 | `ChatService`、`App.controller` | Agent 请求与普通聊天清晰区分，保留既有普通聊天路径 |
| P2-2 | 查看过程 | 消息卡片增加折叠 Trace 区 | 仅展示工具名称、条件摘要、行数、耗时和状态；不泄露超范围明细 |
| P2-3 | 前端异常体验 | 超时、权限拒绝、候选选择提示 | 用户得到可执行提示，不显示 ABAP/网关原始堆栈 |
| P2-4 | 构建与部署回归 | UI5 构建、BSP 增量包、网关验证 | 既有登录、聊天、会话、模型管理无回归 |

### P3：试运行与扩展评审（预计 3–5 个工作日）

- 选择受控用户和受控工厂试运行，按审计日志检查误调用、超时和结果偏差；
- 根据业务反馈完善库存域卡，而不是放宽通用查询权限；
- 评审是否引入批次、销售订单库存、价值库存，以及是否需要两段模型路由；
- 仅在跨系统或长流程需求明确后，重新评估 n8n/Dify 或异步后台执行。

## 八、验收计划

| 编号 | 场景 | 判定标准 |
|---|---|---|
| V1 | 结构化协议验证（20 条） | 合法 JSON ≥90%；其余请求安全拒绝或一次修复后成功；无越权工具执行 |
| V2 | 料号、工厂、日期齐全 | 3–4 轮内得到库存快照和指定过账日收发；数字与 SE16/业务报表基准一致 |
| V3 | 料号前缀多候选 | 返回最多 10 个候选并要求用户确认，不擅自选择物料 |
| V4 | 料号不存在 | 明确说明未找到，不能虚构库存或收发 |
| V5 | 当前无库存 / 当天无收发 | 作为有效业务结论分别呈现，不报系统错误 |
| V6 | 多单位或多库存类型 | 禁止跨单位直接加总；库存类型完整展示或明确说明范围 |
| V7 | 无工厂权限 | 工具执行前拒绝，审计记录拒绝原因，不向模型传递数据 |
| V8 | 模型、工具超时或非法 JSON | 在预算内结束，回复可理解的降级说明；会话和既有聊天功能不受影响 |

## 九、需业务与技术负责人确认的事项

1. “当天”是否固定为过账日期 `BUDAT_MKPF = sy-datum`，还是需要支持用户指定日期、工厂日历或时区。
2. 库存报告首期是否包含非限制、质检、冻结/退货、在途等全部库存类型；每种类型的业务定义。
3. 工厂访问权限的权威来源：现有 SAP 授权对象、Z 权限表，或二者组合。
4. MSEG/MATDOC 的目标系统验证结果，以及大数据量下允许的查询时长和结果粒度。
5. 企业模型网关是否允许库存数量、移动类型和库位摘要进入模型上下文，以及日志保留策略。
6. 是否接受首期“只读、无审批、无后台任务”的边界。

## 十、结论

该方案可以启动，但首期的正确形态不是“AI 驱动的任意查表”，而是“AI 选择经过业务固化、权限受控的库存分析工具”。现有项目已具备 UI、会话、OData、模型配置和 ABAP 编排基础；需要新增的是 Agent 循环、严格协议、专用工具、业务授权、审计和 Trace 展示。完成 P0 验证后再进入 P1，可把主要风险提前锁定在数据口径、权限和性能，而不是上线后处理错误查询与数据泄露。
