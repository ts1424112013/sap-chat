## 1. 结论

用户想在一个会话里做到：先跑 ZDPSD021，然后说"根据上面的结果，查一下这些料号的 COO"，灵犀接着取数，并把两份数据按料号对起来分析。

方案分三块，可以分批上线：

| 块 | 解决什么 | 做法 | 工作量 |
|---|---|---|---|
| **#00 修 bug** | 「自动」场景里，"这些料号……查表 X"只拿到库存工具，灵犀回答"只能查库存" | 选工具时，路由已认出"查表"就以路由为准，不再只按关键词猜 | 0.5 天 |
| **#02 报表内关联查表** | 报表执行会话里查表被"换场景"提示挡住 | 新只读工具 `lookup_by_result`：后端从当前结果里取出料号清单，到指定表批量查，把查到的字段接回结果，存成一份新结果 | 约 3 天 |
| **#01 报表接力** | 把上一份结果的料号自动带进下一张报表 | 新只读工具 `prefill_report`：后端把料号清单填进下一张报表的参数卡（**不直接执行**，仍由用户提交）；跑完后一键用「组合分析」按料号关联 | 约 4 天 |
| 小改 | TCode 打错只回"未登记" | 未登记时列出相近的已登记报表（权限内） | 0.5 天 |

两条原则贯穿全文：

1. **料号清单不经过模型**。1021 个料号如果让模型抄进 SQL 或参数，以现在的输出速度（约 37 字/秒）要好几分钟，还容易抄错或被截断（10.28 #02 就是长 SQL 被截断）。模型只说"用哪一列、筛什么、填到哪"，**清单由后端从存储行里取**。
2. **不新增权限模型**。查表沿用数据分析现有的检查（敏感表黑名单 + 表存在 + SAP 表权限 `VIEW_AUTHORITY_CHECK`），并要求用户本身开通了「数据分析」场景；报表接力沿用报表登记、报表授权和参数卡确认。

## 3. #00 「自动」场景选错工具（bug）

### 3.1 现象

聊天导出 16:41："这些料号的COO分别是什么，可以去查表ZIDPMMTLK 中的TLK58" → 灵犀回答"当前可用的工具仅支持库存查询（快照、收发、批次）"。

### 3.2 原因（按代码推断，需要用审计里的工具清单确认）

- 那次会话应该是「自动」场景。路由按"查表 ZIDPMMTLK"认成了 DATA / TABLE。
- 但选工具用的是 `match_domain`，问题里有"料号"，先命中了库存域，于是只给了库存 4 个工具。
- 两边不一致，模型拿着库存工具回答了查表问题。

### 3.3 改法

在 `analyze_agent` 拿到路由结果之后加一步：「自动」场景下，路由明确认出对象时，工具域跟着路由走。

- 路由是 `object_kind = TABLE` → 用 DATA 域（数据分析没开放时仍按 V15.12 处理）。
- 路由是 `MATERIAL` → 用库存域。
- 其他情况保持现状。

只改 `ZCL_AI_AGENT_SERVICE`，一处小分支。

## 4. #02 报表执行里关联查表

### 4.1 用户看到什么

```
用户：这些料号的 COO 是什么？去表 ZIDPMMTLK 查 TLK58
灵犀：（调用 describe_table 看表结构，确认料号字段）
      （调用 lookup_by_result：用结果里的「鴻海料號」去 ZIDPMMTLK 按料号查 TLK58）
      已在 ZIDPMMTLK 查到 1021 个料号中的 998 个，23 个没有记录。
      COO 分布：CN 612、VN 301、……   [结果卡：ZDPSD021 + COO，1727 行]
用户：只看 1AM 开头的，按 COO 汇总可用库存
灵犀：（对新结果用 query_result）……
```

### 4.2 新工具 `lookup_by_result`（只读）

参数（模型给的都只是候选，后端逐项核对）：

| 参数 | 说明 |
|---|---|
| `table` | 要查的表，例如 `ZIDPMMTLK` |
| `key_field` | 表里的关联字段，例如料号字段 |
| `source_column` | 当前结果里的关联列，例如「鴻海料號」 |
| `fields` | 要带回的字段，最多 10 个，例如 `["TLK58"]` |
| `filter` | 可选：先筛选结果行（格式同 `query_result` 的筛选），例如"鴻海料號以 1AM 开头" |
| `where` | 可选：表上的附加条件（例如工厂），走 SQL_GUARD 的同一套检查 |

后端步骤：

1. **核对结果**：结果号由后端给（同 `query_result`，只能是本轮定位到的那一份），用 `load_result` 读全部存储行。
2. **取关联值**：按 `filter` 筛选行，取 `source_column` 去重后的值；值的格式统一沿用组合分析的 `norm_key`（处理前导零、大小写、空格）。
3. **核对表和字段**：敏感表黑名单、表存在、`VIEW_AUTHORITY_CHECK`；`key_field`、`fields` 必须在 DD03L 里存在。
4. **分批查表**：每批 500 个值，用 range 表加动态 SELECT（只读，不拼值进 SQL 文本），合计最多 `LOOKUP_MAX_KEYS`（默认 5000）个值。
5. **接回结果**：按关联值左关联，原结果每行加上带回的字段（列名写成「TLK58·ZIDPMMTLK」）。同一关联值在表里有多行时，按组合分析的规则处理（文字取第一个），并在说明里写明"有 N 个料号在表里有多条记录"。
6. **存成新结果**：复用 `ZAI_COMBO_RUN` / `ZAI_COMBO_DATA`，模式记为 `LOOKUP`，在**当前会话**登记成 `COMBO_RESULT`。前端照常出结果卡，后续追问时 `query_result` 查的就是这份新结果。
7. **给模型的返回**：命中数、未命中数、新增字段的取值分布（前 20），以及新结果号。不返回明细。

### 4.3 什么时候放开

报表执行场景里，路由认出"查表"时，下面四条都满足才放行（不再提示换场景），否则维持现在的提示：

1. 开关 `RPT_TABLE_LOOKUP = X`（默认关）；
2. 本会话有可用的报表结果；
3. 用户开通了「数据分析」场景（`ZCL_AI_ACCESS=>scene_ok( 'DATA' )`）——**没开通数据分析的人，在报表场景里也查不了表**；
4. 工具已注册。

放行时，本轮工具 = `query_result` + `describe_table` + `lookup_by_result`。**不给 `run_sql`**：报表场景只做"拿结果去关联"，不做随意写 SQL。

### 4.4 改动对象

| 对象 | 改动 |
|---|---|
| `ZCL_AI_INTENT_ROUTER` | `apply_scene` 的 REPORT 分支：满足 4.3 时把 TABLE 意图改成"结果追问 + 关联查表"标记（新字段 `lookup_ok`） |
| `ZCL_AI_AGENT_SERVICE` | 看到 `lookup_ok` 时加两个工具；执行分发加 `lookup_by_result` |
| `ZCL_AI_TOOL_REGISTRY` | 注册 `lookup_by_result`（不进任何模块白名单，同 `query_result`，只由 AGENT_SERVICE 按条件加） |
| `ZCL_AI_AGENT_GUARD` | 嵌套参数解析（同 `query_result` 的做法） |
| 新类 `ZCL_AI_RESULT_LOOKUP` | 4.2 的 1–7 步；表检查复用 `ZCL_AI_SQL_GUARD` 的公开方法 |
| `ZCL_AI_COMBO_SERVICE` | 新公开方法：把一份"行 + 列"存成组合结果并登记到指定会话（现在 `create` 只接收前端的组合说明） |
| 前端 | 结果卡认 `LOOKUP` 模式的标题和来源说明；其他沿用组合结果卡 |
| ZAI_CHAT_CFG | `RPT_TABLE_LOOKUP`（默认空 = 关）、`LOOKUP_MAX_KEYS`（5000） |

不加 SE11 表，也不加 SEGW。

## 5. #01 报表接力（上一份结果 → 下一张报表参数）

### 5.1 用户看到什么

```
用户：依据以上的结果，去 ZDPMM159 查这些料号的 COO（只要 1AM 开头的）
灵犀：（query_result 确认 1AM 开头 1021 个料号）
      （prefill_report：ZDPMM159，料號 ← 结果列「鴻海料號」，筛选 1AM 开头）
      [参数卡：TLK Display]
        工廠  [1001]              ← 从 ZDPSD021 的运行参数带入（同名参数）
        料號  已带入 1021 个值（来自运行 0050569C）  [展开] [清空]
        ……其余参数
      请确认后提交。
用户：（提交）→ 运行完成 → 结果卡多一个按钮「和运行 0050569C 关联」
用户：（点击）→ 按料号关联的组合结果 → 照常追问分析
```

### 5.2 怎么认出"接力"

报表执行场景下，同时满足以下三条，认成新意图 `RUN_FROM_RESULT`：

- 问题里点名了一个 TCode；
- 问题里有指代上一份结果的说法：沿用现有指代正则（这些 / 以上 / 上面 / 刚才……的结果、数据），再加上"这些料号""塞进去""带进去""依据……结果"；
- 本会话有可用结果。

不满足时照旧：出报表卡，或者回复未登记。

### 5.3 新工具 `prefill_report`（只读，不执行）

接力这一轮走模型（工具 = `query_result` + `prefill_report`），因为"这些料号""只要 1AM 开头"需要模型理解。

| 参数 | 说明 |
|---|---|
| `tcode` | 下一张报表 |
| `target_param` | 要填的参数（必须是多值或范围参数） |
| `source_column` | 当前结果里取值的列 |
| `filter` | 可选，格式同 `query_result` |

后端步骤：

1. 核对报表：已登记、启用、用户有报表授权（复用 `build_report_intro` 的同一套检查）。
2. 核对参数：`target_param` 必须存在，并且是多值 / 范围参数。
3. 取值：读结果行 → 按 `filter` 筛选 → 取 `source_column` 去重；最多 `RELAY_MAX_VALUES`（默认 2000，按开放点 1 的实测结果再调）。超过上限时**不截断**，而是报错，请模型加筛选条件。
4. 带入同名参数：上一份运行参数里有同名、或同一 DDIC 字段的参数（例如工廠），作为默认值带入，参数卡上标注"来自上一次运行"。
5. 生成参数卡：沿用现有的 `pending_params_json`，多值参数带上 `prefilled_from`（来源结果号、列名、值个数）。任务状态置 WAITING_INPUT，**执行仍走用户提交 → StartReportRun**，"聊天里不直接提交作业"这条规则不变。
6. 记下接力关系：运行发起时，把来源结果号写进本次运行（任务的 pending 里已有，提交时带上），供 5.4 使用。

### 5.4 跑完以后关联

- 结果卡上出现按钮「和运行 XXXX 关联」（只有接力运行才有）。
- 点击后调用组合分析，模式为关联：
  - 左边是来源结果，关联列为 `source_column`；
  - 右边是新结果，关联列**自动选择**：在新结果的各列里，挑与带入值重合最多的一列（这样不需要维护"参数 → 结果列"的对应关系）；重合率低于 50% 时让用户在面板里手选。
- 组合结果**登记在当前会话**（现在是新开组合会话，见决策 D3），然后直接进入追问。

## 6. 两条路怎么选

| | #02 报表内查表 | #01 报表接力 |
|---|---|---|
| 第二步数据来源 | 直接读表 | 跑登记过的报表 |
| 速度 | 快（一次查询，没有后台作业） | 慢（要提交参数卡、等作业跑完） |
| 业务口径 | 只有表里的原始字段 | 报表里的业务逻辑都在 |
| 前提 | 用户开通了数据分析，并有 SAP 表权限 | 报表已登记，用户有报表授权 |
| 留痕 | 工具调用审计 | 运行记录 + 参数卡确认 |

建议**先上 #00 和 #02**：COO 这类"按料号补一个字段"的需求，查表最直接，改动也小。然后上 #01，覆盖"第二步必须走报表口径"的情况。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 关联值格式不一致（前导零、大小写） | 统一用组合分析的 `norm_key`；未命中数如实告诉用户 |
| 表里同一料号有多条记录（例如按工厂区分） | `where` 参数让模型加工厂条件；说明里写明多条记录的数量 |
| 带入值太多，参数卡卡顿或作业超时 | 有上限，超过就报错让模型加筛选；参数卡收起显示 |
| 报表场景查表变成绕过权限的旁路 | 四条放行条件（§4.3）+ 原有表权限检查；不给 `run_sql` |
| 模型选错列或选错参数 | 参数卡上显示来源列和值个数，用户提交前能看到、能清空 |

### 12.2 跟 V1.0 设计不同的地方

1. **查回的数据不另存成新结果（D2 改了）**。V1.0 打算把接好的数据存进组合表、在当前会话登记成新结果。实现时改成：工具把"接回 + 筛选 / 分组 / 排序"一次做完，只返回一张小表；用户追问时模型再调一次（读表按关联值分批，几千个值也很快）。
   - 好处：不用改 `ZCL_AI_COMBO_SERVICE`、不用改前端、不用加配置表；结果仍显示在回答下方的表格里，能导出。
   - 代价：没有"一份完整的接好的数据"可以单独打开或再组合。真需要时再按 V1.0 的做法补。
2. **`ZCL_AI_AGENT_GUARD` 不用改**。嵌套 args 本来就原样透传（`query_result` 也是这样）。
3. **#00 改法**同 §3.3；放在「自动」场景的能力检查之后，没开数据分析时仍按原来的提示处理。
4. **放行条件多了一条**：除 §4.3 的四条外，还要求 `SQL_ANALYSIS_ENABLED` 打开、用户允许 SQL（`ZAI_CHAT_USER-SQL_ALLOWED`，字段存在时）。这和数据分析里查表的门槛一致。
5. **表上的附加条件**参数叫 `conditions`（V1.0 写的是 `where`），只认结构化的 字段 / 操作 / 值，不接受 SQL 文本。
