# 灵犀 Agent 上下文与输出管理方案

版本：V1.0；编写日期：2026-10-28（Asia/Shanghai）。

状态：供讨论的设计。本次只核查本地源码、编写方案，没有修改业务代码，也没有连接 SAP 验证。

与《01-灵犀Agent工作流接入方案》配套：01 管“任务做完没有”，本方案管“给模型看什么、让模型写多长、多久内写完”。两份方案共用 01 §4.2 的工具结果记录。

## 1. 结论

1. **256k 上下文窗口够用，不是瓶颈。** 现在单次运行最坏约 10 万字，折算后不到窗口的四分之一。
2. **真正的瓶颈是输出速度和 180 秒同步预算。** 按 10.28 #01 推算，模型每秒约输出 37 个 token，写满 4096 token 约需 110 秒。
3. 因此工作重点按顺序是：
   - **先量**：记下每次模型调用的实际用量；
   - **管输出**：控制回答长度，并给最后写回答留出时间；
   - **修裁剪**：数据分析结果目前按字符硬切，会丢掉总行数和截断标记；
   - **适度放宽上下文**：追问时带的历史太少，可以放宽，但不必放到很大。
4. 所有阈值做成配置项，用实测数据调整；能由程序决定的，例如裁剪、折叠、收尾时机、任务状态，都不交给模型。

## 2. 模型与运行前提

| 项目 | 当前情况 | 来源 |
|---|---|---|
| 模型 | DeepSeek V4 Flash（公司内部部署） | 用户确认，10-28 |
| 上下文窗口 | 256k token（部署设定；模型本身支持更长） | 用户确认 |
| 思考模式 | 关闭 | 用户确认 |
| 单次输出上限 | 网关上限不清楚；`ZAI_MODEL_CFG-MAX_TOKENS` 未维护时代码按 4096 处理 | 待网关确认；代码见 `ZCL_AI_LLM_CLIENT` 约 187 行 |
| 前缀缓存 | 可能没开 | 待确认 |
| 输出速度 | 约 37 token/秒 | **估算**：10.28 #01 第 5 轮 109.7 秒写满 4096 token；仅一个数据点，待第 0 步实测 |
| 总预算 | `AGENT_BUDGET_SEC` 默认 180 秒，上限 180 秒；每次调用模型的超时 = 剩余预算 | 代码；ICM `PROCTIMEOUT` 需 ≥ 200 秒 |
| 本地 Mock | 用 GLM，思考关闭或低档 | 本地速度与长度表现不能代表公司模型 |

按 37 token/秒估算：4096 token ≈ 110 秒，6000 token ≈ 160 秒，8192 token ≈ 220 秒。**8192 已超过 180 秒总预算**，所以 10.28 处理结果里“`MAX_TOKENS` 建议改成 8192”需要按本方案 §5.2 修正。

## 3. 现状

以下描述的是当前仓库代码（main 9f67875），不能据此认定已部署到 SAP。按记录，SAP 上运行的是 676cea6，不含 9f67875。

### 3.1 每次调用模型送了什么

开始循环前按顺序拼装：领域卡 → 技能卡 → 输出协议 → 任务上下文包（任务层开启时）或最近对话 → 报表结果明细（引用报表时）→ 用户问题。循环中每一轮再追加两条：模型原样输出的 JSON，以及包装后的工具结果。前面的内容不会删减，每轮全部重发。

| 内容 | 当前上限 | 代码位置 |
|---|---|---|
| 最近对话（未开任务层） | 最近 2 轮，每条 500 字 | `ZCL_AI_AGENT_SERVICE` 常量 `gc_ctx_pairs` / `gc_ctx_chars`，`get_recent_ctx` |
| 任务内消息 | 最近 2 轮，每条 500 字 | `ZCL_AI_TASK_SERVICE=>build_context` 默认参数 |
| 任务摘要 | 回答的前 120 字 | `ZCL_AI_AGENT_SERVICE` 约 1639 行 |
| 任务结果引用 | 只有名称、行数、状态，不存明细 | `register_artifact( iv_summary_json = '' )` |
| 报表结果明细 | 8000 字 | `gc_art_chars` |
| 单个工具结果 | 8000 字，按字符截断 | `ZCL_AI_AGENT_GUARD` `gc_max_result_chars`、`trim_result` |
| 源码工具结果 | 每页 400 行 / 18000 字；回填 24000 字 | `gc_src_page` / `gc_src_chars` / `gc_src_feed` |
| SQL 明细回填 | 200 行 | `ZCL_AI_SQL_EXECUTOR` `gc_llm_rows` |
| 数据分析结果回填 | 先按整行裁到 12 万字，再按 8000 字硬切 | `ZCL_AI_DATA_ANALYSIS_SERVICE` `gc_model_chars` + `trim_result` |

### 3.2 存在的问题

**问题 1：数据分析结果被拦腰截断（与窗口大小无关，需优先修）。**
- `build_datasets_json` 的字段顺序是 `name, status, error, columns, rows, total_rows, truncated, …`，明细 `rows` 排在总行数和截断标记前面。
- 它自带的按行裁剪预算是 12 万字，回填时实际不起作用；随后 `trim_result` 在第 8000 字直接切断。
- 结果是：行数一多，模型只看到半截明细和一句“已按 8000 字符上限截断”，看不到总行数，也看不到截断标记，可能把能看到的几行加起来当全量。
- `run_sql` 同样受影响：说明文字“共 N 行，已仅回填前 200 行”排在前面能看到，但 200 行多列明细超过 8000 字后同样被硬切，模型以为拿到了 200 行，实际只看到其中一部分。

**问题 2：追问时能看到的上一轮信息太少。** 只带 2 轮对话、每条 500 字，任务摘要只有回答前 120 字。用户说“按工厂再拆一下”时，上一轮的物料、日期、关键数字可能已经被截掉。

**问题 3：单次运行内的内容只增不减。** 没有前缀缓存时，每轮都要重新读一遍全部输入。目前前几轮每轮 1–2 秒，压力不大；但读源码场景会明显变大，10.28 #01 那次读到第 4 页时，上下文里已经堆了 1600 行源码。

**问题 4：没有给最后写回答留时间。**
- 每次调用模型的超时就是剩余预算（约 973–979 行）。工具步骤用掉 100 秒的话，最后写回答只剩 80 秒，约 3000 token。
- 数据分析在回答之后还要再调一次模型生成结构化分析（约 1475 行起），也从同一预算里扣，最少只给 5 秒。

**问题 5：回答长度只有代码分析有要求。** 9f67875 在代码分析领域卡里加了“1500 字以内、每段代码不超过 15 行”（尚未上 SAP），数据分析、库存、报表结果分析都没有长度要求。

**问题 6：看不到实际用量。** `ZCL_AI_LLM_CLIENT` 只解析 `choices` 里的正文和结束原因，没有读返回中的 `usage`；审计表只记耗时，不记 token 数。上面的输出速度只能靠一次记录推算。

## 4. 设计原则

1. **上下文是注意力，不只是空间。** 窗口放得下，不等于模型抓得住；只放当前需要的，大数据留在后端，给模型引用编号和摘要。
2. **程序决定，模型执行。** 裁剪、折叠、收尾时机、任务状态都由后端按规则处理。不让模型自己写摘要当记忆：摘要容易丢数字，也无法核对。
3. **先量后调。** 新阈值全部放进 `ZAI_CHAT_CFG`，未维护时按默认值运行；默认值与现行为一致或略宽，按审计实测再调整。配置键 `CFGKEY` 为 CHAR 20，键名不超过 20 个字符。
4. **与 01 共用结果记录。** 工具结果记录同时用于完成验收（01 §4.4）、运行内折叠（本方案 §5.3）和跨轮任务状态（本方案 §5.4）。

## 5. 方案

### 5.1 第 0 步：记录每次模型调用的实际用量

1. `ZCL_AI_LLM_CLIENT=>chat` 增加可选导出参数（例如 `ev_usage`），解析返回中的：
   - 输入 token、输出 token；
   - 缓存命中 token：不同网关字段名不同，DeepSeek 风格为 `prompt_cache_hit_tokens`，OpenAI 风格为 `prompt_tokens_details.cached_tokens`。取得到就记，取不到留空，不报错。
   - 旧调用方不传该参数时行为不变。
2. Agent 侧同时统计本次发送的消息总字数，网关不返回 `usage` 时也有参考。
3. 每次模型调用在 `ZAI_AGENT_STEP` 写一行：`TOOL_ID = 'LLM_CALL'`，`SUMMARY` 写“第几轮 / 输入 token / 输出 token / 缓存命中 / 结束原因 / 发送字数”（200 字以内），`ELAPSED_MS` 写耗时。
   - 不新增表字段，不改 SE11、SEGW。
   - **只写审计，不进返回前端的 TraceJson 和进度表**，思考卡里不显示。实现上单独收集，`save_audit` 时合并写入。
4. 用途：确认实际输出速度（输出 token ÷ 耗时）、每轮输入有多大、前缀缓存是否命中。现场跑一周左右，再用数据确定 §5.2、§5.3 的数值。

### 5.2 输出与时间预算

1. **`MAX_TOKENS` 先不调大。** 保持 4096，最多到 6000 左右，不采用 10.28 处理结果里的 8192。拿到实测速度后按下式复核：`MAX_TOKENS ÷ 实测速度` 应小于收尾预留时间（见第 3 条）。
2. **各场景写明回答长度（写进领域卡）。** 以下为建议起点，按实测调整：

| 场景 | 建议 |
|---|---|
| 代码分析 | 维持 9f67875 的 1500 字以内、每段代码不超过 15 行 |
| 数据分析 | 结论和关键数字，800 字以内；明细看结果表，回答里不重复列表 |
| 库存 | 600 字以内；数量以结果卡展示为准 |
| 报表结果分析 | 1000 字以内 |

   用户明确要求详细说明时可以放宽，但建议分几次追问展开，而不是一次写满。

3. **给收尾留出时间。** 新增配置 `AGENT_FINAL_RSV_SEC`（19 位），建议值 90 秒。
   - 每轮开始前，如果剩余预算小于预留时间，本轮直接按最后一轮处理：后端提示收尾，并拒绝执行新工具（与 01 §4.3“最后一轮由后端禁止执行新工具”合用同一处判断）。
   - 预留时间应覆盖“写最终回答 + 数据分析结构化调用”两次模型调用；数值按 `MAX_TOKENS ÷ 实测速度 + 余量` 定。
   - 未维护时的默认值在实施时定：取 0（不预留）与现行为完全一致；取 90 秒则工具步骤会更早结束。
4. **截断兜底保留。** 继续使用 9f67875 的“压缩重写 + 保留已写内容”。按 01 §4.4，抢救出的回答记为部分完成，不算已完成。
5. **长期方向。** 只要还是同步请求，180 秒就是硬上限。要彻底摆脱，需要让 Agent 在后台运行、前端轮询结果（边跑边看的进度通道已经有了），对应 01 第三阶段。

### 5.3 单次运行内的上下文

1. **修复数据分析和 SQL 结果的裁剪（优先）。**
   - 回填给模型时只按整行裁剪，不再按字符硬切：`build_datasets_json` 的回填预算与单个工具结果上限一致，保证 JSON 完整。
   - 每个数据集把 `total_rows`、实际回填行数、`truncated` 放在 `name` 之后、`columns` 之前。
   - 截断说明写清楚：“共 N 行，回填前 M 行；需要整体结论请改用汇总查询”。
   - `trim_result` 保留作最后一道保险，正常情况下不应再触发。
   - 前端使用的 AnalysisJson 不裁剪（`iv_max_chars = 0`），前端按字段名读取，字段顺序变化不影响解析；实施时用现有前端测试确认。
2. **上限做成配置项，适度放宽。**

| 内容 | 现在 | 建议起点 | 配置键（拟） |
|---|---|---|---|
| 单个工具结果 | 8000 字 | 20000 字 | `AGENT_RESULT_CHARS`（18 位） |
| 报表结果明细 | 8000 字 | 20000 字 | `AGENT_ART_CHARS`（15 位） |
| 源码回填 | 24000 字 | 保持；已有关键词定位 | — |
| SQL 明细 | 200 行 | 保持 | — |

   SQL 明细不放宽，是因为模型对上百行做心算求和不可靠，汇总应交给 SQL。

3. **运行内总量检查。**
   - 每轮调用模型前计算消息总字数。超过 `AGENT_CTX_CHARS`（15 位，建议起点 12 万字，按 §5.1 实测的读输入耗时调整）时，把最早的工具结果折叠成一行事实：工具、参数、状态、行数、结果编号。最近一次工具结果保留原文。
   - 现在可能没有前缀缓存，折叠不会造成缓存损失。如果以后开启了缓存，改为只追加、超过阈值时一次性折叠，避免每轮改动前面的内容导致缓存失效。
   - 依赖 01 §4.2 的结果记录，与 01 第一阶段一起做。
4. **任务提醒放在最后。** 01 的计划（目标、要求、已完成、缺口）由程序生成一段简短提醒，附在每轮最新一条消息的末尾，不放在消息最前面：模型对最近的内容更敏感，以后开启缓存也不会破坏前缀。

### 5.4 跨轮追问的上下文

1. **放宽历史（第一阶段）。** 同一任务带最近 4 轮、每条 2000 字，用配置项 `AGENT_HIST_PAIRS`（16 位）、`AGENT_HIST_CHARS`（16 位）替代写死的 2 轮 / 500 字。`get_recent_ctx` 与 `build_context` 两条路径同步修改。大部分追问靠这一条就能解决。
2. **结构化任务状态（第二阶段）。** 把“回答前 120 字”换成程序生成的任务状态：
   - 已确认的参数：工厂、物料、日期、公司代码等；
   - 关键结论：取自验收通过的结果记录，不取模型原文；
   - 结果编号；
   - 未完成项。

   需要新增存储（字段或表），涉及 SE11，放在第二阶段，与 01 第二阶段一起做。
3. **追问需要上一轮的数据时，重新查询，不存明细快照。** 保存查询定义（SQL 或分析计划加参数），追问时按当前用户重新执行，并标注查询时间。这样权限会按当前用户重新检查，数据也是最新的。`ZAI_SQL_LOG` 已记录执行过的 SQL，能否复用待核对字段。报表结果继续用现有的结果存储。

### 5.5 以后再做

- **用户偏好**：默认工厂、公司代码、显示单位、回答详略。新建表，内容少，用户自己可见可改；只存偏好，不存业务数据。
- **历史会话检索**：“上次查的那个工单”。按关键字检索本人历史即可，不需要向量库。
- **前缀缓存开启后**：运行内改为只追加，见 §5.3 第 3 条。

## 6. 不做的事

| 不做 | 原因 |
|---|---|
| 让模型写摘要当主要记忆 | 摘要容易丢数字，无法核对 |
| 直接调大各项上限来解决问题 | 上下文更挤、读输入更慢，截断问题本身没解决 |
| 为了隔离上下文引入多 Agent | SAP 查询链路短，同步请求下收益小（与 01 §6 一致） |
| 在任务表里存业务明细快照 | 数据会过期，权限可能已变化 |

## 9. 需要确认的事项

| 事项 | 怎么确认 | 影响 |
|---|---|---|
| 网关单次输出上限 | 问网关管理员；或发一次 `max_tokens = 8192` 的长输出请求，看是否被拒 | `MAX_TOKENS` 取值 |
| 网关是否返回 `usage` | 第 0 步上线后看审计 | §5.1 是否只能靠发送字数 |
| 是否开了前缀缓存 | 问网关管理员；或看 `usage` 里的缓存命中字段 | §5.3 第 3 条的策略 |
| 实际输出速度 | 第 0 步审计数据 | 收尾预留时间、`MAX_TOKENS` |
| 现场 `MAX_TOKENS` 当前值 | 查 `ZAI_MODEL_CFG` 中 Agent 模型那一行 | 是否已按 10.28 建议改成 8192，需要改回 |

## 10. 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 数据分析返回 1000 行 | 模型能看到“共 1000 行，回填前 M 行”；回答不把部分行加总当全量 |
| 单个结果超过上限 | 按整行裁剪，JSON 完整，不出现“已按字符上限截断” |
| 工具步骤用掉大部分预算 | 剩余时间少于预留时，不再调工具，直接写回答，回答完整 |
| 要求写长回答 | 回答在场景字数范围内；超长时压缩重写，状态为部分完成 |
| 追问“按工厂再拆一下” | 能用上一轮确认过的物料、日期和关键结论 |
| 审计 | 每次模型调用有一行 `LLM_CALL` 用量记录；思考卡不显示 |
| 网关不返回 `usage` | 只记发送字数和耗时，不报错，主流程不受影响 |
| 新配置都未维护 | 按默认值运行，与现行为一致或略宽 |

Mock 测试、ABAP 静态检查、SAP 现场执行分别记录，不互相替代。比较改造前后的指标：每次运行耗时、回答被截断的次数、超时次数、追问时答非所问的次数。
