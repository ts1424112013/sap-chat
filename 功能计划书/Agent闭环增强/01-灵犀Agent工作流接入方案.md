# 灵犀 Agent 工作流接入方案

版本：V1.0；编写日期：2026-10-28（Asia/Shanghai）。

状态：供讨论的接入设计。本次只核查本地源码、编写方案，没有修改业务代码，也没有连接 SAP 验证部署状态。

## 1. 建议怎么接

在现有 Agent 循环上增强三件事：**明确要完成什么、记录实际查到了什么、由程序检查是否完成**。

目标流程：理解目标 → 提取任务要求 → 选择受控工具 → 执行 → 记录结果 → 检查缺口 → 必要时修正 → 验收交付。

继续使用现有 UI5 前端、ABAP 后端和企业模型网关。首期采用单 Agent，以库存只读查询为试点；验证稳定后扩展到数据分析和代码分析。模型是否能稳定遵守扩展协议，需要用当前实际使用的模型单独评测。

## 2. 现有基础与实际差距

以下描述的是当前仓库里的代码，不能据此认定对应能力已经部署到 SAP。

| 环节 | 当前代码已有 | 本次建议补充 |
|---|---|---|
| 理解与路由 | 场景、意图、任务选择与领域卡 | 为试点场景生成可检查的任务要求 |
| 规划 | 提示模型形成简短计划；PLANNING 记录阶段耗时 | 把关键目标与必需结果保存为结构化清单 |
| 工具执行 | 注册表、场景与技能交集、参数与权限校验、执行分发 | 在所有执行分支统一记录结果与重试次数 |
| 观察与修正 | 工具结果回填；协议格式修复；部分错误可再次提交 | 同一错误的修正次数由程序限制；识别无进展循环 |
| 验证 | 领域卡已有自查清单；查询、参数和图表有专门校验 | 增加统一的完成验收，连接目标、工具结果与结论 |
| 任务上下文 | 按 Task 读取有限消息、摘要与结果引用 | 在本次运行中保留完整目标与关键事实，避免只剩聊天摘要 |
| 过程展示 | 已有 AgentProgress 源码、真实步骤和预览；部署文档标注尚未部署 | 复用已有思考卡显示检查通过项与未完成项 |
| 停止与继续 | 有任务 PAUSE/RESUME 状态；主 Agent 仍是同步请求 | 后续增加执行边界上的停止检查与持久化恢复 |

最关键的代码依据：`ZCL_AI_AGENT_SERVICE=>analyze_agent` 中，`action=final` 分支直接设置 `status=OK`；后续把 `OK` 映射为任务 `COMPLETED`。模型输出格式错误时保留下来的不完整正文，也可能被标记为 `OK`。因此，“产生回答”和“完成业务目标”需要分开判定。

现有库存工具、查询护栏和任务隔离应继续复用。`AGENT_MAX_ROUNDS` 当前默认 10 轮、总预算默认 180 秒；这些限制继续生效。

## 3. 用户实际会看到什么

示例请求：**“查物料 MAT001 在工厂 1000 的当前库存，并分析指定过账日的收发。”**（物料和工厂仅作示例。）

1. 灵犀提取两个要求：当前库存、指定日期收发。如果日期尚未明确且无法从上下文确定，先询问日期。
2. 读取库存快照，保存查询对象、单位、查询时点和工具执行结果。
3. 读取指定过账日收发，保存日期、方向、数量与单位。
4. 检查两部分是否查到、工厂和物料是否一致、数量是否分单位呈现。
5. 全部满足就给出结论；只查到一部分就明确写“已完成库存查询，收发查询未完成”，保留已获得的有效结果。

思考卡可以展示“读取库存 → 读取收发 → 检查结果 → 整理回答”，展开后看到真实执行情况。展示操作摘要，不展示模型内部推理。

库存快照代表查询时点余额，收发代表某个过账日的流量；不能仅凭这两份数据推导任意历史日的期初、期末库存。零行结果在查询成功且对象、范围已确认时，可以是有效结论。

## 4. 首期运行机制

### 4.1 任务要求：明确验收对象

首期由现有模型在第一次工具决策中附带简短 `plan`，继续保留 `action=tool/final` 两种动作，避免为了计划单独增加一次模型调用。

`plan` 只包含目标、对象、必需结果与可检查条件。后端校验字段类型、数量上限、场景及工具范围；简单知识问答继续允许直接回答。库存试点可将 `stock_snapshot`、`daily_movement`、`batch_stock` 作为有限的要求类型。

示意协议（新增字段均为拟议内容，目前尚未实现）：

```json
{
  "action": "tool",
  "summary": "读取当前库存",
  "plan": {
    "goal": "查询当前库存和指定日期收发",
    "plant": "1000",
    "material": "MAT001",
    "requirements": ["stock_snapshot", "daily_movement"]
  },
  "tool": "get_stock_snapshot",
  "args": {"plant": "1000", "material": "MAT001"}
}
```

计划通过后在本次运行中固定。模型不能在最后一轮删除尚未满足的要求来宣称完成；更改对象、日期或目标时，需要记录变更依据。首期要求来源只能是当前请求、明确的任务上下文和用户补充。

程序不能完整理解任意自然语言。模型可能漏提取要求，因此应在步骤摘要中展示已识别目标，允许用户纠正；“计划检查通过”不能被描述为对所有业务问题的绝对正确保证。首期只对已支持的结构化场景进行完成判定。

### 4.2 结果记录：保存事实与来源

工具每执行一次，由后端生成结果编号，记录：工具、规范化参数、状态、执行时间、对象、返回行数、是否截断、单位/货币、错误分类，以及可用的数据集引用。

这些记录来自实际执行结果，不能由模型自己声明成功。失败结果也要保留，方便决定是否修正。每个工具分支都需要适配，包括库存、SQL、受控分析和源码读取；先覆盖库存试点。

大结果继续沿用已有行数与字符限制，保留结构化摘要和引用；不能直接裁掉 JSON 尾部后当成完整事实。数据集名称、Artifact 元数据不自动等于可重读的数据快照。

### 4.3 防止空转：程序约束重复与重试

- 在同一次运行中，对工具名与规范化参数生成指纹；成功结果仍适用时直接复用，不再次查库。不同物料、日期、分页或用户明确要求刷新属于不同请求。
- 同类失败默认只允许一次有效修正；参数或 SQL 必须有实际变化。未改变输入的重复失败直接拦截。
- 权限拒绝、未支持的能力按终止性问题处理，保留现有权限规则；不能通过换表、换工具绕过。
- 只读查询的临时连接失败可以在剩余预算内重试一次；报表提交等操作沿用其独立的执行与幂等协议。
- 同样的缺口连续没有变化时提前收尾。已有全局轮数、SQL 执行次数、技能轮数和总时间预算共同生效。
- 最后一轮由后端禁止执行新工具，留给回答收尾；不能只在提示词里要求模型停止调用。

### 4.4 完成验收：模型 final 只是候选回答

模型返回 `final` 后，先执行后端检查，再确定任务状态。拟新增独立检查类 `ZCL_AI_AGENT_VERIFY`，降低主循环继续膨胀的风险。

首期检查三类事实：

1. **覆盖**：必需结果是否都有对应的成功工具结果，或者合法的空结果。
2. **口径**：工厂、物料、日期是否一致；库存时点和过账日是否区分；多单位是否分开。
3. **证据**：回答中的结构化关键结论是否引用本次有效结果；失败或截断的数据不能支撑完整结论。

建议 final 可附带 `claims`，每项列明结果编号、字段与值。后端核对引用和值；首期库存的关键数值从核验后的结构化事实生成展示，模型补充解释。不能仅靠对任意回答文字做数字匹配来宣称完成事实验证。

发现缺口且尚有预算时，把明确原因回填给模型，允许一次针对性的补查或改写。验收失败后不能绕过检查直接提交下一版回答。

| 内部验收结论 | 现有任务状态 | 对用户的含义 |
|---|---|---|
| PASS | COMPLETED | 已支持范围内的必需条件全部满足 |
| PARTIAL | PARTIAL | 有有效结果，仍有明确缺口 |
| NEEDS_INPUT | WAITING_INPUT | 缺少必须由用户补充的信息 |
| FAIL | FAILED | 无法提供符合要求的有效结果 |

`Status` 现有字段继续承担运行/错误状态，`TaskStatus` 承担业务完成状态；前后端所有把 `Status=OK` 当作“已完成”的映射都要同步调整。超时仍返回 `TIMEOUT`，但保留部分结果并标明缺口。没有任务字段的旧接口，至少在回答和步骤里明确未完成项。

## 5. 接入位置与接口策略

| 位置 | 拟改内容 |
|---|---|
| `ZCL_AI_AGENT_SERVICE` | 接入计划、结果记录、重复检查、验收与状态映射；各工具执行分支统一接入 |
| `ZCL_AI_AGENT_GUARD` | 解析和校验可选 plan/claims；继续支持旧协议、现有 JSON 修复与边界包装 |
| `ZCL_AI_AGENT_VERIFY`（新增） | 先实现库存要求与证据核验，后续按场景扩展 |
| `ZCL_AI_DOMAIN_CARDS` | 补充有限目标类型与事实引用规则，保留现有业务口径 |
| `ZCL_AI_TASK_SERVICE` | 对齐完成状态与任务摘要；首期不把运行日志塞入 pending_json |
| `ZCL_AI_AGENT_PROGRESS` | 复用进度通道，增加验收步骤；完成进度不等于业务全部完成 |
| `ChatService` / `TraceService` / `App.controller` | 读取现有 TaskStatus，统一展示全部完成、部分完成、待补充；兼容旧接口 |
| `test-server/agent-loop.js` 及相关测试 | 与 ABAP 同步协议、验收、重试和终止规则 |

首期不要求新增 OData 属性：使用已有 Answer、Message、TraceJson、TaskStatus、NeedsInput 展示结果；部署环境是否已有这些属性，实施前通过 `$metadata` 核验。详细机器可读验收结果如后续需要对外提供，再单独设计版本化字段。

计划与结果记录首期只存在本次运行内，最终留存现有审计和任务摘要。因此，首期不承诺刷新后或进程中断后继续执行未完成的循环。

本地 Mock 的库存工具命名与 ABAP 部分不同，必须先做明确映射或统一，避免测试验证了错误的工具协议。已有 `AgentProgress` 的前后端代码和部署步骤直接复用，其 SAP 实施状态需要现场确认。

## 6. 分阶段落地

### 第一阶段：单 Agent 闭环，库存试点

完成 plan、工具结果记录、防重复、有限修正、后端验收和诚实状态展示。只对支持的库存请求启用；普通问答、其他业务继续现有路径。

拟增加配置 `AGENT_CLOSED_LOOP`，默认关闭。一次运行启动时固定开关值；出现问题时关闭开关，仅影响后续运行，回到原有路径。新协议提示也必须跟随开关，旧模型输出不能被误当成已通过增强验收。

### 第二阶段：数据分析与代码分析

数据分析检查过滤条件、分组、完整性、币种单位和结果引用。需要全量统计时优先在服务端聚合；不能对裁剪后的明细样本求和，再当作全量结论。

代码分析检查源码对象、版本/读取片段、行号引用及未覆盖范围。静态阅读可以证明“某段代码存在”，不能证明程序已在 SAP 实际运行通过。

报表和 Fiori 继续复用已有参数确认、授权、运行与结果读取链路；模型调度不能跳过这些步骤。

### 第三阶段：持久化运行与真正的停止/恢复

确有长任务需求时，再增加独立的运行状态存储，保存目标、完成步骤、结果引用、剩余预算和版本。进度表是展示记录，不能替代可靠恢复所需的状态快照。

停止需要主循环在每次模型/工具调用前后检查，阻止后续动作。正在执行的外部调用能否立即中断，取决于对应接口；界面停止、任务暂停、终止后台报表必须分别定义。

多 Agent 作为后续独立评估项：只有可独立拆分、工具权限明确、结果可统一核验的任务才有价值。首期没有引入多 Agent 的必要。

## 7. 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 普通知识问答 | 可直接回答，不为了走流程强行调用工具 |
| 库存与收发都成功 | 两项要求均有证据，任务 COMPLETED |
| 库存成功、收发失败 | 有效库存保留，任务 PARTIAL，列明缺口 |
| 查询成功但为零行 | 对象和范围有效时形成空结果结论，不反复重试 |
| 料号多候选或日期必需但缺失 | WAITING_INPUT，不猜测关键参数 |
| 同参数重复查询 | 本次运行复用有效结果，实际执行次数可核验 |
| 错误后一次有效修正 | 允许继续；重复同一错误被拦截并如实收尾 |
| 权限不足 | 工具拒绝，不能换路径绕过，也不能声称查到了数据 |
| 模型首轮编造业务数据 | 无证据的 final 不能成为 COMPLETED |
| 模型删除未满足要求 | 原始任务要求保留，不能靠缩减计划通过验收 |
| 多单位或库存/收发时间口径混淆 | 验收拒绝相应结论，改正后重新检查 |
| 预算或技能轮数耗尽 | 禁止继续工具执行，保留已验证事实并标记未完成 |
| JSON 格式修复或正文抢救 | 能展示保留正文，但不能自动视为业务已完成 |
| 新开关关闭、旧接口或进度接口缺失 | 保持旧链路可用，不展示虚假的增强验收结果 |

先用可注入的模型响应与工具结果测试循环分支，再用实际模型评估协议稳定性；最后在 SAP 测试环境验证激活、字段回显、权限、真实取数和状态。Mock 测试、ABAP 静态检查、SAP 现场执行分别记录，不互相替代。

对比增强前后的任务完成准确性、未完成误报率、重复执行次数、模型调用次数与耗时。检查通过依靠实际证据；不以工具调用更多作为效果更好的标准。
