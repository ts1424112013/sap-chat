## 这个功能要解决什么

用户可以在同一个 Agent 聊天里执行报表、分析库存、查询自建表，再回到前面的结果继续追问。系统需要理解不同说法，同时把不同业务的参数、状态和结果分开保存，避免串数据、串参数或重复执行。

例如：

1. “执行一下 ZM001，并分析其结果。”
2. 报表缺参数时，展示输入表单。
3. 用户说“先看工厂 1000 的库存”，切换到库存任务，保留报表草稿。
4. 用户说“继续 ZM001”，恢复原报表参数。
5. 报表在后台执行时，用户仍可分析一张自建表。
6. 用户说“回头分析刚才的报表结果”，系统找到对应运行记录。

设计方向：**统一聊天入口，业务模块分开，任务上下文隔离，结果按编号引用。**

一个业务任务可以包含多轮消息；一条消息也可能包含多个动作。不要机械地“一条消息建一个任务”，也不要“一个聊天只做一种业务”。

## 已确定的需求边界

- 保留现有普通对话与 Agent 两种入口，不要求本期合并。
- Agent 可以在一个聊天内切换不同业务；复杂流程保留独立任务。
- 用户的自开发报表大多为静态参数，首期通过配置登记参数。
- 模型理解用户意图，后端确定可用对象、参数、权限与执行动作。
- 首期报表结果优先从已有自建结果表读取。
- 临时 ALV 内表抓取、关闭后数据恢复、通用 GUI 自动点击暂不做。
- 当前只写计划。没有开发、建表、SAP 激活、外部 Skill 安装或部署授权。

## 如何使用这些计划

后续开发按 01 中的 P0 → P1 → P2 → P3 → P4 顺序推进，每阶段用 03 验收，并更新“项目进度”中的专项进度和总览。02 是接口和数据结构的初始基线；P0 核实 SAP 版本、试点报表及结果关联条件后，可以修订，但必须写明原因和影响。

04 中的事项属于后续候选，不因为写进文档就自动进入首期开发范围。所有 ZM001、程序名、表名和运行编号示例均为说明性示例，不表示系统中存在这些对象。
