# Agent 多业务任务与报表分析：后续优化计划

版本：V1.0  
编写日期：2026-10-07（Asia/Shanghai）  
状态：候选路线图；不自动扩大首期开发范围。

## 1. 排序原则

首期先保证“理解意图、任务不串、参数可填、报表可控执行、结果可追溯”。优化项按用户价值、风险和前置条件排序。每一项进入开发前，都要补充范围、字段、权限、验收场景和回滚方案。

## 2. 优化路线

| 编号 | 优化方向 | 解决的问题 | 建议时机 | 前置条件 |
|---|---|---|---|---|
| O1 | 上下文压缩与预算管理 | 长聊天、长结果导致 256K 上下文变慢或失真 | P4 后优先 | Task/Artifact 引用和摘要已稳定 |
| O2 | 报表参数自动发现 | 每个静态报表都手工维护参数成本高 | P3 后 | 试点报表参数模型已验证 |
| O3 | 报表版本与变体管理 | 同一程序不同变式、公司代码或用户默认值不同 | P3/P4 | 报表定义和配置版本已落地 |
| O4 | 结果快照与保留策略 | 结果表更新后，历史分析无法复现 | P3/P4 | Dataset/Artifact 已有稳定编号 |
| O5 | 更多业务模块 | 库存、采购、销售、财务等业务能力扩展 | P4 后按需 | 任务路由和权限框架稳定 |
| O6 | 任务中心、计划执行和通知 | 用户需要查看运行中任务、定时执行或失败提醒 | P4 后 | 后台运行状态可可靠查询 |
| O7 | 质量评估与可观测性 | 无法量化路由、参数和分析质量 | P4 后持续 | 日志脱敏、运行链路编号完整 |
| O8 | 更细权限和审批 | 高风险报表需要按角色、组织或审批执行 | P4 后 | 业务权限责任人确认 |
| O9 | 交互体验 | 参数表单、任务切换、结果引用更直观 | P2 后持续 | 接口状态和错误码稳定 |
| O10 | 临时 ALV 数据捕获 | 报表关闭后临时内表消失，仍希望保留结果 | 后置 P2/P3 | ABAP 程序配合改造或统一出口 |

## 3. 重点优化说明

### O1：上下文压缩与 256K 管理

不把整段聊天和完整结果反复塞给模型。每次 Agent 调用按以下优先级组装上下文：当前用户消息、当前 Task 的目标和状态、最近必要消息、参数快照、结果摘要、可引用的 `ArtifactId / DatasetId`，最后才补充跨任务摘要。

建议记录四类指标：输入 token、输出 token、上下文组装耗时、被截断的结果行数。达到预算后优先压缩历史消息和结果明细，保留编号、口径、过滤条件、时间和错误信息。模型上下文是工作台，不是数据库；完整事实应在 SAP 或服务端按编号读取。

### O2：报表参数自动发现

首期静态参数用配置表登记。后续可按风险从低到高增加：

1. 从已登记程序的选择屏幕元数据生成候选参数。
2. 由开发人员确认字段语义、必填性、范围和敏感级别。
3. 保存为带版本的参数定义，运行时仍以白名单和权限为准。
4. 对动态选择屏幕、用户自定义控件和复杂事件保留人工配置入口。

不要让模型直接读取任意源码后自行执行未知参数。自动发现只生成候选，发布前必须审核。

### O3：报表变式、版本和默认值

同一个 TCode 可能对应不同变式、用户默认值、工厂或公司代码。后续把“报表定义”和“本次运行参数”分开：定义保存程序、TCode、变式和允许参数；运行保存最终展开后的值。配置变更递增 `ConfigVersion`，历史运行仍指向旧版本。

### O4：结果快照和保留

如果结果表会持续更新，分析结论需要知道使用的是哪个时间点的数据。可以按数据量选择：

- 小结果：保存脱敏快照或摘要。
- 大结果：保存查询条件、源表版本/时间、校验摘要和可重跑信息。
- 超过保留期：标记 `EXPIRED`，保留审计元数据，禁止模型假装仍可读取。

### O5：业务模块扩展

每个新业务模块都实现相同的最小契约：意图识别、任务创建/恢复、参数校验、可用工具、结果引用、权限检查、错误码和验收场景。库存、采购和自建表分析可以复用任务框架，但不要把所有业务规则塞进一个超长领域提示词。

### O6：任务中心和异步能力

后台运行稳定后再增加任务中心：按用户展示等待输入、运行中、失败和可分析结果；支持取消、重试、查看运行参数和打开结果。定时任务、邮件或企业消息通知属于独立授权范围，必须单独设计权限和失败重试。

### O7：评估和可观测性

建立脱敏测试集，覆盖“执行 ZM001”“分析库存”“回到刚才的报表”“参数缺失”“同名结果”等自然说法。关注路由准确率、错误追问率、重复执行率、结果引用正确率、P95 响应时间和人工接管率。评估集只保存必要字段，不上传业务明细。

### O8：权限和审批

把查看报表定义、提交运行、读取结果、导出结果和执行高风险报表分开授权。需要审批的报表增加 `WAITING_APPROVAL` 状态和审批人/时间/意见；审批记录与运行记录绑定，不能只靠聊天文本证明审批。

### O9：交互优化

在聊天中提供当前任务、任务切换、待填参数、运行状态和结果引用的轻量卡片。用户仍可以直接输入自然语言；卡片是减少歧义的辅助，不应成为唯一入口。对于多个候选任务，先展示标题、模块、最近时间和状态，再让用户选择。

### O10：临时 ALV 数据捕获（明确后置）

用户已经确认首期先不考虑“关闭 ALV 后恢复临时数据”。后续若业务确实需要，优先推动报表程序在生成 ALV 前提供统一数据出口，或把结果写入受控临时结果表并返回 `DatasetId`。不把通用 GUI 点击、屏幕抓取或关闭窗口后的内表恢复作为默认方案；这类方案稳定性、权限和数据完整性风险都较高。

## 4. 建议的后续迭代顺序

1. P4 验收后先做 O1，确保上下文和结果引用可控。
2. 选 2～3 个真实报表做 O2/O3 小范围验证，再决定是否推广自动发现。
3. 结果会变化的报表优先做 O4；有明确运营需求再做 O6。
4. 新业务按 O5 的模块契约逐个接入，每次只引入一个领域并补齐回归场景。
5. O7/O8 与生产灰度同步推进，避免能力扩展后才补审计和权限。
6. O10 只有在业务确认临时 ALV 是刚需，并且有 ABAP 程序改造配合时才立项。

## 5. 暂不纳入的事项

- 通用 SAP GUI 自动点击和任意屏幕录制。
- 通过模型猜测未登记 TCode、程序或表并直接执行。
- 一次性把所有聊天、所有业务结果和整张表传入模型。
- 把复杂业务规则全部写入一张不可维护的总提示词。
- 在没有权限、保留策略和审计设计前开放结果导出或外部通知。
