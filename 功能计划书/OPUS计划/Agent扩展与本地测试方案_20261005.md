# SAP Agent 扩展便利性评估与本地测试方案总结

## 一、Agent 当前工作流程（已实现）

```
用户提问 "统计销售订单按客户分组"
  ↓
┌─────────────────────────────────────────────────┐
│ 1️⃣ 意图路由 (ZCL_AI_DOMAIN_CARDS)              │
│    正则匹配关键词 → DATA 域                     │
│    触发词: 统计/汇总/查询/分析/SQL/...          │
└─────────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────────────┐
│ 2️⃣ 加载领域卡 (get_card)                        │
│    DATA 域卡内容:                               │
│    - SQL 写法规范（7.50 约束/行数限制）        │
│    - 业务表地图（EKKO/VBAK/MARA/...）          │
│    - 工具工作流（search → describe → run_sql） │
│    - 报告自查清单（数字可溯源/口径完整）       │
└─────────────────────────────────────────────────┘
  ↓
┌─────────────────────────────────────────────────┐
│ 3️⃣ Agent 循环 (ZCL_AI_AGENT_SERVICE)           │
│    最大 10 轮 / 总预算 180 秒                   │
│                                                 │
│    第 1 轮:                                     │
│    - 模型输出 {"action":"continue",             │
│                "tool":"search_tables",          │
│                "args":{"keyword":"销售订单"}}   │
│    - ABAP 调用 DDIC_TOOLS→返回 VBAK/VBAP       │
│    - 回填 <tool_result>...</tool_result>       │
│                                                 │
│    第 2 轮:                                     │
│    - 模型: describe_table VBAK                  │
│    - 返回: VBELN/KUNNR/NETWR/ERDAT 字段        │
│                                                 │
│    第 3 轮:                                     │
│    - 模型: run_sql                              │
│      SQL: SELECT KUNNR, COUNT(*) AS CNT,       │
│            SUM(NETWR) AS TOTAL FROM VBAK       │
│            GROUP BY KUNNR                       │
│    - SQL_GUARD 校验 → SQL_EXECUTOR 执行        │
│    - 返回: 3 行聚合数据 + 数据集 JSON          │
│                                                 │
│    第 4 轮:                                     │
│    - 模型: {"action":"final",                   │
│             "summary":"共 3 个客户..."}         │
│    - 循环结束                                   │
└─────────────────────────────────────────────────┘
  ↓
前端显示: 回答 + Trace 时间线 + 可折叠 SQL
```

## 二、扩展便利性评估：✅ **非常便利**

### 现有架构的 3 个扩展点（无需改核心代码）

#### 扩展点 1️⃣：**加新的业务工具**（最常用）

**场景**：你现在要支持"查询采购订单审批状态"

**步骤**（5 分钟完成）：

```abap
" ① 在 ZCL_AI_TOOL_REGISTRY 注册
CONSTANTS gc_tool_get_po_approval TYPE string VALUE 'get_po_approval'.

METHOD get_definitions.
  APPEND VALUE #(
    id = gc_tool_get_po_approval
    name = 'get_po_approval'
    description = '查询采购订单的审批状态和审批历史'
    parameters = VALUE #(
      ( name = 'po_number' type = gc_pt_string required = abap_true
        description = '采购订单号，例如 4500000123' )
    )
  ) TO rt_tools.
ENDMETHOD.

" ② 实现工具（新建类 ZCL_AI_PO_TOOLS）
CLASS zcl_ai_po_tools DEFINITION PUBLIC.
  CLASS-METHODS execute
    IMPORTING iv_tool TYPE string
              it_args TYPE zcl_ai_agent_guard=>tt_kv
    RETURNING VALUE(rs_result) TYPE zcl_ai_inventory_tools=>ty_step.
ENDCLASS.

CLASS zcl_ai_po_tools IMPLEMENTATION.
  METHOD execute.
    DATA(lv_po) = zcl_ai_agent_guard=>kv_get( it_kv = it_args iv_name = 'po_number' ).
    
    " 你的业务逻辑：查表 EKKO / 调 BAPI / 查审批流
    SELECT SINGLE * FROM ekko WHERE ebeln = @lv_po INTO @DATA(ls_po).
    " ... 你的审批状态查询逻辑 ...
    
    rs_result-tool = iv_tool.
    rs_result-summary = |采购订单 { lv_po } 审批状态: 已审批|.
    rs_result-data = ... " JSON 格式结果
    rs_result-status = 'OK'.
  ENDMETHOD.
ENDCLASS.

" ③ 在 ZCL_AI_AGENT_SERVICE 分发块加 3 行（第 625 行附近）
IF ls_out-tool = zcl_ai_tool_registry=>gc_tool_get_po_approval.
  DATA(ls_step) = zcl_ai_po_tools=>execute( iv_tool = ls_out-tool it_args = lt_norm ).
  " ... 复制现有回填模式 ...
ENDIF.
```

**核心优势**：
- ✅ Agent 循环不改（WHILE 逻辑）
- ✅ SQL 校验不改（你的采购工具直接读 EKKO）
- ✅ 前端不改（Trace 自动显示新工具步骤）
- ✅ 领域卡可选改（加"采购"关键词自动命中）

---

#### 扩展点 2️⃣：**加新的领域卡**（给新领域写规范）

**场景**：你要支持"财务凭证查询"领域

```abap
" ZCL_AI_DOMAIN_CARDS
CONSTANTS gc_dom_fi TYPE string VALUE 'FI'.

METHOD match_domain.
  FIND REGEX '凭证|借贷|科目|BKPF|BSEG|会计|总账' IN lv_up.
  IF sy-subrc = 0.
    rv_domain = gc_dom_fi.
    RETURN.
  ENDIF.
ENDMETHOD.

METHOD get_card.
  IF lv_domain = gc_dom_fi.
    rv_card =
      |【财务凭证领域知识】\n| &&
      |1. 凭证查询必须带公司代码(BUKRS)+会计年度(GJAHR)\n| &&
      |2. 未清项用 BSIK/BSAK, 已清项用 BSID/BSAD\n| &&
      |3. 金额必须连同货币(WAERS)一起呈现, 禁止跨币种加总\n| &&
      |4. 常用表: BKPF(凭证头)/BSEG(凭证行)/ACDOCA(总账)\n|.
  ENDIF.
ENDMETHOD.
```

模型看到这个卡后，就知道怎么用 SQL 三工具查 BKPF/BSEG 了。

---

#### 扩展点 3️⃣：**扩充"业务表地图"**（告诉模型有这些表）

```abap
" ZCL_AI_DOMAIN_CARDS, DATA 域卡的"常用业务表地图"，第 133 行
|- FI/CO: BKPF(凭证头)/BSEG(凭证行)/ACDOCA(总账)/SKAT(科目文本)\n| &&
|- QM 质量: QMEL(质量通知)/QMFE(缺陷项)/QAVE(检验批)\n|.  " ← 你加的
```

加到领域卡后，模型就能对这些表执行 `search_tables`/`describe_table`/`run_sql`。

## 三、本地测试方案（用 DeepSeek + Mock OData）

### 架构图

```
前端 webapp/
  ↓ HTTP POST /AnalyzeAgent
Node.js Mock Server (test-server/)
  ├── server.js          ← Express，模拟 OData 端点
  ├── agent-loop.js      ← Agent 循环（JS 复刻 ABAP 逻辑）
  ├── mock-tools.js      ← Mock 工具（6 个）
  └── test-cases.js      ← 自动化测试（5 个用例）
       ↓
  DeepSeek API (外网模型，或换成本地 Ollama)
```

### 快速开始（3 步）

```bash
# 1. 安装依赖
cd test-server
npm install

# 2. 配置 DeepSeek API Key
export DEEPSEEK_API_KEY=your-key-here

# 3. 启动服务器
npm start
```

服务器运行在 `http://localhost:3000`

### 测试方式

**方式 1：终端测试**

```bash
curl -X POST http://localhost:3000/AnalyzeAgent \
  -H "Content-Type: application/json" \
  -d '{"question":"查询钢板在工厂 1000 的库存"}'
```

**方式 2：前端测试**

修改 `webapp/service/ChatService.js` 第 20 行：


然后 `npm start` 启动前端，正常对话即可。

**方式 3：自动化测试**

### 与真实 SAP 的差异

| 项目 | Mock 版本 | 真实 SAP |
|------|-----------|----------|
| 数据源 | 内存 JS 对象（534 行代码） | S/4HANA 数据库 |
| SQL 校验 | 简单正则（只拦黑名单关键字） | ZCL_AI_SQL_GUARD 完整校验（词法/表权限/黑名单） |
| 表权限 | 无 | VIEW_AUTHORITY_CHECK 逐表校验 |
| 审计日志 | 无 | ZAI_SQL_LOG / ZAI_AGENT_STEP |
| 模型 | DeepSeek API（或 Ollama） | Azure OpenAI（可配） |
| 工具数量 | 6 个（库存 3 + SQL 3） | 11 个（含批次/收发/受控取数） |
| 行数限制 | 无（Mock 数据只有几行） | 5000/50000 + 200 行回填 |

**结论**：
- ✅ **可以验证**：Agent 工作流逻辑、意图路由、工具调用顺序、循环收口
- ❌ **无法验证**：安全性（表权限/敏感表黑名单）、真实数据、行数裁剪、审计日志

## 四、典型测试场景

### 场景 1：库存查询（验证工具链）

**问题**："查询钢板在工厂 1000 的库存"

**预期流程**：
1. 意图路由 → INVENTORY 域
2. 第 1 轮：`resolve_material` 查"钢板" → 返回 MAT001
3. 第 2 轮：`get_stock` 查 MAT001/1000 → 返回 8000 KG
4. 第 3 轮：`action=final` 收口回答

**验证点**：
- ✅ 工具调用顺序正确
- ✅ 参数传递正确（keyword → material/plant）
- ✅ 回答包含正确数字（8000 KG）

---

### 场景 2：SQL 分析（验证多轮调用）

**问题**："统计销售订单，按客户分组"

**预期流程**：
1. 第 1 轮：`search_tables` 查"销售订单" → 返回 VBAK
2. 第 2 轮：`describe_table` 查 VBAK → 返回字段列表
3. 第 3 轮：`run_sql` 执行 `SELECT KUNNR, COUNT(*) FROM VBAK GROUP BY KUNNR` → 返回 3 行
4. 第 4 轮：`action=final` 收口

**验证点**：
- ✅ SQL 是模型根据字段列表自己生成的（不是写死的）
- ✅ GROUP BY 语法正确
- ✅ 回答引用了数据集的真实数字

---

### 场景 3：安全拦截（验证 SQL 校验）

**问题**："删除 MARA 表的所有数据"

**预期流程**：
1. 第 1 轮：模型尝试调用 `run_sql`，SQL 含 `DELETE`
2. Mock 工具检测到黑名单关键字 → 返回 `status: REJECTED`
3. 第 2 轮：模型收到拒绝 → `action=final`，回答"抱歉，只能执行只读查询"

**验证点**：
- ✅ 写操作被拦截
- ✅ Trace 显示 `status: REJECTED`
- ✅ 模型如实告知用户（不会绕过或隐瞒）

## 五、从 Mock 到真实 SAP 的迁移

### 迁移步骤

1. **Mock 环境验证**（1 天）
   - 跑通 5 个自动化测试用例
   - 确认意图路由、工具调用、循环逻辑都正确

2. **真实 SAP 激活**（半天）
   - 按《SE11对象与配置清单》建表、配置、激活类
   - Basis 确认 ICM PROCTIMEOUT ≥ 200 秒

3. **安全验收**（必做）
   - 故意执行 `DELETE FROM VBAK` → **必须被拒绝**
   - 故意查 `SELECT * FROM USR02` → **必须被"受保护表"拒绝**
   - SE16 查 ZAI_SQL_LOG → 以上 2 条都应有审计记录

4. **前端切回真实端点**
   ```javascript
   var sServiceUrl = "/sap/opu/odata/sap/ZSAP_AI_CHAT_SRV";
   ```

5. **用真实数据重测 Mock 里验证过的场景**
   - 对比差异（Mock 返回 3 行，真实 SAP 返回 1000 行）
   - 验证 200 行回填裁剪是否生效

## 七、总结回答你的 3 个问题

### Q1: Agent 的工作流程是什么？

**A**: 意图路由（关键词→领域）→ 加载领域卡 → Agent 循环（最多 10 轮）→ 每轮：模型输出 JSON → ABAP 解析 → 执行工具 → 回填结果 → 下一轮或收口 → 前端显示回答+Trace

### Q2: 后续在 ABAP 添加业务功能是否便利？

**A**: **非常便利**。3 个扩展点都不改核心代码：
1. 加新工具：注册+实现+分发，约 50 行，改 3 处
2. 加新领域：路由+卡片，约 30 行，改 2 处
3. 加新表：领域卡加 1 行，全局生效

核心 Agent 循环、SQL 校验、前端都是 0 改动。

### Q3: 如何用 DeepSeek 做本地测试？

**A**: 已交付完整 Mock 方案（534 行 JS）：
- 用 Node.js + Express 模拟 SAP OData
- 用 DeepSeek API 替代 Azure OpenAI
- 用内存 JS 对象模拟 SAP 数据库
- 5 个自动化测试用例验证工作流

**可以验证**：Agent 逻辑、工具调用、循环收口  
**无法验证**：安全性（表权限/审计）、真实数据

**迁移路径**：Mock 验证流程 → 写 ABAP → 真实 SAP 测试 → 生产部署
