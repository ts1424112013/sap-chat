## 1. 要解决什么

现在每天有几封邮件要 IT 给账号加事务码权限（如 ZDPMM051、ZDPMM052）。IT 的做法是：打开邮件 → 进 SAP → SE16N 往自建权限表里加一行。所有申请目前都会通过。

目标：用户在 Gale-SAP 里自己提交申请，系统校验后直接写对应的权限表；IT 不再开邮件、不再进 SE16N。权限表不写死在程序里——以后多一张权限表，IT 在页面上登记即可，不改代码。

## 3. 方案

### 3.1 流程

1. **申请**：用户填事务码、工厂（可多个）、原因，提交。
2. **定位权限表**（后端）：
   1. 先看**事务码规则**（精确或通配，如 `ZDPMM05*`）→ 指定写哪张表、自动通过还是要审批、能否自助 `ALL`、是否禁止自助；V1.4 起指定了表的规则还可以带**自己的字段映射**（§3.2）。
   2. 没有规则 → **自动发现**：在已登记的权限表里查，该事务码出现过的表即为目标表（出现过 = 这个事务码的权限靠这张表控制）。
   3. 都找不到 → 拒绝，提示"该事务码尚未配置权限表，请联系 IT"。IT 首次手工加一行或配一条规则后，以后即可自助。
3. **校验**：事务码存在（`TSTC`）；工厂存在（`T001W`）或为 `ALL`；规则不是"禁止"；已有权限（本工厂或 `ALL` 的行已存在）→ 直接告诉用户"已有"。
4. **通过或待审批**：规则为自动 / 无规则（自动发现）→ 立即写表；规则为审批，或申请 `ALL` 而规则不允许 → 待 IT 批准。同一账号 + 事务码 + 工厂 + 表已有待审批的申请时，不再重复排队。IT 批量代加不走审批。
5. **留痕**：每次申请、通过、驳回、撤销都记一条，含写入的表名和键值。

### 3.2 表动态怎么做

**登记权限表（IT 在页面上做，一次性）**

1. 输入表名，系统运行时读取表结构：`cl_abap_structdescr=>describe_by_name( 表名 )` → `get_ddic_field_list( )`，拿到字段名、类型、长度、是否主键（`KEYFLAG`）、转换例程（`CONVEXIT`）。用 RTTI 而不是 `DDIF_FIELDINFO_GET`，避开 FM 形参名对不上的坑（踩坑清单 §2.1 第 9 条）。
2. 系统按字段名**建议映射**，IT 确认或修改后保存：

| 映射类型 | 含义 | 按字段名自动建议 |
|---|---|---|
| `TCODE` | 申请的事务码 | TCODE、TCD |
| `USER` | 目标账号 | FIR_ACCOUNT、UNAME、BNAME、USERID、USNAM |
| `WERKS` | 申请的工厂 | WERKS、PLANT |
| `CONST` | 固定值（填在映射里） | —— |
| `DATE` / `TIME` | 写入当天日期 / 时间 | ERDAT、AEDAT / ERZET、AEZET |
| `BY` | 操作人（自助 = 申请人，审批 = 审批人） | ERNAM、AENAM |
| `INITIAL` | 留空 | 其余字段默认 |

`MANDT` 不需要映射（Open SQL 自动带当前集团）。没有事务码列的表（一张表只管一个程序）也能登记，但必须配显式规则指向它，不参与自动发现。

映射约束（V1.3.1）：至少一个 `USER`；同一种映射（`USER` / `WERKS` / `TCODE` 等）可以配给多个字段，写入时都填同一个值，查重 / 撤销按全部这些字段一起比对；参与自动发现的表至少一个 `TCODE`，在任一 `TCODE` 列里找到事务码就算。**没有 `WERKS` 映射的表不按工厂控制**：不论申请了几个工厂只写一行，申请记录里工厂留空。映射（`INITIAL` 除外）只支持 CHAR / NUMC / DATS / TIMS 字段；`DATE` / `TIME` 要求字段长度够放日期 / 时间；固定值不能为空，NUMC / DATS / TIMS 字段的固定值必须是数字。

**规则自己的字段映射（V1.4）**

同一张权限表，不同事务码要填的列可能不一样：有的事务码要把工厂同时写进两列，或把账号多写一列，别的事务码不用。所以事务码规则可以带一份自己的映射：

1. **什么时候用**：事务码命中规则、规则指定了权限表、且这条规则有自己的映射 → 按规则映射写；其余一律按权限表映射（没有规则、规则没配映射、规则不指定表走自动发现）。旧规则没有映射行，行为与 V1.3 完全一样。
2. **整份映射**：规则映射覆盖表的每个字段（页面上先复制权限表的映射再改），配了就和权限表映射脱钩——以后改权限表映射不会带到这条规则（权限表配置里会提示哪些规则用自己的映射）。
3. **约束**与权限表映射相同（至少一个 `USER`、主键必须有映射、只支持 CHAR / NUMC / DATS / TIMS、固定值校验），但**不要求 `TCODE`**（不参与自动发现）。规则不指定表时不能单独配映射。
4. **各环节**：

| 环节 | 用哪份映射 |
|---|---|
| 申请 / 批量代加 | 上面第 1 条选出的映射；写行、查重、"有没有工厂列（一行还是逐工厂）"都按它 |
| 审批 | 批准时**按当前配置重新选**（与批准时重新校验账号 / 工厂 / 表一致）：当前命中的规则指向的就是申请记录里的表、且有自己的映射 → 用它；否则用权限表映射 |
| 查重 | 选中映射里的 `TCODE` / `USER` / `WERKS` 列（同一张表，不同事务码可以按不同的列查重） |
| 撤销 | 不变：按授权时记下的原始主键 `KEY_JSON` 删行，与映射无关 |
| 自动发现 | 不变：只看权限表自己映射里的 `TCODE` 列 |

5. **表结构变了**：表新增字段而规则映射里没有 → 该规则的申请报"规则 X 的字段映射缺少字段 Y，请 IT 重新保存该规则"（与权限表映射的口径相同）；配置页按当前结构列出字段（新字段显示建议值），重新保存规则即补齐。
6. **随规则维护**：删除规则一并删映射；规则改成沿用、或换了目标表而没给新映射 → 原映射作废。

**写入 / 查重 / 撤销（运行时）**

- 写入：`CREATE DATA lr TYPE (表名)` → 按映射逐字段赋值 → `INSERT (表名) FROM <wa>`；重复（subrc=4）按"已有"处理。
- 查重与撤销：按映射里的 `TCODE` / `USER` / `WERKS` 字段拼动态 WHERE，`SELECT SINGLE ... FROM (表名) WHERE (条件)` 查重、`DELETE FROM (表名) WHERE (条件)` 撤销。
- 字段有转换例程（如 `ALPHA`）时先转成内部格式再写：FM 名 `CONVERSION_EXIT_<例程>_INPUT` 用 `CONCATENATE` 拼进中转变量再动态调用（不在参数位置写表达式，踩坑清单 §2.1 第 5、9 条）。

### 3.3 要守住什么

直接用 Open SQL 写自建表不经过 SAP 权限检查——和现在 SE16N 的效果一样，但**控制全部落在程序里**；表做成动态后，配置本身也成了攻击面。必须守住：

1. **只能写登记过的表**。登记时校验：`Z` / `Y` 开头、透明表（`DD02L`）、**不能是本系统的 `ZAI_*` 表**（否则能把 `ZAI_CHAT_USER` 登记成权限表，把自己改成 ADMIN）。登记、改映射只有 ADMIN 能做，并留痕。
2. **字段名只来自 DDIC，值一律转义**。字段名拼进动态 WHERE 前再过一道字符集校验（`A–Z 0–9 _ /`），值用类内 `quote` 转义（单引号写成两个，外面再包一对；不依赖 `cl_abap_dyn_prg` 的方法签名）；值超过字段长度**拒绝而不是截断**（截断会写进一条错误的权限）。
3. **主键必须全部有映射**，否则登记失败（防止写出"半条"权限或误伤其他行）。
4. **禁止清单**：同一张表还可能控制更敏感的权限（例如 0702 用 `ZIDPPP009` 的 `TCODE='ZDPMM702'` 控制删除）。这类事务码配规则 `BLOCK`，禁止自助。`BLOCK` 只拦用户自己申请，IT 批量代加不受限（IT 本来就能 SE16N 维护）。
5. **只能给自己申请**：申请人与目标账号都取 `sy-uname`，不信任前端传值；代他人只能由 ADMIN 的批量代加完成。
6. **`ALL` 默认要审批**，按规则可放开。
7. **只有一组方法读写目标表**（`grant_row` / `revoke_row` / `row_exists`），便于审查。
8. **全量留痕**：比现在 SE16N（无记录）更可审计。状态变化记在申请行本身（同一行从 PENDING 推进到 DONE / REJECTED，DONE 推进到 REVOKED，带 DECIDED_BY / DECIDED_AT / MESSAGE）；配置变更记在表 / 规则的 CHANGED_BY / CHANGED_AT；**不另写"事件行"**。输入校验不过（事务码不存在、工厂格式不对等）只返回错误、不写记录。另建议对各权限表开 SE13 数据变更日志，把手工 SE16N 的修改也记下来（可选，需 Basis 确认参数 `rec/client`）。

### 3.4 两个入口

| 入口 | 谁用 | 做什么 |
|---|---|---|
| 申请权限（用户） | 已开通 Gale-SAP 的用户 | 侧栏会话列表下方「申请权限」：给自己申请；"我的申请"列表 |
| 权限审批（IT） | `ZAI_CHAT_USER.ROLE = ADMIN` | 侧栏「申请权限」下方「权限审批」，**红色角标 = 待审批条数**（登录后、每 2 分钟、切回页面时查一次，条数变多时弹提示）。审批对话框单独设计（自绘头部 + 下划线页签，只有内容区滚动）：待审批一张申请一张卡片，批准 / 驳回在卡片内确认（驳回原因必填）；「最近处理」看最近 30 条 |
| 权限管理（IT） | 同上 | 审批对话框右上「管理」：① 全部记录查询、审批 / 驳回、撤销；② **批量代加**（粘贴账号列表 + 事务码 + 工厂，过渡期邮件里的申请一次处理完）；③ **权限表配置**（登记表 + 字段映射）；④ **事务码规则**（通配、自动 / 审批 / 禁止、是否允许 `ALL`；V1.4：目标表下拉选已登记的表，「字段映射」卡片选「沿用权限表映射」或「本规则单独映射」） |

> 2026-10-20 补充：入口从"侧栏底部钥匙图标 + 设置里的「权限申请」页签"改到侧栏会话列表下方；审批是 IT 天天打开的界面，单独做成卡片式对话框，不再与管理四页签共用。后端接口不变。

二期可加 Agent 入口：用户说"我要 ZDPMM051 的 1000 工厂权限"或贴无权限报错，Agent 识别后弹出同一张确认卡（复用 AskCard），后端调用同一个服务。

### 4.3 SEGW / DPC_EXT

9 个 Function Import，返回类型都用现有 ComplexType `GenericResult`（`Success` / `Message` / `ResultJson`），参数全部 `Edm.String`。`ZCL_ZAI_CHAT_DPC_EXT` 的 execute_action 加对应 WHEN 分支，输出前经 `to_generic_odata`（踩坑清单 §2.3）。

| FI | 方法 | 参数 | `ResultJson` |
|---|---|---|---|
| `AuthSubmit` | POST | `Tcode`、`WerksList`、`Reason` | `ty_submit` |
| `AuthBatchAdd` | POST | `Users`、`Tcode`、`WerksList`、`Reason` | `ty_submit` |
| `AuthDecide` | POST | `ReqId`、`Approve`、`Message` | `ty_submit`（一条） |
| `AuthRevoke` | POST | `ReqId`、`Message` | `ty_submit`（一条） |
| `AuthTableSave` | POST | `Tabname`、`Descr`、`Discover`、`Active`、`FmapJson` | `ty_ack` |
| `AuthRuleSave` | POST | `TcodePat`、`Tabname`、`RuleMode`、`AllowAll`、`Active`、`Delete`、`FmapJson`（V1.4） | `ty_ack` |
| `AuthList` | GET | `Status`、`User`、`Tcode`、`Top`、`Skip` | `ty_list` |
| `AuthTableDescribe` | GET | `Tabname` | `ty_describe` |
| `AuthConfig` | GET | 无 | `ty_config`（V1.4：规则带 `ownMap` / `fields`） |

POST 参数放 URL（沿用 `StartReportRun` 已验证的通道，不依赖未实测的 T-07）。`FmapJson` 用紧凑键（`f` / `t` / `c`），单张表 20 个字段约 1 KB；若某张表字段特别多导致 URL 过长，再按批次分次保存。

V1.3 实现口径：
- 9 个分支都经 DPC 私有方法 `auth_reply` 输出：`Success` = 返回结构的 `error` 为空、`Message` = `error` 或一句话汇总、`ResultJson` = 整个返回结构的 camelCase JSON（**不压缩空值**，`total = 0`、空数组也有键）。`AuthDecide` / `AuthRevoke` 的 `ResultJson` 与申请相同，是 `ty_submit`（一条结果）。
- **V1.4**：`AuthRuleSave` 加参数 `FmapJson`（SEGW 给已有 FI 加一个 `Edm.String` 参数，**勾 Nullable**——这样旧前端不发它也不会 404，回滚前端时不用改 SEGW）。前端 `_authCall` 恒定发全部参数（没给的补空串），所以**先改 SEGW、再换前端**，否则新前端多发的 `FmapJson` 会被网关拒绝。
- **`AUTH_ENABLED` 关闭时**：`AuthSubmit` / `AuthBatchAdd` / `AuthDecide` / `AuthRevoke` 拒绝（不写权限表），普通用户的 `AuthList` 拒绝（对话框显示"尚未启用"）；`AuthTableDescribe` / `AuthTableSave` / `AuthRuleSave` / `AuthConfig` 与 ADMIN 的 `AuthList` 照常——IT 可以先登记表和规则，再打开开关。

## 6. 验收清单

**演示模式（本地，`npm start`）与本地测试**

0. 申请、我的申请、IT 管理四个页签都能走通；非 ADMIN 看不到管理页签。`cd test-server && npm run test:auth` 全过（81 项，2026-10-20）。

**申请与审批**

1. 自助申请 ZDPMM051 / 1000 → 立即 `DONE`；SE16N 看 `ZIDPPP009` 新增一行；用户能进 ZDPMM051。
2. 再申请同一组合 → `EXISTS`，不重复写；已有 `ALL` 时申请单工厂 → `EXISTS`。
3. 申请 ZDPMM051 / `ALL` → `PENDING`；IT 批准后写表；驳回后不写表。
4. 申请 ZDPMM702 → 被 `BLOCK` 拒绝，表无变化。
5. 申请一个任何权限表都没出现过、也无规则的事务码 → 提示联系 IT。
6. 前端篡改目标账号为他人 → 后端仍按 `sy-uname` 处理。
7. 非 ADMIN 调用批量代加 / 审批 / 撤销 / 登记表 / 改规则 → 被拒绝。
8. 批量代加含不存在或已锁账号 → 逐条报告，其余正常写入。
9. 撤销 → 按 `KEY_JSON` 删除对应行，记录 `REVOKED`。

**表动态**

10. 登记 `ZIDPPP009` → 页面列出全部字段，`TCODE` / `FIR_ACCOUNT` / `WERKS` 自动建议正确。
11. 新建一张字段名不同的测试表（如用户字段叫 `BNAME`、多一个必填 `ERDAT`）→ 登记、配规则后申请，写入的行字段正确（`ERDAT` = 当天）。
12. 登记 `ZAI_CHAT_USER`、标准表（如 `USR02`）、不存在的表 → 一律拒绝。
13. 主键字段漏配映射 → 保存被拒绝。
14. 工厂填超长值、或含单引号的值（如 `10'0`）→ 被拒绝，不报 SQL 错、不写错行。
15. 一个事务码同时出现在两张已登记表 → 两张表各写一行、各记一条日志。

**开关**

16. `AUTH_ENABLED` 关闭 → 申请 / 批量代加 / 审批 / 撤销被拒，普通用户的「我的申请」显示"尚未启用"，权限表无变化；IT 照常读表结构、登记表、改规则、查记录。

**V1.3 新增**

17. 登记一张没有工厂列的测试表并配规则 → 申请多个工厂只写一行，记录里工厂为空；再申请 → `EXISTS`。
18. 规则 `BLOCK` 的事务码（ZDPMM702）→ 用户自助被拒；IT 批量代加正常写入。
19. 一次审批 → 记录列表里还是那一行（状态从待审批变成已开通），不会多出一条记录。

**V1.4 新增（事务码规则带字段映射）**

20. 已登记的表多一列工厂（如 `WERKS_TO`）：规则 A 单独映射 `WERKS_TO` = 工厂，规则 B 沿用 → A 的申请两列都写工厂，B 的申请 `WERKS_TO` 留空；A 再申请 → `EXISTS`。
21. 规则 A 改成要审批，申请进待审批；审批前把 A 改回「沿用权限表映射」→ 批准时按权限表映射写（审批按当前配置选映射）。
22. 撤销按规则映射写入的行 → 按原始主键删掉，与当前映射无关。
23. 表新增字段并重新保存了权限表映射、没重新保存规则 A → A 的申请提示重新保存规则；沿用的规则 B 不受影响；重新保存 A 后恢复。
24. 删除规则 A 再新建同名规则 → 是沿用（映射随规则一起删）；规则不指定表时保存单独映射 → 被拒绝。

`ZIDPPP009` 的 SE11 截图已不阻塞开发（系统运行时读结构），但有截图可以先把一期映射配好、提前发现必填字段。

## 8. 依赖与注意

- **先修改进清单 FE-01**：本功能的写操作走 `_taskCall` 的 POST，FE-01（CSRF 失效重试时把查询串拼两遍）会让 token 过期后的第一次提交失败。按计划 bug 修复在新功能编码之前完成。
- **不依赖 T-07**：写操作不走 `_v8Call` 的 form 正文通道。
- **踩坑清单对照**：§2.1 第 7 条（CHAR ↔ string 传参 `CONV`）、第 9 / 11 条（动态调用转换例程的 FM 形参与异常名）、§2.3（`copy_data_to_ref` 下划线）、§2.4（SEGW 生成后验证字段回显）、§2.6（版本头 + 核对标记）。
- **部署**：与另外两项新功能、bug 修复一起，基于 SAP 上 2026-10-13 的基线一次部署；本功能有独立开关 `AUTH_ENABLED`，可以先部署、先配表和规则，再打开。
- **ABAP 未在 SAP 上编译**：按踩坑清单 §2.1 逐条自查过（无 offset/length 表达式、CHAR → string 处都 `CONV`、无嵌套模板、FM 只有 `GUID_CREATE` 和动态的 `CONVERSION_EXIT_*_INPUT`）；激活后先跑 §6 的第 1–4 条。
