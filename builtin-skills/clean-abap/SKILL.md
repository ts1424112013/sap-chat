# Clean ABAP 规范

按 SAP 的 Clean ABAP 风格指南检查代码质量，给出具体、可执行的改进建议。只看可读性、可维护性和正确性；上线前的安全、权限、合规审查用「ABAP 代码审查」技能。

## 先弄清前提

- 本系统是 ABAP 7.55（ABAP Platform 2020，本地部署）。7.55 以内的新语法都能用（内联声明、构造表达式、表表达式、新 Open SQL 写法、ENUM 等），ABAP Cloud 的限制不适用。哪个写法从哪个版本开始有，见「ABAP 7.55 语法边界」技能。
- **按公司现有习惯来**：
  - 命名前缀（lv_ / ls_ / lt_ / gv_ / iv_ / ev_ / rv_ / mo_ 等）是很多公司的规范，不当作问题，也不建议去掉。
  - 「用类代替函数模块」「方法不超过 20 行」「参数不超过 3 个」这类是建议，不是缺陷；对已有的老程序，只在用户想重构时提。
  - 旧写法能正常工作就不算错；只在新写的代码或用户要求现代化时，建议换成新语法。
- 看代码：有 ADT 工具就用 `adt_read_source` 读（长代码用关键字定位分段读）；没有就请用户贴代码或给文件。

## 检查类别

按下面的类别过一遍；细则和正反例见 `references/checklist.md`（检查清单）和 `references/quick-reference.md`（正反例速查）。

| 类别 | 主要看什么 |
|---|---|
| 命名 | 名字说清用途；类名用名词、方法名用动词；布尔方法用 is_ / has_ / can_；不和内置函数重名 |
| 语言 | 优先函数式写法（VALUE、COND、SWITCH、REDUCE）；不用过时语句（MOVE、ADD、TRANSLATE 等）；SELECT 用 @ 主机变量 |
| 常量 | 没有魔法数字和字符串；常量名说含义不说值（不叫 c_01、c_x）；相关常量成组 |
| 变量 | 合适时用内联声明；不用链式 DATA；字段符号只在需要时用 |
| 内表 | 表类型选对（标准 / 排序 / 哈希）；不用 DEFAULT KEY；用 line_exists 代替 READ … TRANSPORTING NO FIELDS；不读两次 |
| 字符串 | 用字符串模板 \|…\| 拼接 |
| 布尔 | 用 abap_bool、abap_true / abap_false、xsdbool( ) |
| 条件 | 尽量写正向条件；IS NOT 而不是 NOT IS；嵌套不超过 3 层；多分支用 CASE |
| 方法 | 用 RETURNING 返回一个结果；一个方法做一件事 |
| 异常 | 用基于类的异常，不用返回码；不捕获 CX_ROOT；没有空 CATCH |
| 注释 | 写「为什么」而不是「做了什么」；用 " 不用 *；删掉注释掉的代码 |
| 格式 | 一行一条语句；每行不超过 120 字符；缩进一致 |
| 测试 | 见「ABAP 单元测试」技能 |

## 严重程度（按影响分，不按规则措辞分）

- **严重**：明显会导致结果错误、丢数据、安全问题或生产故障。
- **主要**：确定的缺陷，或明显的性能、可靠性、可维护性问题。
- **次要**：局部、影响小的改进或风格不一致。

风格偏好（方法长度、命名风格、字符串写法）不能算「严重」。版本或上下文不确定时，写清缺什么信息，不要夸大。

## 输出格式

```
# Clean ABAP 检查结果

## 前提
- 对象：<程序 / 类 / 方法>
- 系统：ABAP 7.55（本地部署）
- 说明：<按公司命名习惯、只看新代码等假设>

## 小结
- 问题共 N 个：严重 x · 主要 x · 次要 x

## 问题
每条写：
- **级别 / 类别**：主要 / 内表
- **位置**：行号、语句或方法名
- **证据**：一小段原代码
- **影响**：会造成什么后果（和上下文有关的要说明）
- **建议**：最小改法，必要时给改后的代码（能在 7.55 激活；拿不准用 `adt_syntax_check` 检查）

## 做得好的地方
- …
```

只改和问题相关的代码，不要整段重写无关部分；只给建议和示例，不去改 SAP 里的代码。
