### <mark>〇-B.9 长文本通道专节（10-21，修 HTTP 414）</mark>

**原因**：OData V2 函数导入（`AnalyzeCode` / `AnalyzeAgent` / `AnalyzeTask`）的参数全部放在 URL 查询串里（方法是 POST 也一样）。URL 编码后中文每字 ×9、代码里的空格换行引号 ×3，几百行代码或一个附件就超过网关 / ICM 的 URL 长度上限，返回 414。

**做法（三个对象配合）**：

- 前端 `ChatService._prepareQuestion`：问题编码后超过 3000 字符（常量 `LONG_Q_LIMIT`）时，先 `POST /ChatTexts`（正文放请求体，不受 URL 长度限制），拿回 `TextId`，再用 `@@ZAI_TEXT:<TextId>` 作为 `Question` 调原来的函数导入；短问题照旧直连。后端没部署 `ChatTexts` 时前端直接提示“内容太长，后端还没有部署长文本通道”，不再发出去换 414。
- DPC_EXT V15.6：`CHATTEXTS_CREATE_ENTITY` 把正文写进 `ZAI_CHAT_TEXT`（记 `OWNER = sy-uname`，顺手清掉本人一天前没用掉的）；`EXECUTE_ACTION` 解析参数后，`Question` 以 `@@ZAI_TEXT:` 开头时经 `resolve_text` 换回原文（只认本人存的，读到即删）。三个函数导入的分支与返回结构都不变，SEGW 里函数导入不用改。
- CHAT_SERVICE V2.5：长内容放行后，贴过的长代码会随最近 10 条历史反复送给模型，容易超出模型上下文 → 送给模型的历史单条超过 6000 字只留开头，合计超过 16000 字后更早的不再带（`ZAI_CHAT_MSG` 里存的仍是全文；本轮问题不受影响）。两个上限是类常量 `gc_hist_msg_max` / `gc_hist_total_max`，按模型上下文大小可调。

<mark>注意：不要把 `POST /ChatTexts` 放进 `$batch`（方法里有 `COMMIT WORK`，changeset 内不允许）；前端 `useBatch` 本来就是关的。</mark>

### <mark>〇-C.5 登记报表要点（`ZAI_RPT_DEF` / `ZAI_RPT_PARAM`）</mark>

### <mark>〇-C.7 回滚口径</mark>

<mark>功能级（首选）：`ZAI_CHAT_CFG` 设 `RPT_CAPTURE_LEGACY = X`，立即回到旧口径，无需改代码；`ZRMM_IDP_0702` 这类带 `ai_capture` 的程序照常工作，没有 `ai_capture` 的报表在旧口径下取不到结果（与上线前相同）。代码级：恢复 〇-C.3 备份的 `ZCL_AI_REPORT_EXEC_SAP` V1.0f 源码并激活；两个新类可以保留（V1.0f 不引用它们）；`ZAI_RPT_RUNNER` 会因找不到 `run_captured` 出现语法错误，V1.0f 不会调用它，保留或删除都可以。新口径已经写入的 `ZAI_RPT_RESULT` 不用清，但 V1.0f 会把其中 `LINE_INDEX = 0` 的元数据行当成一行普通数据显示（多出 `__meta__` 等列），只影响回滚前产生的那些结果。</mark>

<mark>`ZRMM_IDP_0702` 新旧口径都兼容：新口径不下发 `P_RUNID`，它的 `ai_capture` 因 `P_RUNID` 为空直接返回，不会双写；`P_AICAP = 'X'` 仍下发，它的“工厂为空 → `MESSAGE TYPE E`”保护照旧生效。想让某个报表“缺参数 / 无数据”直接判失败而不是 0 行，只需在程序里加 `PARAMETERS p_aicap TYPE c NO-DISPLAY.`，并在对应处 `IF p_aicap = 'X'. MESSAGE '…' TYPE 'E'. ENDIF.`（约 5 行）。</mark>

### <mark>〇-C.8 已知边界</mark>

| 边界 | 说明 |
|---|---|
| 一次只取一份 ALV | 报表在一次运行中多次调用 ALV，以最后一次为准 |
| 自建 `CL_GUI_ALV_GRID`（Custom Container） | 不走标准采集口，取不到；需改成 `REUSE_ALV_*` / `CL_SALV_TABLE` 或单独适配 |
| 技术字段名以数字开头 | 标准类动态建表失败（社区已知问题），作业因运行时错误被取消 → FAILED |
| 行 JSON | `/ui2/cl_json` 序列化（与旧口径一致）：日期 `YYYY-MM-DD`，数值为 JSON 数字，`N` 型保持字符串；ALV 输出表里的内表 / 引用类型列（如 `COLTAB`）被跳过 |
| ALV 回调不触发 | 抑制显示后双击 / 工具栏回调不会被触发，所以 0021 的建调拨单、0161 的维护不会被误触发——这是 `REUSE_ALV_*` 的行为推断，〇-C.4 第 7 项要现场确认 |

### <mark>〇-D.2 为什么不用「SM59 + 技术用户」</mark>

- **权限会越过 Fiori 页面**。设计规则是“助手里看到的不能比 Fiori 页面里多”（Fiori 方案 §8 第 2 条）。我们自己的门禁只校验“是否已开通的助手用户”（`ZCL_AI_FIORI_REPORT_SERVICE` 的 `user_ok`），报表数据层面的权限全靠 Fiori 服务自己的检查（`S_SERVICE`、DPC 里的权限检查）。用技术用户调用，这些检查都按技术用户算，任何助手用户都能拿到技术用户能看的全部数据——不只是“按人过滤的报表”有差异。
- **现场 SM59 `TEST_Fiori` 存的是个人账号密码**：此刻所有人取数都以该账号身份运行；密码一改取数就断。验证通过后请删掉这份登录数据（〇-D.5 第 7 步）。
- **凭据透传走不通，原因不是“网关过滤了认证头”**：浏览器登录后靠会话 cookie 认证，请求里本来就没有 `Authorization` 头（现场诊断串的头名清单里只有 `cookie`）；前端只在用户自己在设置里填了 SAP 账号时才发这个头。就算有，转发的也是用户密码，不该转发。
- SSO2 断言票据也能保住当前用户身份，但要 Basis 开参数；RFC 新会话不需要任何 Basis 配置。

### <mark>〇-D.3 RFC 新会话怎么工作</mark>

```text
前端 RunFioriReport → DPC → FIORI_REPORT_SERVICE.run → ODATA_CLIENT.get
  ├ FIORI_HTTP_DEST 空（默认）
  │    CALL FUNCTION 'Z_AI_ODATA_GET' DESTINATION 'NONE'
  │      'NONE' = 系统自带目标：本系统、当前用户、新会话（不用建 SM59、不存密码）
  │      └ 新会话里：http_get → create_internal → /sap/opu/odata/...   （与 SE38 里直接调一样）
  │    RFC_CONNECTION_CLOSE（用完即关，新会话连同其中的静态状态一起释放）
  └ FIORI_HTTP_DEST 填了 SM59 目标名：create_by_destination（保留作退路）
```

SE38 里直接 `create_internal` 一直是 200，只在网关请求里失败——差别就在“外层有没有一个正在处理的网关请求”。RFC 新会话就是把内部调用放回“没有外层网关请求”的环境。**这是根据现场现象做的推断，必须按 〇-D.6 验证**；验证不过就把 `FIORI_HTTP_DEST` 填回 SM59 目标名（立即生效），再定下一步。

### 11.1 升级顺序（务必先表后类，否则类激活即报错）

2. **SE24 整类覆盖粘贴**（每类进修改模式，源码全选替换后激活，顺序无关）：

3. **SEGW 建模增量**（SE80 打开项目 `ZAI_CHAT`）：
   - 实体 `Model` 新增属性 `SkipSource`（Edm.String，可空，标签「跳过源码解析」）与 `UserHideSrc`（Edm.String，可空，标签「USER禁看源码」）；
   - 实体 `Session` 新增属性 `Pinned`（Edm.String，可空，标签「置顶」）；

### 11.5 已知注意

- **超时分块**：LONG_SRC_CHUNK 开启后单次请求可能 >2 分钟（本地 Ollama 尤甚），必要时调大 `icm/server_conn_timeout`（默认 60s）与前端侧等待预期。
- **权限收口**：V10 起 `save_model_cfg`/`test_model` 后端强制 ADMIN（此前仅前端隐藏入口）；USER 调用会收到「该操作仅管理员可执行」，属设计行为。
- **参数事务缺口未动**：`resolve_tcode` 仍只查 TSTC-PGMNA（SM30 等 OO/参数事务解析为空），为既有待办非本次回归。
