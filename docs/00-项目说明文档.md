## 一、这是什么

**SAP AI 对话助手**是一个部署在企业内网 SAP 系统上的 AI 聊天应用，让 ABAP 开发者和业务顾问直接用自然语言对话：

- **聊 ABAP**：提问里带上程序名/事务代码（如 `ZAPP0018`、`分析 表 MARC 的数据`），后端自动提取**源码 / 表结构 / 表数据样例**喂给大模型，回答贴合你系统里的真实代码与数据；
- **日常问答**：不带对象名的提问就是普通 AI 对话（代码生成、解释、翻译、写文档……）；
- **多人可用、分级管理**：管理员统一维护大模型接入、分析角色、快捷提示词（泡泡）、用户开通；普通用户开箱即用。

技术形态一句话：**SAP UI5 前端（部署为 SAP BSP 应用）+ ABAP OData 服务 + 企业内大模型网关**。全部跑在 SAP 服务器上，不需要额外的前端服务器，也不出内网。


### 2.3 认证模型（双层，排查问题前必读）

1. **SAP 网关层**：HTTP Basic（SU01 账号 + 网关密码）。前端用登录框填的账密构造 `Authorization` 头，先 GET `$metadata` 换 CSRF token，再发业务请求。开屏无凭据探测收到 401 并可能弹浏览器登录框——**这是正常行为，不是故障**。
2. **应用层**：POST `Login` Function Import。网关验密通过后，业务层只查授权表 `ZAI_CHAT_USER` 判断"是否开通 / 什么角色"（Success=X + Role）。登录成功后同一账密自动注入后续所有请求，不再弹 SAP 账密框。

应用本身**不存储任何密码**——账号锁定、密码复杂度、改密周期全部继承 SU01 现行策略。

### 2.4 角色模型

| 角色 | 能力 |
|---|---|
| **ADMIN 管理员** | 全部：维护大模型配置（含连通性测试）、分析角色、泡泡提示词、开通/停用用户、配置后端地址 |
| **USER 使用者** | 只读使用：发起对话、表数据分析、选用已启用的模型/角色/泡泡、导出会话；看不到任何维护入口 |

双保险：前端按角色隐藏入口 + 后端所有管理接口过 `v8_require_admin` 硬校验（绕过前端直调接口同样被拒）。

| 功能 | 说明 |
|---|---|

| 源码分析 | 提问带 Z/Y 程序/类/函数组名或 tcode（先查 TSTC 定位主报表），自动提取源码（含 INCLUDE 递归展开）喂给模型 |

| 主题 | 亮 / 暗双主题，V2 简约版设计基准 + 渐变画布 |
| 演示模式降级 | 后端不可达时自动切演示模式（数据落浏览器 localStorage），页面永远打得开 |
| 附件 | 输入卡可附 txt 等文本文件，内容拼入提问 |

## 五、与"纯后端 ABAP Tcode 对话框"的差异（重点）

很多 SAP 团队的默认做法是：写一个**对话框程序（Module Pool / Dynpro），挂一个 Tcode，用户在 SAP GUI 里敲 Tcode 进入屏幕操作**。本项目没有走这条路，而是"UI5 前端 + OData 后端"。差异如下：

### 5.1 架构对比

| 维度 | 纯 ABAP Tcode 对话框（Module Pool/Dynpro） | 本项目（UI5 + OData） |
|---|---|---|
| 运行载体 | SAP GUI 客户端（Windows 安装件/浏览器窗格），Dynpro 屏幕由 PBO/PAI 驱动 | 任意现代浏览器（Chrome/Edge），UI5 应用由 SAP ICF 直接服务（BSP） |
| 前后端关系 | UI 和业务逻辑都在 ABAP 里，屏幕画在 Screen Painter 上 | UI 是纯静态文件（JS/XML/CSS），业务在 ABAP 类，二者经 OData 契约解耦 |
| 部署 | 每次 UI 改动 = 改 ABAP + 传输请求 | 前端改动 = 重新构建 + 上传 zip（增量包 12 个文件约一两分钟）；后端改动仍走 SE24/传输 |
| 客户端要求 | 必须 SAP GUI；GUI 版本/补丁影响行为 | 免装任何客户端；近两年的 Chrome/Edge 即可（不支持 IE11） |
| 移动/远程 | 基本不可用 | 浏览器能打开就能用（平板/手机/家用 VPN 均可） |

### 5.2 大模型场景的适配性（核心差异）

AI 对话有几个特性，恰好是 Dynpro 的短板：

1. **响应时间长**：一次提问后端要读源码、取样数据、调大模型，几十秒到几分钟很正常。
   - Dynpro：同步对话屏幕会让 SAP GUI 整个卡在等待里，用户无法做别的，还容易被 ICM 超时切断；
   - 本项目：HTTP 请求异步挂起，前端显示思考动画、**发送键变停止键可随时中断**，迟到响应静默丢弃（后端照常落库，重开会话可见）。
2. **长富文本输出**：模型回复是 Markdown 长文 + 代码块。
   - Dynpro：长文本编辑器渲染 Markdown/语法高亮几乎做不到，只能贴纯文本；
   - 本项目：Markdown 渲染、ABAP 代码高亮（highlight.js）、代码块一键复制、流式打字机效果。
3. **数据量与裁剪**：源码 + 表样例要裁剪到 16KB 喂模型——这类"文本加工"逻辑放在 ABAP 类里没差异，但**展示**长内容（滚动、折叠、导出 Markdown）Web 天然占优。
4. **界面迭代频率**：聊天类应用 UI 打磨频繁（本项目 V4→V9 改了六轮视觉）。Dynpro 每轮都要动 ABAP 传输；本项目只动前端文件，后端对象零变更。

### 5.3 用户体验对比

| 体验项 | Tcode 对话框 | 本项目 |
|---|---|---|
| 视觉 | SAP GUI 标准控件，风格固定 | 类主流 AI 产品（DeepSeek 式布局 + V2 简约版设计基准 + 亮/暗主题 + 渐变画布） |
| 输入 | 屏幕字段，逐字段 Tab | 聊天输入卡，Enter 发送 / Shift+Enter 换行，支持附件 |
| 历史记录 | 需自建屏幕 + 自管导航 | 左侧会话栏、按用户隔离、一键导出 Markdown |
| 快捷操作 | 需自建 | 首页泡泡提示词、角色下拉，管理员在线维护全员生效 |
| 断网/后端故障 | 报错终止 | 自动降级演示模式，界面照常可看 |

### 5.4 安全与权限对比

| 项 | Tcode 对话框 | 本项目 |
|---|---|---|
| 认证 | SAP GUI 登录（SNC/SSO 取决于环境） | 同一套 SU01 账密走网关 HTTP Basic + 应用层授权表二次判定 |
| 权限 | 对象级（S_TCODE + AUTHORITY-CHECK） | 同样可用 AUTHORITY-CHECK；另外表数据分析受 `S_TABU_DIS/S_TABU_NAM` 约束（能读哪些表由权限组决定） |
| 应用内分级 | 需自建权限逻辑 | ADMIN/USER 两级，前端隐藏 + 后端 `v8_require_admin` 硬校验 |
| 密码管理 | 无涉及 | 应用零密码存储，全部继承 SU01 策略 |

### 5.5 传输与运维对比

- 两者最终都走 **SE09 工作台请求 + STMS** 传输（本项目前端是 `R3TR WAPA` BSP 对象，与传普通 ABAP 程序同一套流程，Basis 无新增学习成本）；
- 本项目前端首次全量包大（含 UI5 运行时约 8600 文件、31MB，上传约 2 小时），但**日常增量只有十来个文件**，比改 Dynpro 还快；
- 服务器要求：本前端**自带 UI5 1.130 运行时**，不依赖服务器内置 UI5 版本，760 老系统行为一致；唯一依赖是 ICF 标准 UI5 节点激活。

### 5.6 什么时候仍应选纯 ABAP Tcode

诚实说明：本项目方案并非万能。以下场景 Tcode 仍是更好的选择——

- 团队只有 ABAP 技能，没有前端/JS 维护能力，且界面**很少改**；
- 纯表单/纯事务型交互（录数据、过账），不需要富文本与异步长任务；
- 用户全都在 SAP GUI 里工作，希望零切换；
- 环境无法接受浏览器访问（极端安全策略）。

而**内容长、迭代快、要给非 GUI 用户体验的 AI 类应用**，UI5 + OData 是正确分层——这也正是本项目选它的原因。

## 七、本地运行速查

```bash
npm install        # 首次（或拷贝现成 node_modules）
npm start          # http://localhost:8080，UI5 与 highlight.js 均本地加载，离线可用
npm run build      # 构建产物在 dist/
```

- 本地开发：`ui5.yaml` 的 zui5-simple-proxy 把 `/sap` 代理到开发网关，`config.js` 的 host 留空即走代理；
- 演示模式：后端不可达自动降级，admin/123456（仅未初始化环境 + 首登强制改密）或"演示身份进入"。
